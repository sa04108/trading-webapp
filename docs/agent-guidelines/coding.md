# 제품 코드 작성·리뷰 규약

변경할 동작에서 출발해 사용자 진입점, 기존 구현, 실제 호출자를 찾는다. 데이터 호환성·권한·주문·계산의 세부 계약은 [제품 명세](../SPEC.md)에서 확인한다.

## 재사용할 범위 정하기

- 비슷한 화면·훅·함수를 찾으면 정의와 호출자를 함께 읽는다. 표시와 상호작용이 같으면 기존 컴포넌트를 쓴다. 표시가 달라도 선택 상태나 계산 정책이 함께 바뀌어야 하면 그 부분만 공유한다.
- **새 목록의 전체 선택**을 만들 때는 필터 범위, 선택 가능한 항목, 페이지를 넘겼을 때의 의미부터 정한다. 작업과 알림은 같은 체크박스와 `useListSelection`을 쓴다. 이 훅은 개별 선택을 ID 목록으로, 전체 선택을 `{ all: true, excludeIds }`로 표현한다. 페이지를 넘기면 개별 선택은 해제하고 전체 선택과 예외는 유지한다. 전체 선택 수는 서버 집계로 확인한다. [선택 훅](../../src/web/components/use-list-selection.ts)
- 작업은 현재 필터에서 종료된 이력만 숨기고, 알림은 현재 심각도 필터에 맞는 알림을 삭제한다. 새 화면도 전체 선택의 의미가 맞으면 훅을 재사용한다. 삭제 대상·필터·실패 표시는 해당 기능이 결정하고, 접근 권한과 처리 가능한 상태는 서버가 확인한다. [작업 화면](../../src/web/features/jobs/jobs-page.tsx) · [알림 화면](../../src/web/features/notifications/notifications-page.tsx)

## 가장 단순한 구현 고르기

- 현재 요구와 기존 계약을 만족하는 가장 작은 변경을 택한다. 범용 훅·래퍼·인터페이스·설정·의존성을 추가할 때는 지금 필요한 호출자나 기존 방법으로 풀 수 없는 제약을 짚는다. 예상만 하는 기능을 위한 확장 지점은 보류한다.
- 단순화하기 전에 기존 저장 데이터의 읽기 경로와 재시도 시 부작용을 확인한다. 명세가 보장하는 호환성과 주문 중복 전송 방지를 현재 요구에 포함한다.
- 화면의 서버 상태는 해당 기능의 TanStack Query 설정부터 확인한다. 작업 목록처럼 조회 범위를 `queryKey`에 담고, 상태별 폴링은 `refetchInterval`로 제어한다. 요청을 취소해야 하면 `queryFn`의 `signal`을 API 클라이언트를 거쳐 `fetch`까지 전달한다. [작업 조회](../../src/web/features/jobs/api.ts) · [API 클라이언트](../../src/web/lib/api-client.ts)
- 파일과 자식 프로세스를 다룰 때는 배포 환경의 쓰기 경로·권한·종료 동작과 Node 표준 API부터 확인한다. 예를 들어 서버 컨테이너는 루트 파일시스템이 읽기 전용이고, 일봉 판단 실행기는 `fork`로 띄운 자식의 종료를 기다린다. 순수 도메인 계산에는 필요한 값을 인자로 전달하고 OS·DB·웹 프레임워크 접근은 호출 경계에 둔다. [Compose 설정](../../compose.yaml) · [일봉 판단 실행기](../../src/server/modules/trading/infrastructure/daily-trading-engine.ts)

## 거래 판단과 실행 순서 보존하기

- 같은 일봉 매매 정책은 한 곳에서 바꾼다. 백테스트 엔진과 모의매매 판단 워커는 모두 `evaluateDailyBar`를 호출한다. 이 함수는 전략의 `onBars`를 평가하고 준비 봉 수와 데이터 결손에 따라 주문 후보를 걸러낸다. 백테스트는 다음 거래 가능한 봉의 시가를 기준으로 체결을 모사한다. 모의매매 브로커는 현재 시세와 모의 계좌 잔고로 주문을 처리한다. 새 전략 규칙은 전략에 두고 체결 방식은 각 실행 경로가 맡는다. [공통 판단](../../src/runtime/modules/strategy/domain/daily-decision.ts#L33) · [백테스트 엔진](../../src/runtime/modules/backtest/domain/engine.ts#L1216) · [모의매매 판단 워커](../../src/workers/trading-decision-child.ts#L425) · [모의매매 브로커](../../src/server/modules/trading/infrastructure/paper-trading-broker.ts#L95)
- 신호 시점까지 확정된 봉, 공개된 공시, 당시 유효한 유니버스만 사용한다. 한 백테스트에서는 전날의 현금·보유량·미체결 주문과 난수 소비 순서가 다음 거래일로 이어진다. 병렬화할 단위는 상태가 독립된 실행에서 먼저 찾는다.
- 주문 전송 후 응답을 잃으면 주문 의도와 `UNKNOWN` 상태를 보존하고 기존 주문 내역과 대조한다. 타임아웃이나 프로세스 재시작을 이유로 같은 주문을 다시 보내지 않는다. [주문 전송·복구](../../src/server/modules/trading/application/trading-service.ts#L1007) · [주문 운영 계약](../LIVE_TRADING.md)

## 성능 개선을 판단하는 근거

같은 환경과 대표 입력에서 변경 전후를 비교한다. 데이터량이나 동시 실행 수를 늘렸을 때 비용이 어디에서 증가하는지 변경 경로에 맞춰 본다.

| 변경 경로 | 먼저 확인할 값 |
| --- | --- |
| 목록 API | 페이지 크기와 전체 건수에 따른 SQL 횟수·외부 호출 수·응답 시간. 행마다 조회가 반복되는지 확인한다. |
| 일봉 백테스트 | 기존 워커의 `durationsMs`에서 로드·계산·저장·전체 시간을 비교하고 `peakRssBytes`로 자식 프로세스의 최대 RSS를 확인한다. 기존 실행 표본은 CLI의 `backtest:telemetry-report`로 조회한다. [워커 계측](../../src/runtime/workers/backtest-child.ts#L974) · [보고서 명령](../../src/server/cli.ts#L451) |
| 워커 병렬도 | 같은 서버에서 동시 작업 수를 바꾸며 처리량, CPU·메모리 사용량과 API 응답 지연을 함께 본다. |

**병렬화 후 거래 내역이 달라지면 성능 변경을 받아들이지 않는다.** 동일한 입력·데이터 스냅샷·계산 버전·시드로 실행해 체결 시각·순서·수량·가격과 잔고를 대조한다. 최종 수익률이 같아도 첫 차이가 생긴 거래일부터 상태 전달을 확인한다. [분할·전체 입력의 결과 동등성 검사](../../tests/unit/engine-chunked.test.ts)

## 리뷰에서 확인할 근거

- **금지된 import**는 기존 아키텍처 검사가 의존 규칙을 위반한 경로를 찾아내는지 확인한다. [의존 규칙](../../.dependency-cruiser.cjs) · [아키텍처 검사](../../tests/architecture/module-boundaries.test.ts)
- **거래 결과와 주문 상태**는 변경 경로의 회귀 테스트로 확인한다. 예를 들어 주문 응답 유실 시 두 번째 전송이 없는지와 대조 후 상태를 함께 본다. [주문 서비스 테스트](../../tests/unit/trading-service.test.ts#L704) · [회귀 테스트 규약](testing.md)
- **새 추상화**는 실제 호출자와 함께 검토한다. 무엇이 같은 정책이고 무엇이 호출자별 책임인지, 기존 구현을 쓰거나 직접 구현하는 것보다 새 경계가 필요한 이유를 설명한다.
