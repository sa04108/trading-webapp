# 회귀 테스트 규약

테스트 수나 커버리지보다 **중요한 결함을 실제로 검출하는 능력**을 우선한다. 이 문서는 테스트 변경과 회귀 위험이 있는 동작 변경에 적용하는 단일 규약이다. 적절한 기존 테스트는 유지한다.

## 실행 환경과 명령

저장소 루트에서 Node 24와 저장소의 pnpm/lockfile을 사용한다. `vitest.config.ts`는 Node 환경·fork pool·외부 fetch 차단을 사용한다. `better-sqlite3` 때문에 임의로 threads로 바꾸지 않는다.

| 목적 | 명령 / 범위 |
| --- | --- |
| 집중 검증 | `pnpm exec vitest run tests/unit/<파일>.test.ts` (여러 경로 가능) |
| 일반 회귀 전체 | `pnpm test` — unit, integration, architecture |
| 타입·정적 검사 | `pnpm typecheck` / `pnpm lint` |
| 패키징 계약 | `pnpm build:agent` 후 `pnpm test:agent-package` — 별도 설정의 실제 패키지 검사; 공유 빌드 출력과 직렬 실행 |
| 브라우저 상호작용 | `pnpm test:e2e` — Playwright, Vitest 범위 밖 |

watch 대신 `run`을 사용한다. 실행 전 package scripts·config·관련 CI를 확인한다. 테스트 파일은 현재 include에 포함되어야 한다. 전체 실행 비용 비교에는 같은 snapshot 조건·명령·worker 수·환경을 기록하고, 시작 실패를 테스트 실패와 구분한다.

## 계약과 계층 선택

- 요구사항(`docs/SPEC.md` 및 해당 도메인 문서), 공개 API, 도메인 불변조건에서 기대값을 정한다. 구현을 읽되 구현의 현재 반환값을 정답으로 복사하지 않는다.
- 기존 사례를 먼저 찾는다. 영구 테스트를 추가·확장하기 전에 **검출할 결함, 기존 사례가 놓치는 이유, 최소 사례**를 작업 요약에 남긴다. 새 함수나 커버리지 목표만으로 테스트를 늘리지 않는다.
- **Unit:** 계산·검증·변환 등 작은 계약. 빠르고 결정론적인 실제 의존성은 그대로 쓴다. 수익률·수량·수수료·시점 정합성은 손으로 검산 가능한 입력과 값으로 검증한다.
- **Component:** 화면의 표시·접근성·입력 계약. 현재 SSR 테스트는 초기 마크업만 보장한다. 클릭·effect·리프레시·포커스 검증을 SSR 문자열 검사로 대신하지 않는다. 상호작용은 기존 Playwright 경로를 우선 검토한다.
- **Integration:** 실제 SQL/마이그레이션, API 상태·응답·저장 효과, 인증·권한, 작업 수명주기와 경계 결합. `tests/helpers/database-fixtures.ts`의 격리 DB 또는 `createTestApp`을 활용한다. 디스크·WAL·재시작 계약에는 고유 임시 디렉터리의 파일 DB를 쓴다.
- **Architecture:** import 경계·런타임 의존성·빌드 산출물 계약. 소스 문자열 검사는 구조 자체가 계약일 때만 허용한다. 동작을 추측하는 문자열 검사로 실행 검증을 대체하지 않는다.
- 디렉터리 이름보다 실제 검증 경계가 중요하다. 같은 fixture를 쓴다는 이유로 서로 다른 계층의 검출 능력을 중복 취급하지 않는다.

## Assertion

- 결과 값, 저장된 행, 오류 코드, 상태 전이, 외부 부작용을 구체적으로 검사한다. `toBeDefined`, `toBeTruthy`, 길이, 호출 횟수만으로 중요한 내용을 검증했다고 간주하지 않는다. 존재 여부 자체가 계약이거나 후속 정밀 검사의 전제인 경우는 허용한다.
- 성공·실패·경계 중 현실적인 회귀 위험을 선택한다. 서로 다른 원인을 구별할 만큼 fixture 값을 다르게 둔다. 빈 배열에 대한 `every`, 조건부 assertion, 잘못된 경로에서도 성공하는 광범위 `catch`를 피한다.
- 내부 호출 순서·비공개 필드·HTML 속성 순서·우연한 CSS 표현에 묶지 않는다. 외부 호출 자체가 계약이면 대상·필수 인자와 결과/효과를 함께 확인한다.
- 부동소수점 허용 오차는 금액·비율의 단위와 요구 정밀도로 정한다. 구현 함수를 재호출해 기대값을 만들지 않는다. 두 실행의 동등성은 재현성 계약에는 유효하지만 계산 정확성의 독립 정답을 대체하지 않는다.
- Snapshot은 검출 대상이 명확한 작고 검토 가능한 출력에만 쓴다. 실패 원인을 이해하지 못한 일괄 갱신은 금지한다.

## Mock·Stub·Fake와 데이터

- 테스트 대상을 mock하지 않는다. 순수 함수·직렬화·빠른 실제 저장소를 습관적으로 mock하지 않는다. DB 계약은 격리된 실제 SQLite와 SQL을 우선한다.
- 네트워크, 공급자 응답, 시계, 프로세스·컨테이너 경계 등 통제하기 어려운 의존성에만 필요한 double을 둔다. mock의 반환값만 다시 검사하는 테스트는 금지한다. worker 중단·주문 거부 같은 오류 주입은 그 이후 상태와 자원 정리까지 검사한다.
- 서비스 오케스트레이션의 작은 fake는 허용하되 실제 경계 통합 검증 위치를 확인한다. 모듈 전체 mock보다 주입 가능한 좁은 경계를 우선하고 타입을 보존한다.
- fixture는 관련 입력과 기대 결과를 드러내는 최소 크기로 만든다. 공통 builder는 fresh 객체를 반환하고 차이는 각 사례에 명시한다. 큰 만능 fixture와 기대 결과를 계산하는 fixture는 피한다.
- 공급자 원문 fixture는 필드·단위·계정 구간 등 결함 재현에 필요한 차이를 보존하고 출처/재현 조건을 남긴다. 키·토큰·운영 DB·개인정보를 가져오지 않는다.

## 독립성·결정론·실행 비용

- 각 사례가 단독·순서 변경·병렬 파일 실행에서도 성립해야 한다. 공유 가변 객체, 고정 포트/경로, 모듈 상태, 환경 변수, spy, 타이머를 검사하고 `afterEach`/`finally`/fixture teardown으로 복원한다. 자식·서버를 종료한 뒤 DB와 파일을 정리한다.
- 시간은 주입 시계 또는 fake timer, 난수는 고정 seed를 사용한다. 실제 네트워크는 일반 테스트에서 금지한다. 연결 계약은 loopback과 동적 포트를 쓴다.
- 비동기는 제어 가능한 promise/event 또는 `tests/helpers/wait-for-condition.ts`처럼 종료 조건·상한·진단이 있는 대기로 동기화한다. 임의 sleep으로 완료를 추정하지 않는다. 실패를 숨기려고 retry/timeout을 늘리지 않는다.
- 실제 SQL 필요 여부와 무관한 전체 앱 기동, 반복 migration/build/process spawn, 거대한 입력을 먼저 조사한다. 독립 상태를 보장할 수 있을 때만 불변 준비물을 공유한다. 트랜잭션 테스트를 mock으로 바꿔 속도를 얻지 않는다.
- 일반 회귀, E2E, 패키징, 대용량/자원 검사를 구분한다. 무거운 검사를 기본 suite에서 옮길 때 명시적 필수/release/scheduled 실행 경로를 보존한다. 성능 실험은 기본적으로 저장소 밖 임시 검증이며, 영구화에는 반복 요구·재현 환경·의미 있는 한도·실행 지점이 필요하다.

## 변경 절차와 중복 판단

1. 관련 구현·계약·테스트·helper·config를 읽고 기존 결과를 실행해 기준선을 잡는다. 기존 실패와 환경 제약을 기록한다.
2. 사례마다 검출할 결함을 설명한다. 버그 수정은 가능하면 최소 재현의 실패를 먼저 확인한다. 원래 구현에서 재현하지 못했다면 그 한계를 적는다.
3. 기존 사례 확장이나 fixture 정리를 우선한다. 같은 계약·입력 경계·실패 원인을 검사하고 별도 검출 능력이 없을 때만 병합/삭제한다. 이름·문법이 비슷하다는 이유는 부족하다.
4. 수정·삭제 전후 계약을 대조한다. 고유 경계/실패 시나리오를 옮긴 대상 파일·사례와 이유를 diff/작업 요약에 남긴다. 실패한 테스트는 실패했다는 이유로 삭제하지 않는다.
5. 변경 파일 → 관련 묶음 → 최종 통합 snapshot의 필수 전체 검사 순으로 검증한다. 순서 의존성이 의심되면 고정 seed shuffle 등 표적 재실행을 한다. 무관한 반복 전체 실행은 피한다.
6. 중요한 assertion은 결함을 넣었을 때 실패할지 검토한다. 필요하면 임시로 비교/반올림/상태 전이를 바꾸는 선택적 mutation 실험을 하고, 실제 assertion 실패와 설정/컴파일 실패를 구분한다. 실험 코드를 복원하고 관련 검사를 다시 통과시킨다.

## 완료 기준과 금지 행동

- 금융 계산·재현성·미래정보 차단, 원천 데이터 무결성, DB 원자성, 작업 임대/동시성/복구, API·인증·권한, 공급자 속도 제한·재시도 등 변경 경로의 핵심 계약을 보존한다.
- 테스트를 통과시키기 위한 assertion 약화, 무분별한 skip, 실제 검증의 mock 대체, 기대값 임의 변경, 필수 시나리오 삭제, 무관한 운영 코드 수정은 금지한다. 구현 결함이면 테스트를 왜곡하지 말고 별도 결함으로 보고한다.
- 완료 시 변경 이유·보존한 시나리오·실행 명령·대상 snapshot·성공/실패/skip·미실행 이유를 기록한다. 대규모 정비는 전체 파일별 검토 범위와 유지/수정/병합/삭제/미해결 근거, 같은 조건의 전후 실행 비용을 남긴다. 패턴 검색이나 통과 여부만으로 검토 완료를 선언하지 않는다.

- [Microsoft: Test existing code with AI](https://code.visualstudio.com/docs/agents/guides/test-code-with-ai): 기준선, 독립 기대값, 구현 결함과 테스트 문제의 구분을 적용한다.
- [GitHub: How to write a great AGENTS.md](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/): 구체적 명령·경계·문서 위치를 사용한다. 에이전트별 규칙 사본을 만들지 않고 `AGENTS.md`에서 이 문서를 참조한다.
