# Vitest 전체 검토 및 정비 기록

## 범위와 판단 기준

기준 코드: `0a5e413ec271485032be8a1993117e4fc41910fe` (`devel`). 테스트 파일의 전체 내용, 관련 구현·도메인 계약, fixture·설정·CI를 읽고 검토했다. 검색 결과와 통과 여부는 조사 보조 자료로만 사용했다. 운영 소스, DB 스키마, 의존성, Vitest worker/timeout 설정은 변경하지 않았다.

- 전체 264개 파일: `unit` 217, `integration` 45(별도 패키지 검사 1 포함), `architecture` 2. React SSR component 검사도 현재 `unit`에 있다.
- 수정 41개: unit 23, integration 18. 나머지 223개 유지. 신규/삭제 테스트 파일은 없다.
- 주된 조치별 분류: 유지 223, 구조·격리·비용 개선 28, assertion 강화 12, 중복 병합 중심 1. 한 파일에 여러 조치를 한 경우가 있어 실제 사례 병합은 아래에 별도로 적었다.
- 기본 suite의 외부 fetch는 `tests/setup/provider-network-guard.ts`가 차단한다. SQL 계약은 실제 SQLite, 재시작/WAL은 고유 임시 경로, 프로세스 경계는 실제 child/loopback으로 확인한다.
- 재사용 fixture: `database-fixtures.ts`, `test-fixtures.ts`, `test-app.ts`, `seed.ts`, `symbol-master-seed.ts`, `backtest-preparation*.ts`, `wait-for-condition.ts`. 공통 fixture를 무조건 확장하지 않고 직접 서비스 검사에 기존 DB fixture를 재사용했다.
- 최종 파일에서 module mock 사용 3개, spy/fn 사용 81개, fake timer 사용 6개, snapshot 및 명시적 skip/todo 사용 0개. 이 수치는 검색 기반 보조 지표이며 double의 적절성은 개별 호출 경계와 결과 검증으로 판단했다.

## 정책 정립과 기존 규칙 조정

`testing.md`에 계약·계층·assertion·double·fixture·결정론·비용·변경 절차·금지 행동·완료 기준을 모았다. 공식 참고 문서 4개의 적용 근거와 이 저장소에 필요한 실제 SQL, fork pool, 외부 fetch 차단, 별도 패키징 검증을 명시했다.

`AGENTS.md`에는 테스트 변경뿐 아니라 버그 수정/동작 변경으로 회귀 위험이 생기면 **문서의 실제 내용을 읽어야 한다**는 조건부 참조만 남겼다. 기존의 영구 테스트 신중 추가, 임시 실험 분리, 의도별 검사 원칙은 없애지 않고 상세 가이드로 옮겼다. 모든 변경마다 테스트를 양산하지 않고 검출할 고유 결함을 설명하도록 통일했다. 다른 에이전트용 규칙 사본은 만들지 않았다.

중복 사례의 이전 근거:

1. `fact-repository`: 기본 저장/조회 사례 1개를 기존 빈 배열 저장 사례로 합쳤다. 동일 fixture의 정확한 roundtrip 검증과 비파괴 저장 검증을 모두 수행한다.
2. `backtest-universe-preview`: 단일 날짜 schedule 길이만 재검사한 사례 1개를 같은 rule/날짜를 쓰는 첫 응답 계약 사례로 합쳤고 `toHaveLength(1)`도 이전했다.
3. `backtest-universe-rule-run`: 재무 없이 price-only 전략을 제출하는 사례 1개는 동일 payload 조건을 이미 가진 topN=maxPositions 허용 사례에 통합했다. topN 초과 거부와 실제 child 실행/PIT는 별도 유지했다.
4. `period-validation-service`: FAILED/INTERRUPTED 각각에 중복되던 실행 버전 변경 시나리오를 독립 사례 1개로 분리했다. 두 상태 실패와 버전 실패를 모두 검사하면서 동일 버전 오류의 반복 실행만 줄였다.

삭제한 독립 사례는 3개이고 각 계약은 위 대상에 남아 있다. 파일 삭제/skip 전환은 없다. 테스트 수의 순증감은 실행 결과로 집계하며 품질 목표로 사용하지 않는다.

검증 명령과 한계:

- 변경 파일·관련 묶음 집중 실행 후 최종 전체 suite exit 0. 기준선에도 기존 테스트 실패는 없었다.
- `pnpm typecheck`: 최종 exit 0. `pnpm lint`: exit 0. 초기에는 기존 ignored `.e2e-data` 생성 번들을 임시 이동해 소스 오류와 분리했다. 최종적으로 `scripts/e2e-server.ts`가 생성하는 이 경로를 ESLint ignore에 추가하고, 원래 위치에 복원한 상태에서 기본 명령을 통과시켰다. 소스 lint 규칙은 완화하지 않았다.
- 초기 sandbox 실행의 `spawnSync node EPERM`은 테스트 시작 전 환경 오류였다. 실행 권한을 조정해 실제 기준선과 최종 결과를 확보했다. 정비 도중 발생한 구문/타입/lint 오류는 수정 후 관련 검사를 다시 통과시켰다.
- 순서 격리: 상태/타이머/인증/DB 정리를 바꾼 8개 파일을 `pnpm exec vitest run <대상 8개 파일> --sequence.shuffle --sequence.seed=17012026`으로 실행해 132/132 통과했다. 대상: wizard-draft-api, totp, wait-for-condition, symbol-master-scheduler, backtest-preparation-orchestrator, agent-coordinator, fact-coverage-store, integration/auth.
- `pnpm build`, `pnpm build:agent`, `pnpm test:agent-package --reporter=json --outputFile=<임시 JSON 경로>`: 모두 exit 0. 별도 패키지 검사 1파일/2사례 통과(실제 archive 검증 및 동봉 Node의 준비·백테스트 실행). 패키지 검사는 변경 전 별도 실행 기준선이 없어 전후 시간 비교에서 제외했다. 기본 suite와 합쳐 최종 264파일/2,758사례 통과했다. 웹 빌드는 기존 500 kB 초과 chunk 경고를 출력했으며 코드 분할은 이번 범위에서 변경하지 않았다.

## 검증 범위의 한계와 잔여 과제

- 264개 파일 중 미검토 파일은 없다. 이 기록은 확인한 문제를 정비한 결과이며 모든 가능한 결함/비결정성을 증명하지 않는다.
- `agent-client-diagnostics`의 비공개 finalizer 접근은 손상 파일·outbox·ACK 실패 주입을 위해 유지했다. `distributed-universe-preparation`의 비공개 연결 조회도 동기화에 한정했다. 공개 프로세스 통합 검사는 별도로 유지하며, 이 seam 제거는 운영 코드의 주입 경계 재설계가 필요하다.
- SSR component 검사와 순수 live helper 검사는 실제 브라우저 클릭/effect/포커스나 SSE hook의 전체 상호작용을 보장하지 않는다. 이번에는 운영 UI를 변경하지 않아 Playwright E2E를 실행하지 않았다. 해당 동작 변경 시 기존 E2E 경로에서 검증해야 한다.
- 실제 SQL/child/runtime 버전 그래프 검사는 실행 비용이 커도 고유한 배선·트랜잭션·복구 결함을 검출하므로 유지했다. 더 큰 성능 개선은 파일별 실행 프로파일과 fixture 경계 재설계가 필요하다. 필수 검사를 기본 suite에서 숨기지 않았다.
- 전체 suite의 전후 각 1회 측정이므로 호스트 부하·캐시 변동을 포함한다. wall time 차이를 안정적인 성능 보장으로 해석하지 않는다. 모든 변이 조합을 검사한 mutation score는 산출하지 않았다.
- `devel`에는 자동 검사 workflow가 없고 publish/deploy는 `main` 대상이다. 로컬 검증 근거를 사용하며 main 병합·배포 및 Windows/Docker 플랫폼 검증은 수행하지 않았다.
