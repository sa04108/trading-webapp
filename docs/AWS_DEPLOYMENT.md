# AWS 확장 방향

현재 제공하는 운영 방식은 미니 PC의 Docker Compose다. AWS 기능·리소스·배포 스크립트를 지금 추가하지 않는다. 이후 일부 서비스를 연동하거나 서버 전체를 이전할 때도 **서버 컨테이너 이미지와 기존 앱 환경변수 계약**을 재사용한다. 앱 전용 systemd 유닛·SSH 배포를 다시 만들지 않는다.

## 현재 유지할 경계

- `config.env`는 로컬 Compose 운영자의 단일 설정 원본이다. 앱은 이 파일을 직접 읽지 않고 환경변수만 읽는다. Compose의 도메인·Traefik·이미지·CPU/메모리 값은 앱에 전달하지 않는다.
- 서버 이미지는 비 root로 실행하고 HTTP 3000, readiness, SIGTERM, 표준 출력 로그를 제공한다. 영속 파일은 `/var/lib/quant-platform`에 모은다. 같은 이미지 digest를 다른 컨테이너 실행 환경에서도 사용한다. 현재 서버 이미지는 linux/amd64이므로 AWS 실행 아키텍처도 이에 맞춘다.
- 현재 `compose.yaml`과 `scripts/server.sh`는 로컬 운영 도구다. AWS 작업 정의·네트워크·권한·저장소는 향후 별도 배포 구성에서 관리한다. 로컬 도구에 AWS 분기나 사용하지 않는 변수를 미리 넣지 않는다.
- AWS의 비밀값은 Secrets Manager/Parameter Store 등 배포 환경의 저장소에서 동일한 앱 환경변수로 주입한다. 로컬 config.env와 AWS 비밀을 동시에 수동 관리하는 구조로 만들지 않고, 이전 시 관리 원본을 명확히 전환한다. AWS 내부 실행은 IAM role을 우선 사용한다.

## 일부 AWS 서비스만 연결하는 경우

미니 PC 서버와 로컬 DB는 유지하고 실제 요구가 생긴 기능만 추가한다.

| 목적 | 후보와 추가 범위 |
| --- | --- |
| 백업·불변 스냅샷 보관 | S3. 기존 DB 백업 세트를 완성·검증한 뒤 업로드하며 업로드 실패와 보존 정책을 별도로 처리한다. SQLite 파일을 S3에 직접 열어 쓰지 않는다. |
| 로그 수집 | CloudWatch Logs. 컨테이너 로그 전달 계층에서 설정하고 버퍼·전송 실패·디스크/메모리 예산을 정한다. 백테스트 계산 경로가 로그 전송을 기다리지 않게 한다. |
| 추가 계산 장치 | 현재 Agent 프로토콜을 사용하는 컨테이너. 서버와 실행 버전·리스·데이터 스냅샷 계약을 유지하고 장치 수명과 비용 제한을 별도로 설계한다. |

AWS SDK를 쓰는 기능이 생기면 해당 모듈의 설정과 구현을 추가한다. 현재 로컬 파일 구현이 S3 등으로 자동 교체 가능한 것은 아니므로 경로·내구성·실패 처리 계약도 함께 검토한다. 미니 PC의 AWS 인증은 단기 자격증명/역할 연계 가능성을 먼저 검토하고 필요한 최소 권한만 부여한다. AWS 계정 키를 공통 config 예시에 미리 추가하지 않는다.

## 서버 전체를 이전하는 경우

현재 DB는 운영·계산용 **SQLite WAL 파일 두 개**이고, 작업 조정과 일부 상태도 단일 서버를 전제로 한다. 따라서 컨테이너 실행 환경만 바꾸며 다중 서버나 임시 파일 저장소를 쓰면 안 된다.

| 후보 | 판단 |
| --- | --- |
| EC2 + Docker Compose | 현재 운영 방식과 가장 가까운 이전 경로다. 같은 이미지와 config.env를 사용하고 named volume의 실제 저장소를 영속 EBS 위에 둔다. 이후 관리형 배포로 옮기는 중간 단계로 사용할 수 있다. |
| ECS on EC2 + EBS | AWS에서 배포·재시작을 관리하려는 경우의 우선 검토안이다. ECS task/service로 앱을 실행하고 데이터가 있는 호스트에 배치한다. EBS 연결·마운트·재연결과 단일 실행 보장은 별도 인프라 구성이 필요하다. |
| ECS Fargate | 현재 구성의 즉시 대체안으로 택하지 않는다. 현재 SQLite를 임시 태스크 디스크나 EFS/NFS에 올리는 것은 영속성 또는 WAL 공유 메모리·잠금 계약에 맞지 않는다. 영속 저장소와 데이터 접근 구조를 먼저 설계해야 한다. |

ECS 경로는 단일 서버를 전제로 준비한다. `desiredCount=1`만으로 배포 중 중복 실행이 방지되지는 않으므로, 기존 task를 중지하고 데이터 마운트/쓰기 주체를 확인한 뒤 DB 준비와 새 task 기동을 진행해야 한다. EC2 교체 시 EBS를 보존하고 가용 영역 제약·재연결·권한·기동 차단을 설계한다. task별 새 볼륨 생성이나 빈 경로 기동을 기존 데이터 복구로 간주하지 않는다. 중단 없는 교체·다중 서버가 필요하면 공유 DB뿐 아니라 스케줄러·리스·세션·파일 저장 책임도 먼저 바꿔야 한다.

HTTPS는 기존 Traefik 또는 ALB+ACM 중 운영 요구에 맞게 결정한다. ALB를 선택하면 WebSocket/SSE 연결·idle timeout·종료 대기와 신뢰할 프록시 범위를 검증한다. GHCR 이미지는 그대로 사용할 수 있으며 ECR로 복제할 경우 서버·Agent digest 참조와 설치기의 레지스트리 허용 정책을 확인한다. AWS 환경의 자원 크기는 해당 인스턴스에 맞춰 정하며 G3 값을 자동 적용하지 않는다.

구현 시에는 배포 인프라를 Terraform 또는 CDK 등으로 별도 관리하고, 후보 이미지 고정 → 기존 쓰기 중지 → 영속 데이터 확인 → DB 준비 → readiness 검증 순서를 유지한다. 실제 이전 승인 전에는 운영 DB를 건드리지 않는 임시 데이터로 종료·재기동·인스턴스 교체·배포 실패 복구를 검증한다.
