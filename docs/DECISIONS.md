# DECISIONS

명세 밖 선택과 이유를 기록한다. (스펙 §37)

## D-001: 개발 머신 Node 22, 운영은 Node 24 유지

- **변경 내용:** `engines`는 스펙대로 `>=24 <25`를 유지하되 `engine-strict`를 켜지 않아 Node 22 개발 머신에서 설치·테스트를 허용한다.
- **이유:** 현재 개발 PC(Windows)에 Node v22.14.0이 설치되어 있고, 사용하는 네이티브 모듈(better-sqlite3, argon2, @duckdb/node-api)은 22/24 모두 prebuild를 제공한다.
- **대안:** 개발 머신에 Node 24 설치 — 사용자 시스템 변경이라 보류. 필요 시 사용자가 직접 업그레이드.
- **보안/비용/마이그레이션 영향:** 없음. 운영 배포 절차(§22)는 그대로 Node 24 LTS.

## D-002: 1차 증권사 어댑터는 키움 REST API, 토스는 사전신청 승인 후

- **변경 내용:** `RestBrokerMarketDataSource`의 1차 구현을 키움 REST API로 한다. 자격증명(App Key) 발급 전까지 어댑터는 구조·단위 테스트만 검증하고 비활성 상태로 둔다.
- **이유:** 토스증권 Open API는 사전신청 대기 중. 키움 REST API는 리눅스에서 직접 호출 가능함을 확인(2026-07-25, openapi.kiwoom.com).
- **대안:** 토스 대기 — 데이터 수집이 지연됨. CSV/Parquet import가 MVP 검증 경로이므로 어댑터 지연은 MVP 완료를 막지 않는다.
- **영향:** 도메인·애플리케이션 코드 영향 없음(Port/Adapter). 스펙 13장에 반영 완료.

## D-003: 서버 코드는 상대 import, 웹은 Vite alias

- **변경 내용:** 서버(tsc 컴파일)는 경로 별칭 없이 상대 import를 사용한다. 웹은 shadcn 관례대로 `@/` → `src/web`, `@shared/` → `src/shared` alias를 사용한다.
- **이유:** tsc는 별칭을 런타임 경로로 재작성하지 않으므로 tsc-alias 등 추가 도구 없이 dist가 그대로 동작하게 한다.
- **영향:** 없음. dependency-cruiser 규칙은 경로 기반으로 동일하게 적용.

## D-004: TOTP 라이브러리 otpauth, ID는 ULID

- **변경 내용:** TOTP는 `otpauth`(무의존성, RFC 6238), ID 생성은 `ulid` 사용. QR 대신 CLI가 otpauth:// URI와 base32 secret을 출력한다.
- **이유:** 스펙은 라이브러리를 지정하지 않음. otpauth는 유지보수 활발·zero-dep. ULID는 스펙 예시 `bt_01J...` 형식과 일치.
- **⚠️ TOTP 부분 폐기 (D-014):** TOTP 자체를 제거하면서 `otpauth` 의존성도 함께 뺐다. ULID 결정은 그대로 유효하다.

## D-005: 차트 시리즈 서버 측 다운샘플링 (~1,000 포인트)

- **변경 내용:** 자산 곡선·드로다운 API 응답을 LTTB로 최대 1,000포인트로 다운샘플한다. 원본 전체 시리즈는 export로 제공.
- **이유:** Recharts(SVG)는 수천 포인트 이상에서 모바일 성능이 급락한다. (스택 검토에서 확인된 한계)
- **영향:** UI 정확도 손실은 시각적으로 무시 가능. 지표 계산은 항상 전체 시리즈로 수행.

## D-007: TypeScript 5.9 고정 (TS 7 네이티브 컴파일러 회피)

- **변경 내용:** 2026-07 기준 최신 TypeScript 7.0(네이티브)을 쓰지 않고 `typescript@~5.9.0`으로 고정한다.
- **이유:** typescript-eslint 8.65가 TS 7.0을 지원하지 않아 lint 게이트가 깨진다 (공식 지원은 TS ≥7.1 예정).
- **대안:** TS 6 API 호환 모드 — 검증 비용 대비 이득 없음. typescript-eslint가 TS 7을 지원하면 업그레이드.
- **영향:** 컴파일 속도 외 기능 차이 없음.

## D-008: better-sqlite3 v12 고정

- **변경 내용:** better-sqlite3를 v13이 아닌 `^12`로 고정한다.
- **이유:** v13은 개발 머신의 Node 22용 prebuild를 제공하지 않아 소스 컴파일(Visual Studio 필요)로 폴백한다. v12는 Node 22/24 prebuild 제공.
- **영향:** 운영(Node 24)에서도 v12 prebuild 사용. Node 24 전환 후 v13 업그레이드 가능.

## D-006: KR 세션 캘린더는 MVP에서 단순화

- **변경 내용:** KR 정규장 09:00–15:30 KST, 주말 제외만 반영. 공휴일·조기폐장은 미반영하고 결과 화면 경고(§9.4)에 명시한다.
- **이유:** 휴장일 캘린더 유지관리는 MVP 범위를 넘는다. 데이터가 없는 날은 봉이 없으므로 백테스트 정확성에는 영향이 제한적.
- **영향:** coverage의 "누락" 판정이 공휴일을 누락으로 오인할 수 있음 — coverage 화면에 한계 문구 표시.
- **추가 (PR #1 리뷰 반영):** 세션이 정의되지 않은 시장(US)의 import 는 명시적으로 거부한다. KR 세션으로 빈 1h 집계를 만들고 완료로 위장하던 문제의 수정 — US 지원 시 DST 를 포함한 세션 정의가 선행돼야 한다.

## D-009: 스펙 §12 스키마 편차 — 소비자 없는 테이블은 만들지 않는다

- **변경 내용:** §12 의 `strategies`/`strategy_versions` 테이블은 만들지 않고(전략은 코드 등록식 레지스트리가 유일한 출처, §2.5), 초기 스캐폴딩으로 생성됐던 `application_settings`/`data_sync_jobs` 테이블은 읽고 쓰는 코드가 없어 제거했다. (제거 마이그레이션은 D-015 의 스쿼시로 흡수됐다 — 해당 테이블은 이제 생성되지 않는다.)
- **이유:** 아무도 소비하지 않는 스키마는 "무결(더할 것도 뺄 것도 없는 상태)" 원칙 위반이며, 실제 사용 시점의 요구와 어긋난 채 굳어진다.
- **영향:** 증권사 동기화 작업 이력(§13)이 필요해지면 그 시점의 요구대로 테이블을 신설한다.

## D-010: 파괴적 마이그레이션과 자동 롤백의 짝 맞춤

- **변경 내용:** deploy.sh 는 서비스 재시작(=마이그레이션 적용) 직전에 SQLite 스냅샷을 만들고, health check 실패로 롤백할 때 스냅샷을 함께 복원한다 — 이전 릴리스 코드가 새 스키마(예: 삭제된 컬럼)를 만나 `no such column` 으로 죽는 "명목상 롤백"을 막는다.
- **운영 규칙:** 컬럼·테이블 삭제 같은 파괴적 스키마 변경은 코드가 해당 참조를 중단한 **다음** 릴리스에 싣는 것을 원칙으로 한다 (expand-contract). 스냅샷 복원은 이 규칙이 지켜지지 않았을 때의 안전망이다.
- **보존:** 스냅샷은 성공 배포 후에도 최근 5개를 남긴다. health check 는 통과했지만 그 뒤에 문제가 드러나 **수동** 롤백(§30 10단계, §35 runbook)을 하는 경우에도 짝이 맞는 스키마로 되돌아가야 하기 때문이다. backup.sh 의 30일 정리 규칙은 `backup-*` 디렉터리만 훑으므로 deploy.sh 가 직접 회전시킨다.
- **영향:** 스냅샷~롤백 사이의 쓰기는 유실된다. 단일 운영자가 배포 중인 수 초의 창이라 실질 위험은 없다. 수동 롤백 절차는 배포 성공 시 deploy.sh 가 그대로 출력한다.

## D-011: 감사 로그 보존 기간은 정책이므로 설정으로 노출한다

- **변경 내용:** M15 의 정리 작업이 감사 로그를 90일 하드코딩으로 삭제하던 것을 `AUDIT_LOG_RETENTION_DAYS` 설정으로 뺐다 (기본 90, `0` 이면 삭제하지 않음). 보존 기간이 켜져 있으면 부팅 로그에 명시한다.
- **이유:** 스펙 §16 이 요구하는 것은 감사 기록의 *생성*이지 파기가 아니다. 세션·로그인 시도 정리는 명백한 위생 작업이지만 감사 로그 파기는 정책 결정이고, 정책은 코드 상수에 숨지 않아야 한다.
- **영향:** 기본 동작은 종전과 같다. 감사 기록을 남겨야 하는 요구가 생기면 `AUDIT_LOG_RETENTION_DAYS=0` 으로 끈다 — 대신 테이블은 무한히 증가한다.

## D-012: 스펙 §32 편차 — maxPositions 는 전략 파라미터가 아니라 요청 필드

- **변경 내용:** §32 의 `HourlyBreakoutParameters` 에 있던 `maxPositions` 를 요청의 `risk.maxPositions` 로 옮기고 전략 버전을 1.2.0 으로 올렸다 (I3). 엔진은 더 이상 전략 파라미터 가방에서 이름으로 상한을 찾지 않는다.
- **이유:** 포지션 상한은 엔진의 리스크 제약(§9.2-6)이지 전략 로직의 입력이 아니다. 이름 규약("maxPositions" 키가 있으면 쓰고 없으면 10")은 계층 간 보이지 않는 결합이었고, 그 이름을 쓰지 않는 전략은 조용히 상한 없이 돌았다. §15 의 요청 예시 자체가 이 파라미터를 담고 있지 않다.
- **호환성:** 이미 저장된 요청은 복제 시 `rebaseStoredRequest` 가 `parameters.maxPositions`(없으면 기존 기본값 10)를 `risk` 로 옮기고 전략 버전을 현재 값으로 재기준한 뒤, 무엇이 바뀌었는지 경고로 알린다 (I9). 복제는 §10 이 지정한 중단 작업 복구 경로이므로 스키마 변경으로 막히지 않는다.
- **영향:** 위저드가 자본 단계에서 상한을 명시적으로 입력받는다. 향후 전략 버전이 올라가도 과거 작업의 복제는 계속 동작하며, 재현이 아닌 재실행임을 경고로 구분한다.

## D-013: 로컬 백업 보관은 일수가 아니라 용량으로 제한한다

- **변경 내용:** backup.sh 의 `-mtime +30` 회전을 총 용량 상한으로 교체했다 — `BACKUP_MAX_TOTAL_MB`(기본 10240) 를 넘으면 가장 오래된 백업부터 삭제한다. `BACKUP_MIN_KEEP`(기본 2) 아래로는 줄이지 않고, 백업 생성 **전에** 직전 백업 크기만큼 여유를 미리 확보한다.
- **완성본만 센다:** 백업은 `.incomplete-<stamp>` 에 쓰고 끝까지 성공했을 때만 `backup-<stamp>` 로 rename 한다. `BACKUP_MIN_KEEP` 은 개수를 세는 규칙이므로, 반쪽 디렉터리가 `backup-*` 로 보이면 그 보장이 빈 껍데기로 채워진다.
- **이유:** 호스트 디스크는 40GB 고정인데(§18 Micro) 백업 1벌의 크기는 시간봉 Parquet 과 함께 자란다. "30일" 은 개수만 묶을 뿐 총량을 묶지 못해, 데이터가 커지면 백업이 디스크를 채우고 애플리케이션까지 같이 죽인다. 제약이 용량이면 정책도 용량이어야 한다.
- **스펙 관계:** §31 의 30일 lifecycle 은 **S3** 규칙이고 그대로 유지한다 — S3 는 이 제약을 받지 않는다. 로컬 30일은 그 정책을 제약이 다른 곳에 복사한 것이었다.
- **영향:** 보관 "기간" 이 데이터 크기에 따라 달라진다. 데이터가 커질수록 남는 백업 벌수가 줄어드는 대신 디스크가 넘치지 않는다 — 복원 가능한 백업 0벌보다 얕은 이력이 낫다. 생성 전 선정리 때문에 정상 상태 사용량은 상한 근처에서 진동한다.

## D-014: TOTP 2단계 인증 제거 — 스펙 §16 편차

- **변경 내용:** 스펙 §16 이 요구하는 비밀번호 + TOTP 2단계 인증을 제거하고 비밀번호 단일 단계로 바꿨다. TOTP secret·복구 코드·`otpauth` 의존성·`POST /auth/totp/verify` 라우트·로그인 2단계 화면을 모두 없애고, `users.totp_secret`·`users.totp_enabled`·`users.recovery_code_hashes_json`·`sessions.pending_totp` 컬럼을 삭제했다. (삭제 마이그레이션은 D-015 의 스쿼시로 초기 마이그레이션에 흡수됐다 — 해당 컬럼은 이제 어느 시점에도 생성되지 않는다.)
- **이유:** 이 플랫폼은 WireGuard VPN 내부에서만 접근하는 단일 관리자용 도구다. 망 경계에서 이미 접근이 제한되고 그 위에 사용자 이름·비밀번호가 있는 상태에서 TOTP 는 방어를 의미 있게 늘리지 않는 반면, 인증 앱 등록·복구 코드 보관·기기 분실 시 복구 경로라는 운영 부담을 상시로 지운다.
- **기능 플래그가 아니라 제거인 이유:** `totpEnabled` 를 끄는 선택지도 있었지만, 아무도 켜지 않는 경로를 남기면 검증되지 않은 채 굳는다 (D-009 와 같은 이유). 쓰지 않을 코드는 남기지 않는다.
- **남는 방어:** Argon2id 해시, 비밀번호 14자 이상 강제(CLI), 로그인 실패 5회/15분 잠금, 사용자 부재 시 타이밍 균등화, 세션 유휴 12시간·절대 7일 만료, httpOnly·Secure·SameSite=Strict·signed 쿠키, Origin==Host CSRF 검사, 127.0.0.1 bind + VPN 경계. 비밀번호 최소 길이 14자는 이제 유일한 비밀 값의 강도를 결정하므로 낮추지 않는다.
- **세션 고정:** 회전 시점이 TOTP 검증에서 로그인 성공으로 옮겨갔을 뿐, 로그인마다 새 세션 ID 를 발급하는 것은 그대로다. 서버가 발급하지 않은 쿠키 값은 어느 시점에도 인증된 세션이 되지 않는다.
- **D-010 예외:** D-010 은 파괴적 스키마 변경을 코드가 참조를 끊은 *다음* 릴리스에 싣는 expand-contract 원칙을 세웠다. 이 변경은 코드 제거와 DROP COLUMN 을 한 릴리스에 함께 실었다 — 운영 서버가 아직 구축되지 않아 보호할 데이터가 없고 되돌릴 이전 릴리스도 배포된 적이 없다. 원칙 자체는 유효하며, 운영 시작 후에는 지킨다.
- **되돌리기 비용:** 실거래 단계에서 2단계 인증 요구가 생기면 재구현이 필요하다 — 의존성 추가, 컬럼 복원 마이그레이션, 2단계 로그인 흐름 복원. 그 시점의 요구(TOTP 인지 passkey 인지)에 맞춰 새로 설계하는 편이 지금 쓰지 않는 경로를 유지하는 것보다 낫다고 판단했다.
- **설계 문서:** `docs/superpowers/specs/2026-07-26-totp-removal-design.md`

## D-015: 배포 전 마이그레이션 스쿼시 — 이력은 0000 하나로

- **변경 내용:** 마이그레이션 0000~0007 과 대응 스냅샷을 모두 지우고 현재 스키마 기준의 단일 마이그레이션(`0000_ambiguous_bedlam.sql`)으로 다시 생성했다. `migrations/` 는 297KB → 42KB 가 됐다 (스냅샷 8개가 272KB 를 차지했다).
- **이유:** 한 번도 배포된 적 없는 마이그레이션 이력은 보존 가치가 없다. 중간 단계 스키마로 되돌릴 대상 DB 가 존재하지 않으므로, 8단계 이력은 저장소 용량과 읽는 사람의 주의만 소모한다.
- **런타임/도구 역할 구분 (소스 확인):** `drizzle-orm/migrator` 는 `meta/_journal.json` 과 각 `<tag>.sql` 만 읽고 `*_snapshot.json` 은 전혀 읽지 않는다. 스냅샷은 `drizzle-kit generate` 가 다음 diff 를 만들 때만 쓰며 최신 1개로 충분하다. 반대로 `.sql` 은 journal 에 항목이 있으면 반드시 존재해야 하고(없으면 부팅 시 throw), 새 DB 의 스키마를 만드는 유일한 출처다.
- **왜 지금이 마지막 기회인가:** `sqlite-core/dialect.cjs` 의 적용 판정은 해시가 아니라 journal 의 `when` 타임스탬프다 (`Number(lastDbMigration[2]) < migration.folderMillis`). 스쿼시한 마이그레이션은 기존 DB 에서 재실행돼 `table already exists` 로 죽는다. 즉 스쿼시는 **모든 기존 DB 를 버릴 수 있을 때만** 가능하며, 운영 서버 구축 이후에는 선택지가 사라진다.
- **영향:** 로컬 개발 DB(`data/app.sqlite`)를 폐기했으므로 관리자 계정을 `pnpm cli admin:create` 로 다시 만들어야 한다. 운영 데이터는 없었다.
- **검증:** 스쿼시 전 스키마(0000~0007 누적 적용)와 스쿼시 후 새 DB 의 `sqlite_master` 를 비교해 32개 객체 중 31개가 완전히 동일함을 확인했다. 유일한 차이는 `backtest_jobs` 의 **컬럼 순서** — 나중에 `ALTER TABLE ADD COLUMN` 으로 붙던 `dataset_version`·`dataset_hash`·`progress_label` 이 이제 선언 순서대로 들어간다. 컬럼 이름·타입·NOT NULL 집합은 동일하고, 코드에 `SELECT *` 나 위치 기반 INSERT 가 없어(drizzle 은 항상 명시적 컬럼 목록을 생성한다) 영향이 없다. 앞으로 모든 DB 가 같은 마이그레이션에서 생성되므로 순서도 일관된다.

## D-016: WireGuard·Caddy → Tailscale — 스펙 §23~§27 편차

- **변경 내용:** 사설망을 순수 WireGuard 에서 Tailscale 로, TLS 종단을 Caddy 에서
  `tailscale serve` 로 교체했다. `infra/provision.sh`(서버, 멱등) +
  `scripts/bootstrap.sh`(개발 PC) 가 §21~§29 를 단일 명령으로 수행한다. Caddy 가 주던
  것 중 앱에 없던 HSTS 는 `SECURITY_HEADERS` 에, 압축은 `@fastify/compress` 로 옮겼다.
- **이유:** 순수 WireGuard 는 단일 명령 프로비저닝이 원리적으로 불가능하다 — Lightsail
  공개키를 기존 WG 서버(리포 밖 머신)에 peer 로 등록해야 터널이 서고, 그 전에는
  핸드셰이크 확인이 불가능해 UFW 를 안전하게 켤 수 없다. 요구사항 "클라우드가 무엇이든
  동일하게, 쉽고 빠르게" 가 이 제약과 양립하지 않는다.
- **보안 모델:** 데이터 평면은 동일한 WireGuard 다 — 노드 간 E2E 암호화, 앱은 여전히
  인터넷에 비노출, D-014(비밀번호 단일 단계)의 전제 유지. 바뀐 것은 control plane 뿐이다.
- **새 의존:** Tailscale control plane. 다운 시 기존 연결은 유지되나 신규 조인·재인증이
  실패한다. 노드 키 만료는 `tag:server` 로 면제한다 — 태그 없이 조인하면 헤드리스
  서버가 몇 달 뒤 조용히 떨어진다.
- **락아웃 가드:** provision.sh 를 기본/`--harden` 2 단계로 나누고, bootstrap.sh 가
  tailnet 경유 SSH 를 실제로 시도해 성공했을 때만 하드닝을 실행한다. 스펙 §25 의
  "검증 전 차단 금지" 가 제어 흐름으로 강제된다.
- **스펙 관계:** §23(WireGuard)·§24(퍼블릭 방화벽 마감, 선택으로 강등)·§25(UFW 규칙,
  tailscale0 으로)·§27(Caddy, 제거) 편차. §18 의 호스트 요구사항과 §30 배포 절차는
  그대로다. deploy.sh 는 수정하지 않았다.
- **Git 설정:** 셸 스크립트를 Windows 개발 머신에서도 LF 로 체크아웃하도록 `.gitattributes` 에
  `*.sh text eol=lf` 를 추가했다. scripts/bootstrap.sh 가 infra/provision.sh 를 scp 로
  서버에 전달하는데, 개발 PC 가 core.autocrlf=true 이고 CRLF 로 체크아웃되면 Ubuntu 에서
  shebang 이 `#!/bin/sh\r` 이 되어 프로비저닝이 실패한다.
- **설계 문서:** `docs/superpowers/specs/2026-07-26-tailscale-provisioning-design.md`
