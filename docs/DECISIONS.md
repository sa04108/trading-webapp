# DECISIONS

명세 밖 선택과 이유를 기록한다. (스펙 §37)

## D-001: 개발 머신 Node 22, 운영은 Node 24 유지

- **변경 내용:** `engines`는 스펙대로 `>=24 <25`를 유지하되 `engine-strict`를 켜지 않아 Node 22 개발 머신에서 설치·테스트를 허용한다.
- **이유:** 현재 개발 PC(Windows)에 Node v22.14.0이 설치되어 있고, 사용하는 네이티브 모듈(better-sqlite3, argon2, @duckdb/node-api)은 22/24 모두 prebuild를 제공한다.
- **대안:** 개발 머신에 Node 24 설치 — 사용자 시스템 변경이라 보류. 필요 시 사용자가 직접 업그레이드.
- **보안/비용/마이그레이션 영향:** 없음. 운영 배포 절차(§22)는 그대로 Node 24 LTS.

## D-002: 1차 증권사 어댑터는 키움 REST API, 토스는 사전신청 승인 후

- **변경 내용:** `RestBrokerMarketDataSource`의 1차 구현을 키움 REST API로 한다. 자격증명(App Key) 발급 전까지 어댑터는 구조·단위 테스트만 검증하고 비활성 상태로 둔다.
- **이유:** 토스증권 Open API는 사전신청 대기 중. 키움 REST API는 리눅스에서 직접 호출 가능함을 확인(2026-07-25, openapi.kiwoom.com).
- **대안:** 토스 대기 — 데이터 수집이 지연됨. CSV/Parquet import가 MVP 검증 경로이므로 어댑터 지연은 MVP 완료를 막지 않는다.
- **영향:** 도메인·애플리케이션 코드 영향 없음(Port/Adapter). 스펙 13장에 반영 완료.

## D-003: 서버 코드는 상대 import, 웹은 Vite alias

- **변경 내용:** 서버(tsc 컴파일)는 경로 별칭 없이 상대 import를 사용한다. 웹은 shadcn 관례대로 `@/` → `src/web`, `@shared/` → `src/shared` alias를 사용한다.
- **이유:** tsc는 별칭을 런타임 경로로 재작성하지 않으므로 tsc-alias 등 추가 도구 없이 dist가 그대로 동작하게 한다.
- **영향:** 없음. dependency-cruiser 규칙은 경로 기반으로 동일하게 적용.

## D-004: TOTP 라이브러리 otpauth, ID는 ULID

- **변경 내용:** TOTP는 `otpauth`(무의존성, RFC 6238), ID 생성은 `ulid` 사용. QR 대신 CLI가 otpauth:// URI와 base32 secret을 출력한다.
- **이유:** 스펙은 라이브러리를 지정하지 않음. otpauth는 유지보수 활발·zero-dep. ULID는 스펙 예시 `bt_01J...` 형식과 일치.

## D-005: 차트 시리즈 서버 측 다운샘플링 (~1,000 포인트)

- **변경 내용:** 자산 곡선·드로다운 API 응답을 LTTB로 최대 1,000포인트로 다운샘플한다. 원본 전체 시리즈는 export로 제공.
- **이유:** Recharts(SVG)는 수천 포인트 이상에서 모바일 성능이 급락한다. (스택 검토에서 확인된 한계)
- **영향:** UI 정확도 손실은 시각적으로 무시 가능. 지표 계산은 항상 전체 시리즈로 수행.

## D-007: TypeScript 5.9 고정 (TS 7 네이티브 컴파일러 회피)

- **변경 내용:** 2026-07 기준 최신 TypeScript 7.0(네이티브)을 쓰지 않고 `typescript@~5.9.0`으로 고정한다.
- **이유:** typescript-eslint 8.65가 TS 7.0을 지원하지 않아 lint 게이트가 깨진다 (공식 지원은 TS ≥7.1 예정).
- **대안:** TS 6 API 호환 모드 — 검증 비용 대비 이득 없음. typescript-eslint가 TS 7을 지원하면 업그레이드.
- **영향:** 컴파일 속도 외 기능 차이 없음.

## D-008: better-sqlite3 v12 고정

- **변경 내용:** better-sqlite3를 v13이 아닌 `^12`로 고정한다.
- **이유:** v13은 개발 머신의 Node 22용 prebuild를 제공하지 않아 소스 컴파일(Visual Studio 필요)로 폴백한다. v12는 Node 22/24 prebuild 제공.
- **영향:** 운영(Node 24)에서도 v12 prebuild 사용. Node 24 전환 후 v13 업그레이드 가능.

## D-006: KR 세션 캘린더는 MVP에서 단순화

- **변경 내용:** KR 정규장 09:00–15:30 KST, 주말 제외만 반영. 공휴일·조기폐장은 미반영하고 결과 화면 경고(§9.4)에 명시한다.
- **이유:** 휴장일 캘린더 유지관리는 MVP 범위를 넘는다. 데이터가 없는 날은 봉이 없으므로 백테스트 정확성에는 영향이 제한적.
- **영향:** coverage의 "누락" 판정이 공휴일을 누락으로 오인할 수 있음 — coverage 화면에 한계 문구 표시.
- **추가 (PR #1 리뷰 반영):** 세션이 정의되지 않은 시장(US)의 import 는 명시적으로 거부한다. KR 세션으로 빈 1h 집계를 만들고 완료로 위장하던 문제의 수정 — US 지원 시 DST 를 포함한 세션 정의가 선행돼야 한다.

## D-009: 스펙 §12 스키마 편차 — 소비자 없는 테이블은 만들지 않는다

- **변경 내용:** §12 의 `strategies`/`strategy_versions` 테이블은 만들지 않고(전략은 코드 등록식 레지스트리가 유일한 출처, §2.5), 초기 스캐폴딩으로 생성됐던 `application_settings`/`data_sync_jobs` 테이블은 읽고 쓰는 코드가 없어 제거했다 (마이그레이션 0006).
- **이유:** 아무도 소비하지 않는 스키마는 "무결(더할 것도 뺄 것도 없는 상태)" 원칙 위반이며, 실제 사용 시점의 요구와 어긋난 채 굳어진다.
- **영향:** 증권사 동기화 작업 이력(§13)이 필요해지면 그 시점의 요구대로 테이블을 신설한다.

## D-010: 파괴적 마이그레이션과 자동 롤백의 짝 맞춤

- **변경 내용:** deploy.sh 는 서비스 재시작(=마이그레이션 적용) 직전에 SQLite 스냅샷을 만들고, health check 실패로 롤백할 때 스냅샷을 함께 복원한다 — 이전 릴리스 코드가 새 스키마(예: 삭제된 컬럼)를 만나 `no such column` 으로 죽는 "명목상 롤백"을 막는다.
- **운영 규칙:** 컬럼·테이블 삭제 같은 파괴적 스키마 변경은 코드가 해당 참조를 중단한 **다음** 릴리스에 싣는 것을 원칙으로 한다 (expand-contract). 스냅샷 복원은 이 규칙이 지켜지지 않았을 때의 안전망이다.
- **영향:** 스냅샷~롤백 사이의 쓰기는 유실된다. 단일 운영자가 배포 중인 수 초의 창이라 실질 위험은 없고, 성공 배포 시 스냅샷은 즉시 삭제된다.
