# DECISIONS

명세 밖 선택과 이유를 기록한다. (스펙 §37)

## D-001: 개발 머신 Node 22, 운영은 Node 24 유지

- **변경 내용:** `engines`는 스펙대로 `>=24 <25`를 유지하되 `engine-strict`를 켜지 않아 Node 22 개발 머신에서 설치·테스트를 허용한다.
- **이유:** 현재 개발 PC(Windows)에 Node v22.14.0이 설치되어 있고, 사용하는 네이티브 모듈(better-sqlite3, argon2, @duckdb/node-api)은 22/24 모두 prebuild를 제공한다.
- **대안:** 개발 머신에 Node 24 설치 — 사용자 시스템 변경이라 보류. 필요 시 사용자가 직접 업그레이드.
- **보안/비용/마이그레이션 영향:** 없음. 운영 배포 절차(§22)는 그대로 Node 24 LTS.

## D-002: 1차 증권사 어댑터는 키움 REST API, 토스는 사전신청 승인 후

- **변경 내용:** `RestBrokerMarketDataSource`의 1차 구현을 키움 REST API로 한다. 자격증명(App Key) 발급 전까지 어댑터는 구조·단위 테스트만 검증하고 비활성 상태로 둔다.
- **이유:** 토스증권 Open API는 사전신청 대기 중. 키움 REST API는 리눅스에서 직접 호출 가능함을 확인(2026-07-25, openapi.kiwoom.com).
- **대안:** 토스 대기 — 데이터 수집이 지연됨. CSV/Parquet import가 MVP 검증 경로이므로 어댑터 지연은 MVP 완료를 막지 않는다.
- **영향:** 도메인·애플리케이션 코드 영향 없음(Port/Adapter). 스펙 13장에 반영 완료.

## D-003: 서버 코드는 상대 import, 웹은 Vite alias

- **변경 내용:** 서버(tsc 컴파일)는 경로 별칭 없이 상대 import를 사용한다. 웹은 shadcn 관례대로 `@/` → `src/web`, `@shared/` → `src/shared` alias를 사용한다.
- **이유:** tsc는 별칭을 런타임 경로로 재작성하지 않으므로 tsc-alias 등 추가 도구 없이 dist가 그대로 동작하게 한다.
- **영향:** 없음. dependency-cruiser 규칙은 경로 기반으로 동일하게 적용.

## D-004: TOTP 라이브러리 otpauth, ID는 ULID

- **변경 내용:** TOTP는 `otpauth`(무의존성, RFC 6238), ID 생성은 `ulid` 사용. QR 대신 CLI가 otpauth:// URI와 base32 secret을 출력한다.
- **이유:** 스펙은 라이브러리를 지정하지 않음. otpauth는 유지보수 활발·zero-dep. ULID는 스펙 예시 `bt_01J...` 형식과 일치.
- **⚠️ TOTP 부분 폐기 (D-014):** TOTP 자체를 제거하면서 `otpauth` 의존성도 함께 뺐다. ULID 결정은 그대로 유효하다.

## D-005: 차트 시리즈 서버 측 다운샘플링 (~1,000 포인트)

- **변경 내용:** 자산 곡선·드로다운 API 응답을 LTTB로 최대 1,000포인트로 다운샘플한다. 원본 전체 시리즈는 export로 제공.
- **이유:** Recharts(SVG)는 수천 포인트 이상에서 모바일 성능이 급락한다. (스택 검토에서 확인된 한계)
- **영향:** UI 정확도 손실은 시각적으로 무시 가능. 지표 계산은 항상 전체 시리즈로 수행.

## D-007: TypeScript 5.9 고정 (TS 7 네이티브 컴파일러 회피)

- **변경 내용:** 2026-07 기준 최신 TypeScript 7.0(네이티브)을 쓰지 않고 `typescript@~5.9.0`으로 고정한다.
- **이유:** typescript-eslint 8.65가 TS 7.0을 지원하지 않아 lint 게이트가 깨진다 (공식 지원은 TS ≥7.1 예정).
- **대안:** TS 6 API 호환 모드 — 검증 비용 대비 이득 없음. typescript-eslint가 TS 7을 지원하면 업그레이드.
- **영향:** 컴파일 속도 외 기능 차이 없음.

## D-008: better-sqlite3 v12 고정

- **변경 내용:** better-sqlite3를 v13이 아닌 `^12`로 고정한다.
- **이유:** v13은 개발 머신의 Node 22용 prebuild를 제공하지 않아 소스 컴파일(Visual Studio 필요)로 폴백한다. v12는 Node 22/24 prebuild 제공.
- **영향:** 운영(Node 24)에서도 v12 prebuild 사용. Node 24 전환 후 v13 업그레이드 가능.

## D-006: KR 세션 캘린더는 MVP에서 단순화

- **변경 내용:** KR 정규장 09:00–15:30 KST, 주말 제외만 반영. 공휴일·조기폐장은 미반영하고 결과 화면 경고(§9.4)에 명시한다.
- **이유:** 휴장일 캘린더 유지관리는 MVP 범위를 넘는다. 데이터가 없는 날은 봉이 없으므로 백테스트 정확성에는 영향이 제한적.
- **영향:** coverage의 "누락" 판정이 공휴일을 누락으로 오인할 수 있음 — coverage 화면에 한계 문구 표시.
- **추가 (PR #1 리뷰 반영):** 세션이 정의되지 않은 시장(US)의 import 는 명시적으로 거부한다. KR 세션으로 빈 1h 집계를 만들고 완료로 위장하던 문제의 수정 — US 지원 시 DST 를 포함한 세션 정의가 선행돼야 한다.

## D-009: 스펙 §12 스키마 편차 — 소비자 없는 테이블은 만들지 않는다

- **변경 내용:** §12 의 `strategies`/`strategy_versions` 테이블은 만들지 않고(전략은 코드 등록식 레지스트리가 유일한 출처, §2.5), 초기 스캐폴딩으로 생성됐던 `application_settings`/`data_sync_jobs` 테이블은 읽고 쓰는 코드가 없어 제거했다. (제거 마이그레이션은 D-015 의 스쿼시로 흡수됐다 — 해당 테이블은 이제 생성되지 않는다.)
- **이유:** 아무도 소비하지 않는 스키마는 "무결(더할 것도 뺄 것도 없는 상태)" 원칙 위반이며, 실제 사용 시점의 요구와 어긋난 채 굳어진다.
- **영향:** 증권사 동기화 작업 이력(§13)이 필요해지면 그 시점의 요구대로 테이블을 신설한다.

## D-010: 파괴적 마이그레이션과 자동 롤백의 짝 맞춤

- **변경 내용:** deploy.sh 는 서비스 재시작(=마이그레이션 적용) 직전에 SQLite 스냅샷을 만들고, health check 실패로 롤백할 때 스냅샷을 함께 복원한다 — 이전 릴리스 코드가 새 스키마(예: 삭제된 컬럼)를 만나 `no such column` 으로 죽는 "명목상 롤백"을 막는다.
- **운영 규칙:** 컬럼·테이블 삭제 같은 파괴적 스키마 변경은 코드가 해당 참조를 중단한 **다음** 릴리스에 싣는 것을 원칙으로 한다 (expand-contract). 스냅샷 복원은 이 규칙이 지켜지지 않았을 때의 안전망이다.
- **보존:** 스냅샷은 성공 배포 후에도 최근 5개를 남긴다. health check 는 통과했지만 그 뒤에 문제가 드러나 **수동** 롤백(§30 10단계, §35 runbook)을 하는 경우에도 짝이 맞는 스키마로 되돌아가야 하기 때문이다. backup.sh 의 30일 정리 규칙은 `backup-*` 디렉터리만 훑으므로 deploy.sh 가 직접 회전시킨다.
- **영향:** 스냅샷~롤백 사이의 쓰기는 유실된다. 단일 운영자가 배포 중인 수 초의 창이라 실질 위험은 없다. 수동 롤백 절차는 배포 성공 시 deploy.sh 가 그대로 출력한다.

## D-011: 감사 로그 보존 기간은 정책이므로 설정으로 노출한다

- **변경 내용:** M15 의 정리 작업이 감사 로그를 90일 하드코딩으로 삭제하던 것을 `AUDIT_LOG_RETENTION_DAYS` 설정으로 뺐다 (기본 90, `0` 이면 삭제하지 않음). 보존 기간이 켜져 있으면 부팅 로그에 명시한다.
- **이유:** 스펙 §16 이 요구하는 것은 감사 기록의 *생성*이지 파기가 아니다. 세션·로그인 시도 정리는 명백한 위생 작업이지만 감사 로그 파기는 정책 결정이고, 정책은 코드 상수에 숨지 않아야 한다.
- **영향:** 기본 동작은 종전과 같다. 감사 기록을 남겨야 하는 요구가 생기면 `AUDIT_LOG_RETENTION_DAYS=0` 으로 끈다 — 대신 테이블은 무한히 증가한다.

## D-012: 스펙 §32 편차 — maxPositions 는 전략 파라미터가 아니라 요청 필드

- **변경 내용:** §32 의 `HourlyBreakoutParameters` 에 있던 `maxPositions` 를 요청의 `risk.maxPositions` 로 옮기고 전략 버전을 1.2.0 으로 올렸다 (I3). 엔진은 더 이상 전략 파라미터 가방에서 이름으로 상한을 찾지 않는다.
- **이유:** 포지션 상한은 엔진의 리스크 제약(§9.2-6)이지 전략 로직의 입력이 아니다. 이름 규약("maxPositions" 키가 있으면 쓰고 없으면 10")은 계층 간 보이지 않는 결합이었고, 그 이름을 쓰지 않는 전략은 조용히 상한 없이 돌았다. §15 의 요청 예시 자체가 이 파라미터를 담고 있지 않다.
- **호환성:** 이미 저장된 요청은 복제 시 `rebaseStoredRequest` 가 `parameters.maxPositions`(없으면 기존 기본값 10)를 `risk` 로 옮기고 전략 버전을 현재 값으로 재기준한 뒤, 무엇이 바뀌었는지 경고로 알린다 (I9). 복제는 §10 이 지정한 중단 작업 복구 경로이므로 스키마 변경으로 막히지 않는다.
- **영향:** 위저드가 자본 단계에서 상한을 명시적으로 입력받는다. 향후 전략 버전이 올라가도 과거 작업의 복제는 계속 동작하며, 재현이 아닌 재실행임을 경고로 구분한다.

## D-013: 로컬 백업 보관은 일수가 아니라 용량으로 제한한다

- **변경 내용:** backup.sh 의 `-mtime +30` 회전을 총 용량 상한으로 교체했다 — `BACKUP_MAX_TOTAL_MB`(기본 10240) 를 넘으면 가장 오래된 백업부터 삭제한다. `BACKUP_MIN_KEEP`(기본 2) 아래로는 줄이지 않고, 백업 생성 **전에** 직전 백업 크기만큼 여유를 미리 확보한다.
- **완성본만 센다:** 백업은 `.incomplete-<stamp>` 에 쓰고 끝까지 성공했을 때만 `backup-<stamp>` 로 rename 한다. `BACKUP_MIN_KEEP` 은 개수를 세는 규칙이므로, 반쪽 디렉터리가 `backup-*` 로 보이면 그 보장이 빈 껍데기로 채워진다.
- **이유:** 호스트 디스크는 40GB 고정인데(§18 Micro) 백업 1벌의 크기는 시간봉 Parquet 과 함께 자란다. "30일" 은 개수만 묶을 뿐 총량을 묶지 못해, 데이터가 커지면 백업이 디스크를 채우고 애플리케이션까지 같이 죽인다. 제약이 용량이면 정책도 용량이어야 한다.
- **스펙 관계:** §31 의 30일 lifecycle 은 **S3** 규칙이고 그대로 유지한다 — S3 는 이 제약을 받지 않는다. 로컬 30일은 그 정책을 제약이 다른 곳에 복사한 것이었다.
- **영향:** 보관 "기간" 이 데이터 크기에 따라 달라진다. 데이터가 커질수록 남는 백업 벌수가 줄어드는 대신 디스크가 넘치지 않는다 — 복원 가능한 백업 0벌보다 얕은 이력이 낫다. 생성 전 선정리 때문에 정상 상태 사용량은 상한 근처에서 진동한다.

## D-014: TOTP 2단계 인증 제거 — 스펙 §16 편차

- **변경 내용:** 스펙 §16 이 요구하는 비밀번호 + TOTP 2단계 인증을 제거하고 비밀번호 단일 단계로 바꿨다. TOTP secret·복구 코드·`otpauth` 의존성·`POST /auth/totp/verify` 라우트·로그인 2단계 화면을 모두 없애고, `users.totp_secret`·`users.totp_enabled`·`users.recovery_code_hashes_json`·`sessions.pending_totp` 컬럼을 삭제했다. (삭제 마이그레이션은 D-015 의 스쿼시로 초기 마이그레이션에 흡수됐다 — 해당 컬럼은 이제 어느 시점에도 생성되지 않는다.)
- **이유:** 이 플랫폼은 WireGuard VPN 내부에서만 접근하는 단일 관리자용 도구다. 망 경계에서 이미 접근이 제한되고 그 위에 사용자 이름·비밀번호가 있는 상태에서 TOTP 는 방어를 의미 있게 늘리지 않는 반면, 인증 앱 등록·복구 코드 보관·기기 분실 시 복구 경로라는 운영 부담을 상시로 지운다.
- **기능 플래그가 아니라 제거인 이유:** `totpEnabled` 를 끄는 선택지도 있었지만, 아무도 켜지 않는 경로를 남기면 검증되지 않은 채 굳는다 (D-009 와 같은 이유). 쓰지 않을 코드는 남기지 않는다.
- **남는 방어:** Argon2id 해시, 비밀번호 14자 이상 강제(CLI), 로그인 실패 5회/15분 잠금, 사용자 부재 시 타이밍 균등화, 세션 유휴 12시간·절대 7일 만료, httpOnly·Secure·SameSite=Strict·signed 쿠키, Origin==Host CSRF 검사, 127.0.0.1 bind + VPN 경계. 비밀번호 최소 길이 14자는 이제 유일한 비밀 값의 강도를 결정하므로 낮추지 않는다.
- **세션 고정:** 회전 시점이 TOTP 검증에서 로그인 성공으로 옮겨갔을 뿐, 로그인마다 새 세션 ID 를 발급하는 것은 그대로다. 서버가 발급하지 않은 쿠키 값은 어느 시점에도 인증된 세션이 되지 않는다.
- **D-010 예외:** D-010 은 파괴적 스키마 변경을 코드가 참조를 끊은 *다음* 릴리스에 싣는 expand-contract 원칙을 세웠다. 이 변경은 코드 제거와 DROP COLUMN 을 한 릴리스에 함께 실었다 — 운영 서버가 아직 구축되지 않아 보호할 데이터가 없고 되돌릴 이전 릴리스도 배포된 적이 없다. 원칙 자체는 유효하며, 운영 시작 후에는 지킨다.
- **되돌리기 비용:** 실거래 단계에서 2단계 인증 요구가 생기면 재구현이 필요하다 — 의존성 추가, 컬럼 복원 마이그레이션, 2단계 로그인 흐름 복원. 그 시점의 요구(TOTP 인지 passkey 인지)에 맞춰 새로 설계하는 편이 지금 쓰지 않는 경로를 유지하는 것보다 낫다고 판단했다.
- **설계 문서:** `docs/superpowers/specs/2026-07-26-totp-removal-design.md`

## D-015: 배포 전 마이그레이션 스쿼시 — 이력은 0000 하나로

- **변경 내용:** 마이그레이션 0000~0007 과 대응 스냅샷을 모두 지우고 현재 스키마 기준의 단일 마이그레이션(`0000_ambiguous_bedlam.sql`)으로 다시 생성했다. `migrations/` 는 297KB → 42KB 가 됐다 (스냅샷 8개가 272KB 를 차지했다).
- **이유:** 한 번도 배포된 적 없는 마이그레이션 이력은 보존 가치가 없다. 중간 단계 스키마로 되돌릴 대상 DB 가 존재하지 않으므로, 8단계 이력은 저장소 용량과 읽는 사람의 주의만 소모한다.
- **런타임/도구 역할 구분 (소스 확인):** `drizzle-orm/migrator` 는 `meta/_journal.json` 과 각 `<tag>.sql` 만 읽고 `*_snapshot.json` 은 전혀 읽지 않는다. 스냅샷은 `drizzle-kit generate` 가 다음 diff 를 만들 때만 쓰며 최신 1개로 충분하다. 반대로 `.sql` 은 journal 에 항목이 있으면 반드시 존재해야 하고(없으면 부팅 시 throw), 새 DB 의 스키마를 만드는 유일한 출처다.
- **왜 지금이 마지막 기회인가:** `sqlite-core/dialect.cjs` 의 적용 판정은 해시가 아니라 journal 의 `when` 타임스탬프다 (`Number(lastDbMigration[2]) < migration.folderMillis`). 스쿼시한 마이그레이션은 기존 DB 에서 재실행돼 `table already exists` 로 죽는다. 즉 스쿼시는 **모든 기존 DB 를 버릴 수 있을 때만** 가능하며, 운영 서버 구축 이후에는 선택지가 사라진다.
- **영향:** 로컬 개발 DB(`data/app.sqlite`)를 폐기했으므로 관리자 계정을 `pnpm cli admin:create` 로 다시 만들어야 한다. 운영 데이터는 없었다.
- **검증:** 스쿼시 전 스키마(0000~0007 누적 적용)와 스쿼시 후 새 DB 의 `sqlite_master` 를 비교해 32개 객체 중 31개가 완전히 동일함을 확인했다. 유일한 차이는 `backtest_jobs` 의 **컬럼 순서** — 나중에 `ALTER TABLE ADD COLUMN` 으로 붙던 `dataset_version`·`dataset_hash`·`progress_label` 이 이제 선언 순서대로 들어간다. 컬럼 이름·타입·NOT NULL 집합은 동일하고, 코드에 `SELECT *` 나 위치 기반 INSERT 가 없어(drizzle 은 항상 명시적 컬럼 목록을 생성한다) 영향이 없다. 앞으로 모든 DB 가 같은 마이그레이션에서 생성되므로 순서도 일관된다.

## D-016: WireGuard·Caddy → Tailscale — 스펙 §23~§27 편차

- **변경 내용:** 사설망을 순수 WireGuard 에서 Tailscale 로, TLS 종단을 Caddy 에서
  `tailscale serve` 로 교체했다. `infra/provision.sh`(서버, 멱등) +
  `scripts/bootstrap.sh`(개발 PC) 가 §21~§29 를 단일 명령으로 수행한다. Caddy 가 주던
  것 중 앱에 없던 HSTS 는 `SECURITY_HEADERS` 에, 압축은 `@fastify/compress` 로 옮겼다.
- **이유:** 순수 WireGuard 는 단일 명령 프로비저닝이 원리적으로 불가능하다 — Lightsail
  공개키를 기존 WG 서버(리포 밖 머신)에 peer 로 등록해야 터널이 서고, 그 전에는
  핸드셰이크 확인이 불가능해 UFW 를 안전하게 켤 수 없다. 요구사항 "클라우드가 무엇이든
  동일하게, 쉽고 빠르게" 가 이 제약과 양립하지 않는다.
- **보안 모델:** 데이터 평면은 동일한 WireGuard 다 — 노드 간 E2E 암호화, 앱은 여전히
  인터넷에 비노출, D-014(비밀번호 단일 단계)의 전제 유지. 바뀐 것은 control plane 뿐이다.
- **새 의존:** Tailscale control plane. 다운 시 기존 연결은 유지되나 신규 조인·재인증이
  실패한다. 노드 키 만료는 `tag:server` 로 면제한다 — 태그 없이 조인하면 헤드리스
  서버가 몇 달 뒤 조용히 떨어진다.
- **락아웃 가드:** provision.sh 를 기본/`--harden` 2 단계로 나누고, bootstrap.sh 가
  tailnet 경유 SSH 를 실제로 시도해 성공했을 때만 하드닝을 실행한다. 스펙 §25 의
  "검증 전 차단 금지" 가 제어 흐름으로 강제된다. `--harden` 게이트는 `BackendState`
  뿐 아니라 `tag:server` 소유도 확인한다 — Running 이어도 태그 없이 조인했으면
  거부한다(최종 리뷰 F1). 태그 없는 조인은 지금은 멀쩡히 동작하다가 노드 키 만료
  시점(약 180일 뒤)에 조용히 락아웃으로 이어지는데, 그 확인을 되돌릴 수 없는 UFW
  적용 직전으로 옮겨 무경고 실패를 막았다.
- **고정 아웃바운드 IP:** §18/§23 요구사항은 그대로 유지된다 — 증권사 API 트래픽은
  Lightsail Static IP 로 나가야 한다. provision.sh 기본 모드가 `checkip.amazonaws.com`
  확인을 정보성으로 출력한다. Tailscale 은 WireGuard 에 없던 새 우회 경로가 있다 —
  이 노드에 `tailscale set --exit-node=...` 를 걸지 않는다(걸면 아웃바운드가 조용히
  우회된다).
- **CT 로그 노출:** `tailscale serve --https=443` 도 `<host>.<tailnet>.ts.net` 앞으로
  Let's Encrypt 인증서를 받아 CT 로그에 공개된다 — 설계 §2 가 기각한 다른 대안과 같은
  성질이지만, 이름이 tailnet 안에서만 해석되고 퍼블릭에 아무것도 듣지 않으므로 무해하다.
- **스펙 관계:** §23(WireGuard)·§24(퍼블릭 방화벽 마감, 선택으로 강등)·§25(UFW 규칙,
  tailscale0 으로)·§27(Caddy, 제거) 편차. §18 의 호스트 요구사항과 §30 배포 절차는
  그대로다. deploy.sh 는 동작을 바꾸지 않았다 — 최종 리뷰에서 usage 문자열·주석의
  `<wireguard-host>` 예시만 tailnet FQDN 으로 교체했다(사용자 승인 예외).
- **Git 설정:** 셸 스크립트를 Windows 개발 머신에서도 LF 로 체크아웃하도록 `.gitattributes` 에
  `*.sh text eol=lf` 를 추가했다. scripts/bootstrap.sh 가 infra/provision.sh 를 scp 로
  서버에 전달하는데, 개발 PC 가 core.autocrlf=true 이고 CRLF 로 체크아웃되면 Ubuntu 에서
  shebang 이 `#!/bin/sh\r` 이 되어 프로비저닝이 실패한다.
- **설계 문서:** `docs/superpowers/specs/2026-07-26-tailscale-provisioning-design.md`

## D-017: 평면 분리 헌법 — 플랫폼 read-only, TOTP 복원(D-014 부분 폐기), Tailscale 제거(D-016 폐기)

- **변경 내용:** 보안 모델의 전제를 "플랫폼 전체를 사설망 뒤에 숨긴다"에서 "플랫폼의
  권한을 줄이는 대신 노출을 허용한다"로 교체했다. 플랫폼은 조회·백테스트·데이터
  관리·비상정지(끄기 전용)만 담당하고, 돈·전략·보안 설정 조작은 SSH CLI 전용이다
  (스펙 §2.6 신설). 인증은 비밀번호 + TOTP 2단계로 복원(§16), 노출은 도메인 +
  Caddy(Let's Encrypt) + UFW 22/80/443 이다.
- **D-014 부분 폐기:** TOTP 제거의 근거가 "사설망 경계가 이미 접근을 제한한다"였다 —
  그 경계가 사라지므로 전제가 소멸한다. D-014 가 예고한 대로 재구현했다: 복구 코드
  해시는 sha256 → Argon2, 등록은 admin:create 내장 → 별도 `totp:enroll`(CLI 전용).
  스키마 컬럼 4개는 배포 전이므로 0000 마이그레이션에 스쿼시로 흡수했다 (D-015 근거
  재적용 — 배포된 적 없는 이력은 보존 가치가 없다).
- **D-016 폐기:** 망 경계 요구가 없어졌으므로 Tailscale·`tag:server`·노드 키 관리
  의존을 제거했다. 퍼블릭 22 는 닫지 않는다 — 클라우드 브라우저 SSH 콘솔(키 인증)이
  out-of-band 복구 경로가 되므로, D-016 의 락아웃 가드 체계(tailnet SSH 실증,
  `--harden` 2단계) 전체가 불필요해져 provision.sh 는 단일 실행으로 돌아왔다.
  sshd 하드닝(키 전용 인증)은 유지한다 — 하드닝의 대상은 접속 클라이언트가 아니라
  "열린 포트가 인터넷으로부터 무엇을 받아주느냐"이고, 브라우저 SSH 는 키 인증이라
  영향이 없다.
- **킬스위치 단방향:** 플랫폼에서 자동매매는 끌 수만 있다. 세션 탈취 시 "끄기"의
  최대 피해는 기회비용이지만 "켜기"는 돈을 움직일 길을 연다. 구현은 자동매매 엔진과
  함께 한다 (D-009 — 소비자 없는 코드를 미리 만들지 않는다).
- **CT 로그:** 도메인이 Let's Encrypt CT 로그에 공개된다 — 퍼블릭 서비스 전제이므로
  무해하다.
- **스펙 관계:** §2.2·§2.6·§16 은 본문을 개정했다. §23(WireGuard)·§24(퍼블릭 방화벽
  마감)·§25(UFW 원문)·§27(Caddy 내부 TLS)은 이 결정으로 대체된다 — 현행 규칙은
  스펙 §2.2 다이어그램과 infra/provision.sh 가 정의한다.
- **설계 문서:** `docs/superpowers/specs/2026-07-27-platform-readonly-constitution-design.md`

## D-018: 토스증권 Open API 어댑터 — 승인 완료로 2차 어댑터 추가 (D-002 예정 이행)

- **변경 내용:** `createTossMarketDataSource` 를 broker infrastructure 에 추가했다
  (`toss/toss-market-data-source.ts`). 공식 OpenAPI JSON
  (openapi.tossinvest.com/openapi-docs/latest/openapi.json, v1.2.5) 기준으로 캔들 수집을
  실제 매핑까지 구현했다 — 키움 어댑터(자격 증명 발급 전 비활성 스텁)와 달리 스펙이
  공개되어 있어 검증 가능했다. 공용 `BrokerNotConfiguredError` 는 `errors.ts` 로 추출했다.
- **인증:** OAuth2 client_credentials, `POST /oauth2/token` — 키움(JSON body)과 달리
  form-urlencoded 다. 토큰 유효 24h, 재발급 시 이전 토큰이 즉시 무효화되므로 프로세스당
  단일 `BrokerRestClient` 로 캐싱을 공유한다. 모의 환경은 없고 실전만 제공되며, 허용 IP
  사전 등록제다(§18 고정 아웃바운드 IP 전제 유지).
- **1h 미제공:** `interval` 은 `1m`/`1d` 뿐이다. `1h` 요청은 조용히 근사하지 않고
  `UnsupportedTimeframeError` 로 명시적으로 실패시킨다 — 시간봉은 스펙 §13 대로 1분봉
  집계로 생성한다.
- **페이지네이션 계약:** `fetchCandles` 1회 = 1페이지(최대 200봉). `before`(inclusive)
  커서를 `toTsMs` 의 UTC ISO 로 보내고, `hasMore` 면 호출자가 `toTsMs` 를 반환된 가장
  오래된 봉 직전으로 좁혀 이어받는다 — port 의 이어받기 시맨틱과 일치하고, 장시간
  단일 호출을 피한다. `nextBefore` 는 inclusive 라 마지막 봉이 중복될 수 있으나
  `normalizeCandles` 가 멱등 처리한다.
- **오데이터 차단:** 가격·거래량이 decimal *문자열* 로 오므로 숫자 변환 실패(NaN)는
  봉을 버리지 않고 요청 전체를 실패시킨다.
- **참고:** 요청서에 첨부된 developers-apps-in-toss.toss.im 은 토스증권이 아니라
  앱인토스(미니앱 플랫폼) 문서다. 실제 포털은 developers.tossinvest.com.

## D-019: 1h Parquet 백업 제외 — 캔들은 전 timeframe 백업하지 않는다 (스펙 §31 개정)

- **변경 내용:** backup.sh 에서 `timeframe=1h` Parquet 아카이브를 제거했다. 백업 대상은
  SQLite(계정·감사 로그·데이터셋 메타·백테스트 이력)와 exports 만 남는다. 당시에는
  D-019 이전 백업과의 호환을 위해 1h 복구 경로를 조건부로 유지했다 (후속 상태는 D-031).
- **이유:** §31 의 원칙("재취득 가능한 것은 백업하지 않는다")을 캔들 전체에 일관 적용한다.
  1m/1d 는 증권사 재수집으로, 1h 는 1분봉 세션 경계 집계(코드는 git 에 있다)로 재생성
  가능하다 — 1h 만 백업하던 것은 원본(1m)은 버리고 파생물만 지키는 비대칭이었다.
- **수용한 위험:** 재생성 가능성은 원본 1분봉의 생존에 의존한다. 디스크 유실 시 1분봉은
  증권사 보관 깊이까지만 복구되므로, 그보다 오래된 구간은 1h 도 함께 소실된다. 이 위험의
  대응은 백업이 아니라 1m 파티션의 S3 아카이브다 — 증권사 보관 깊이 실측(D-018 후속)
  결과 축적분이 보관 창을 넘어서기 시작할 때 켠다.
- **영향:** 백업 1벌 크기가 수 MB 수준으로 줄어 D-013 의 10GB 캡이 사실상 SQLite·exports
  전용이 됐다. 당시 복원 테스트 절차는 유지했으며, 현재 복구 정책은 D-031 을 따른다.

## D-020: 증권사 캔들 동기화 파이프라인 — 어댑터와 저장소 사이를 잇는다

- **변경 내용:** `BrokerSyncService`(market-data/application)를 추가해 `MarketDataSource`
  포트에서 Parquet 저장소로 캔들을 나르는 유스케이스를 구현했다. 백필(API 보관 깊이
  바닥까지)과 증분을 자동 판별하고, 페이지마다 저장·워터마크 갱신(`broker_sync_state`,
  마이그레이션 0001)으로 어느 지점에서 중단돼도 다음 실행이 이어받는다 (§13).
  `POST /datasets`(BROKER 데이터셋 생성)와 `POST /datasets/sync`(501 스텁 교체, 202 +
  jobId)가 입구이고, env 는 `TOSS_CLIENT_ID`/`TOSS_CLIENT_SECRET`/`TOSS_BASE_URL`/
  `SYNC_MIN_FREE_DISK_MB` 다.
- **수집 정책 (대화 확정):** 일봉은 원하는 종목을 수십 년, 1분봉은 매매·백테스트
  유니버스로 한정 (유니버스 = 데이터셋 심볼 목록, 새 도메인 개념 없음). 시간봉은
  수집하지 않고 1분봉 집계로 생성한다. 데이터셋 timeframe 관례는 CSV import 와 동일
  (1m 수집 → 1h 데이터셋, 1d → 1d).
- **추상화 검토 (사용자 요청):** 포트는 충분했고 갭 3개를 보수했다 —
  ① 포트 계약 에러가 broker 인프라에 정의돼 있어 애플리케이션이 잡을 수 없던 것을
  `ports.ts` 로 역전 (`MarketDataSourceNotConfiguredError`·`UnsupportedTimeframeError`,
  기존 이름은 재수출로 보존), ② market-data→broker 금지를 dependency-cruiser 규칙으로
  구조화, ③ 백필 완료 플래그·워터마크 저장처 신설. 증권사 선택(토스 우선)은 조립부
  전용 지식으로 남는다 (§2.4).
- **집계 정확성:** 페이지 단위 1h 집계는 세션 경계에 걸친 반쪽 시간봉을 만들 수 있어
  (idempotent 저장과 결합 시 조용한 오데이터), sync 중에는 1m 만 저장하고 심볼 수집
  종료 후 새로 커버된 구간을 현지 일 단위로 스트리밍 재집계한다.
- **실행 모델:** fire-and-forget + 잡 레코드(기존 dataImportJobs, sourceType BROKER).
  백테스트 JobQueue 는 일반화하지 않았다 — 원자적 claim 이 필요한 다중 워커용이고
  sync 는 데이터셋당 1개 실행 가드(409)와 부팅 시 고아 잡 정리로 충분하다 (D-009).
- **범위 밖:** 증분 자동 스케줄러(백업 자동화와 함께 나중에), 1m S3 아카이브(D-019,
  보관 깊이 실측 후), 종목 마스터 API, 헬스 대시보드 디스크 지표.
- **설계 문서:** `docs/superpowers/specs/2026-07-28-broker-sync-design.md`

## D-021: 데이터셋 CRUD 완성 — 유니버스 밸브의 실체화

- **변경 내용:** `PATCH /datasets/:id`(심볼 추가/제거)와 `DELETE /datasets/:id` 를 추가하고
  웹 데이터셋 페이지에 증권사 데이터셋 생성·동기화(잡 폴링)·심볼 칩 편집·삭제 확인을
  붙였다. D-020 이 "유니버스 관리 = 심볼 목록 편집"이라 했지만 그 편집 수단이 API 에
  없었다 — 밸브가 설계로만 존재하던 공백의 보수다.
- **심볼 제거 시멘틱:** 수집만 멈추고 쌓인 봉·워터마크는 남긴다. 지우는 건 비가역이고
  남기는 건 값싸며, 재추가 시 증분 이어받기가 공짜다. 심볼 구성 변경은 백테스트가 보는
  유효 데이터를 바꾸므로 버전을 올린다 (§9.5).
- **삭제 시멘틱:** 물리 Parquet(`deleteDataset` — dataset= 최상위 파티션 하나가 전부, §11)
  을 먼저 지우고 DB 행을 지운다(자식은 cascade). 순서 이유: 파일 삭제 실패 시 데이터셋이
  온전히 남는 쪽이, DB 먼저 지우고 고아 파티션이 조용히 남는 쪽보다 낫다.
  `backtestJobs.datasetId` 는 의도적으로 FK 가 아니므로 완료된 백테스트 기록은 pinned
  버전·해시와 함께 역사로 남는다 — 삭제가 재현성 기록을 파괴하지 않는다.
- **삭제 가드:** 실행 중 sync 잡(409, market-data 자체 판단)과 활성 백테스트(409) 를
  거부한다. 백테스트 확인은 market-data 가 backtest 테이블을 읽지 않도록 조립부가
  `jobQueue.activeCountForDataset` 람다를 라우트에 주입한다 (§7 모듈 경계).

## D-022: 동기화 취소 경로 — 페이지 경계 취소, in-process 플래그

- **변경 내용:** `POST /data-jobs/:id/cancel` 과 웹 카드의 "동기화 취소" 버튼을 추가했다.
  취소는 in-process 플래그로 전달되고 `pullRange` 가 페이지 경계(다음 fetch 직전)에서
  확인해 잡을 CANCELLED 로 접는다. 저장된 페이지·워터마크는 남으므로 재실행이
  이어받는다 — 취소가 데이터를 버리지 않는다.
- **이유:** D-021 의 삭제 가드(409)가 "실행 중 잡을 접고 삭제"의 반대 방향 경로 없이
  들어가, 장시간 백필 중인 데이터셋은 서비스 재시작 말고는 접을 수단이 없었다.
- **재접속 UX:** `DatasetSummary.runningSyncJobId` 로 실행 중 잡을 노출해, 새로고침
  이나 다른 탭에서도 카드가 진행 중 상태에 붙고 취소할 수 있다.
- **한계:** 취소는 같은 프로세스의 잡만 가능하다(fire-and-forget 이 프로세스 내 실행
  이므로 충분). 재시작 고아 잡은 기존 부팅 정리가 담당한다. 취소 시 coverage 갱신은
  하지 않는다 — 다음 성공 sync 가 갱신한다.

## D-023: 2026-07-28 운영 장애 — 동기화 쓰기 증폭이 무스왑 1GB 박스를 질식시켰다

- **증상:** 1분봉 백필 중 서버 전체 마비 — SSH·브라우저 SSH 불응, networkd netlink
  타임아웃, journald 중단. OOM 킬 기록 없음. Lightsail 콘솔 재부팅으로 복구.
- **근본 원인 (sar·journal 증거):** 백필 저장이 페이지(200봉)마다 월 파티션 전체를
  읽기→병합→재작성해, 백필이 진행될수록 저장 1회가 무거워지는 쓰기 증폭이 있었다.
  이 재작성이 DuckDB 를 메모리 상한(384MB)까지 밀어올려 10분 만에 +300MB
  (247→555MB, 가용 114MB) — 스왑 0 인 909MB 박스에서 커널이 회수할 페이지가
  바닥나 페이지 캐시 스래싱으로 sshd 까지 아사했다. 완전 고갈 직전에서 수십 분을
  버텼기 때문에 OOM 킬러는 뜨지 않았다. 유닛의 MemoryMax=768M 은 캡에 닿지 않아
  무력했다 — 앱이 캡 이내로만 써도 시스템 몫이 없었다.
- **오인 주의:** 직전에 누른 데이터셋 삭제 버튼은 무관하다 (지워진 건 다른 데이터셋,
  마비 시점에 돌던 것은 실측-1m 동기화). 429 크롤(차트 그룹 실한도가 문서 추정보다
  낮음)은 동기화를 느리게 만들어 노출 시간을 늘렸을 뿐 직접 원인이 아니다.
- **수정 (3층):**
  1. 근본 — pullRange 저장 배칭: 페이지마다 저장하지 않고 1만 봉씩 모아 저장
     (파티션 재작성 월당 ~1회). 에러·취소로 빠져나갈 때도 finally 에서 flush 해
     페이지 수준 이어받기 보존을 유지한다. 워터마크는 여전히 저장 이후에만 넓힌다.
  2. 인프라 — provision.sh 에 스왑 2GB (마비를 "느려짐"으로 강등), 유닛에
     MemoryHigh=512M(조기 회수 압박) + MemoryMax 768→640M (시스템 몫 확보).
  3. 운영 즉시 조치 — 서버에 스왑·systemd override 를 수동 적용 완료 (재프로비저닝
     시 리포 버전으로 수렴).
- **후속 (미구현):** 차트 그룹 rate limit 실측 반영 — 스펙 §13 의 "응답 헤더 반영"
  (X-RateLimit-*) 을 공통 REST 클라이언트에 구현하면 429 크롤이 사라진다.

## D-024: 백테스트가 데이터셋 timeframe 을 무시했다 — 일봉 데이터셋은 전부 실패했다

- **증상:** 삼성전자 일봉을 정상 수집(커버리지가 봉 개수·마지막 봉까지 보고)한 뒤
  2025-07-27 ~ 2026-07-24 로 백테스트를 돌리면 "선택한 기간·종목에 데이터가 없습니다"
  로 실패했다. 커버리지 화면과 백테스트가 정면으로 모순된 상태.
- **근본 원인:** `backtest-child.ts` 의 캔들 로드가 `timeframe: '1h'` 로 하드코딩되어
  있었다. 데이터셋의 timeframe 은 "백테스트가 소비하는 기준"이라는 관례를 이미 갖고
  있는데(1m 수집·import → 1h 사전 집계로 `'1h'`, 일봉 수집 → `'1d'`,
  `createBrokerDataset`) 자식 프로세스만 그 필드를 읽지 않았다. Parquet 레이아웃은
  `timeframe=` 을 파티션 경로에 쓰고 `getCandles` 는 폴백 없이 해당 디렉터리만 읽으므로,
  일봉 데이터셋에는 `timeframe=1h/` 가 존재하지 않아 심볼이 조용히 건너뛰어지고 0봉이
  됐다. 즉 **일봉 수집 데이터셋의 백테스트는 예외 없이 전부 실패**했다 (D-020 이
  일봉 수집을 추가한 시점부터).
- **오인 주의:** 데이터 커버리지 문제가 아니다. 커버리지는 `dataset.timeframe` 기준으로
  계산되어 처음부터 정확했다. 에러 메시지가 "데이터 커버리지를 확인하세요" 라고
  안내해 진단을 반대 방향으로 밀었다.
- **수정:** `dataset.timeframe` 을 그대로 사용한다. 에러 메시지에 찾던 timeframe 을
  넣어(`선택한 기간·종목에 1d 데이터가 없습니다`) 커버리지가 정상인데 실패하는 경우가
  다시 생기면 여기서 갈리게 했다.
- **왜 안 잡혔나:** 자식 프로세스 경로에 일봉 데이터셋 테스트가 없었다. 기존 통합
  테스트는 1h CSV 만 쓴다 — CSV import 는 애초에 1m/1h 만 받으므로 1d 데이터셋을
  만들 수 없고, 1d 는 증권사 동기화 경로에서만 생긴다. 회귀 테스트
  (`tests/integration/backtest-daily-dataset.test.ts`)는 그 상태를 직접 재현한다:
  `createBrokerDataset(…'1d'…)` + 1d 봉 저장 + coverage 갱신 → 자식 프로세스 완주와
  읽은 봉 수까지 확인한다.

## D-025: 복제를 두 갈래로 — 그리고 제출 검증이 기간을 보게 했다

- **변경 내용:** 상세 화면의 단일 "복제 실행" 을 `복제`(동일 조건 즉시 재실행)와
  `재설정 및 복제`(원본 값으로 프리필된 위저드를 전략부터 다시)로 분리했다. 후자는
  읽기 전용 `GET /backtests/:id/clone-draft` 가 재기준된 요청·경고·`blockers` 를 주고,
  위저드가 `?from=<jobId>` 로 그 값을 채운 뒤 평범한 `POST /backtests` 로 제출한다.
- **제출 검증 보강 (같은 릴리스):** `validateSubmission` 이 기간에 봉이 있는지 보지 않아,
  D-024 의 실행이 201 로 접수되고 한참 뒤 FAILED 로 끝났다. `data_coverage` 로 기간 ×
  커버리지 겹침을 검사해 **요청한 종목 전부가 구간 밖이면 400** 으로 즉시 거부하고
  보유 범위를 메시지에 담는다. 심볼 멤버십 검사만으로는 부족했다 — 그건 설정된
  유니버스 기준이라 아직 한 번도 동기화되지 않은 종목이 통과한다.
- **일부만 비면 거부하지 않는다:** 신규 상장처럼 이력이 짧은 종목 하나로 유니버스
  전체를 막는 건 과하다. 대신 자식 프로세스가 실제로 봉을 낸 심볼과 비교해 제외된
  종목을 실행 경고로 남긴다 — 커버리지 추정이 아니라 실측이다.
- **초안 검증 정책은 D-050이 대체한다:** 처음에는 `clone-draft`가 검증을 돌리고 사유를
  `blockers`로 돌렸다. 전체 유니버스 해소가 전략 화면 진입을 지연한다는 운영 문제가
  확인돼 D-050에서 초안을 재기준 전용으로 축소했다. 현행 `/clone`이 제출 검증을
  통과해야 하는 성질은 그대로다 — 동일 조건 재실행은 조건이 유효할 때만 뜻이 있다.
- **계보는 기록하지 않는다:** 재설정 경로는 전략까지 바꿀 수 있어 "원본의 복제" 라
  부르기 애매하다. 평범한 신규 제출로 두고 감사 로그에는 `backtest.created` 로만 남긴다.
- **경계 계산 공유:** `periodToTsRange` 를 `src/shared/schemas/backtest-request.ts` 로
  빼 제출 검증과 실행부가 함께 쓴다. 각자 계산하면 제출 검증은 통과시키는데 실행부는 0봉을 보는
  D-024 와 같은 종류의 어긋남이 생긴다.
- **대기열 상한:** `enqueue` 에 깊이 제한이 없어 `복제` 연타로 QUEUED 가 무한히 쌓였다.
  동시 실행 상한(기본 1)이 있어 서버가 죽지는 않지만, 리소스 가드는 제출 순간의 여유만
  보고 쌓인 대기열은 보지 않는다. `MAX_QUEUED_BACKTESTS`(기본 20)로 429 를 반환한다.
  QUEUED 만 센다 — 실행 중은 동시 실행 상한이 이미 묶는다. 429 를 507 과 구분하는 이유는
  사용자가 할 일이 다르기 때문이다(기다리거나 취소 vs 호스트 자원 확보).

## D-026: 백테스트 소비 timeframe 명시화 — 1분봉 소비를 열었다

- **문제:** 백테스트 요청에 timeframe 개념이 없었다. 실행부가 `dataset.timeframe`
  (1h | 1d) 을 암묵적으로 소비하고, "무슨 봉으로 돌렸는지" 는 요청·결과·UI 어디에도
  없었다. 1m 원본이 물리적으로 존재하는데 (1h 데이터셋은 1m + 1h 를 함께 보관)
  백테스트만 접근할 수 없었다 — §11 "1시간봉 우선" 은 메모리 관례이지 구조가 아니다.
  엔진·전략은 timeframe 무지(봉 배열 + 봉 개수 파라미터)라 코어 변경은 없다.
- **변경:** 요청 스키마에 `timeframe`(optional — 과거 저장 요청 호환, 미지정 =
  데이터셋 timeframe). 제출 검증이 데이터셋 제공 범위
  (`availableTimeframes`, market-data domain 공유 헬퍼)를 검사한다. 위저드는 1h
  데이터셋에서 1시간봉(기본)/1분봉을 노출하고 항상 명시해 보낸다 — 재현성(§9.5)
  관점에서 결과·복제가 소비 봉을 들고 다닌다.
- **메모리 가드레일:** 실행부는 기간 내 전체 봉을 배열로 올린다. KR 1m 은 종목·연당
  약 9.5만 봉 — 상한 없이 열면 OOM. `MAX_BACKTEST_BARS`(200만) 를 두 겹으로 지킨다:
  제출 시점엔 coverage 메타데이터 선형 추정(`estimateBars`, 1h→1m 배율 60,
  Parquet 안 읽음 — D-025 원칙)으로 400, 실행부에선 실측 초과 시 실패(제출 후
  import 로 봉이 는 경우의 방어선). 초과는 다운샘플로 뭉개지 않고 명시적으로 거부한다.
- **하지 않은 것:** 데이터셋 모델 재설계(보유 timeframe 목록화)와 스트리밍 엔진 —
  상한으로 충분한 시점에 하는 최적화가 아니다. 1m 전용 coverage 도 계산하지 않는다
  (기간 검증엔 1h coverage 의 시간 범위로 충분하다).

## D-027: 미지원 시장을 UI 에서 고를 수 없게 한다

- **변경 내용:** 데이터셋 생성·CSV 가져오기 폼의 시장 선택을 `GET /markets` 응답으로 렌더하고, 세션이 정의되지 않은 시장(US)은 `disabled` + `(지원 예정)` 으로 두고 이유를 Select 아래에 상시 표시한다. 지원 여부의 단일 출처는 `exchange-session.ts` 의 `SESSIONS` 맵이며 `hasMarketSession` 이 그것을 노출한다. 재무(DART) 수집이 국내 전용이라는 사실은 재무 체크박스 툴팁에 상시 표시한다.
- **이유:** D-006 이 US 를 거부하도록 고쳤지만 UI 는 계속 US 를 선택지로 내놓았다 — 사용자가 받는 안내는 시장을 고르고 종목을 다 넣고 「만들기」를 누른 뒤 오는 400 하나뿐이었다. 거부를 코드가 알고 있는데 화면이 말하지 않는 상태였다. 지원 여부를 `getSessionForMarket` 이 던진다는 사실 안에만 두면 화면이 물어볼 방법이 없어 UI 에 시장 목록을 따로 박게 되고, 세션이 추가되는 날 화면만 낡은 채로 남는다.
- **영향:** 서버 검증(`createBrokerDataset`·`importCsv` 의 `getSessionForMarket` 호출)과 `z.enum(['KR','US'])` 는 그대로 둔다 — UI 는 미리 알려주는 층이지 거부하는 층이 아니고, 스키마에서 US 를 빼면 400 메시지가 "필드가 올바르지 않습니다" 로 뭉개져 시장이 원인이라는 정보가 사라진다.
- **남은 한계:** `formatKrw`/`formatSignedKrw` 가 통화를 원화로 고정한다(`format.ts:8-17`). US 데이터셋이 존재할 수 없어 지금은 드러나지 않지만, US 지원 작업은 DST 포함 세션 정의와 통화 표시 일반화를 **함께** 해결해야 한다. 한쪽만 하면 미국 종목 손익이 "원" 으로 표시된다.

## D-028: `hourly-breakout` → `range-breakout` — 이름·성능·청산을 함께 고쳤다

- **변경 내용:** `hourly-breakout`("시간봉 돌파", v1.2.0)을 `range-breakout`("전고점 돌파", v2.0.0)으로 대체했다. 세 가지를 함께 바꿨다. (1) 돌파 기준선을 봉마다 `getHistory()` 전체를 복사해 구하던 것을 고정 길이 창(`shared/indicators.ts` 의 `RollingMaxState`)으로 바꿨다. (2) 추적 손절(`trailAtrMultiplier`, 기본 2)과 보유 상한(`maxHoldBars`, 선택)을 더했다 — `shared/trailing-stop.ts` 재사용. (3) 종목당 명목 비중 상한(`maxPositionWeightPercent`, 기본 20)을 더했다. ATR 구현도 `shared/indicators.ts` 로 합쳤다. "엔진 검증용 기준 전략" 이라는 규정은 폐기하고 다른 4개와 같은 급의 전략으로 둔다.
- **이유(이름):** 데이터셋이 분봉·시간봉·일봉을 모두 고를 수 있게 되면서(D-026) 이름이 사실과 어긋났다. 로직은 처음부터 봉 수 기반이라 시간봉과 아무 관계가 없었다. 표시명만 고치면 부족하다 — `strategyId` 가 상세 페이지 재현성 카드와 위저드 확인 단계에 그대로 노출되므로 "hourly" 가 화면에 남는다.
- **이유(성능):** `history.slice(0, -1)` 이 봉마다 전체 이력을 복사해 심볼당 O(n²) 였다. 2년 1분봉(약 195,000봉)이면 총 10¹⁰회 규모의 원소 복사에 봉마다 수백 KB 임시 배열 할당이 붙고, `MAX_BACKTEST_BARS`(2백만) 근처는 사실상 완주 불가다. 등록 전략 중 이 전략만 봉마다 `getHistory()` 를 썼다 — 나머지는 증분 지표만 쓴다. D-023 의 무스왑 1GB 박스에서는 느린 문제가 아니라 질식 위험이었다.
- **이유(청산):** 고정 손절과 선택적 고정 익절만 있어서, 익절을 비운 기본 설정에서는 +8 ATR 까지 간 포지션이 되돌아와도 진입가 −2 ATR 까지 전부 내줄 때까지 나갈 장치가 없었다. 돌파 전략에서 추적 손절은 선택이 아니다. `ema-trend-switch` 는 이미 갖고 있는데 정작 가장 필요한 전략이 안 쓰고 있었다.
- **이유(비중 상한):** `riskQuantity` 만으로는 저변동 종목에서 수량이 자본 전액을 넘어선다(ATR/가격 0.5%·리스크 1%·손절 2×ATR 이면 수량 ≈ equity/price). 그러면 엔진이 현금 부족으로 수량을 깎아 체결하므로 선언한 리스크 %도 `risk.maxPositions` 도 의미를 잃고, 자산 곡선은 정상처럼 보이면서 사실상 한 종목 올인이 된다.
- **영향:** id 를 바꿨으므로 과거 `hourly-breakout` 실행은 전략 이름 대신 원본 id 로, 파라미터는 한국어 라벨 없이 원본 키로 표시되고(`/strategies/hourly-breakout/schema` 404), 「재설정 및 복제」 시 전략을 다시 골라야 한다(D-025 의 "사라진 전략" 경로). **별칭 계층을 두지 않는다** — `strategySourceHash` 는 `id + version + 파라미터 스키마` 해시라 id 를 유지해도 v2.0.0 과 과거 실행의 해시 비교는 어차피 끊긴다. 별칭이 사는 것은 재현성이 아니라 표시·복제 편의뿐이고, 지금까지의 실행은 대부분 검증용이다. 과거 실행 데이터를 새 id 로 고쳐 쓰는 마이그레이션도 하지 않는다 — 재현성 메타데이터를 사후 수정하면 "그 실행이 실제로 무엇을 돌렸는지" 를 덮어쓴다.
- **유지한 성질(회귀 금지):** 손절·익절 레벨을 신호봉 종가가 아니라 **실제 체결가** 기준으로 고정한다(갭 진입 대응). 돌파 기준선 창은 현재 봉을 넣기 **전에** 읽는다 — 종가가 자기 자신의 고가를 넘는 일이 구조적으로 불가능하다. 두 성질 모두 `tests/unit/engine.test.ts`·`tests/unit/range-breakout.test.ts` 가 지킨다.
- **남은 한계:** 손절·익절은 종가로만 판정하므로 실제 스톱 주문보다 낙관적이다 — `execution.fillTiming` 이 `NEXT_BAR_OPEN` 리터럴로 고정돼 장중 체결을 표현할 수 없다. 문구로 고지하고 `BACKTEST_BIAS_REVIEW.md` B-008 에 남겼다. 워밍업 봉(`max(atrPeriod, lookbackBars)+1`)이 요청 기간 앞에서 소모되는 것도 그대로다(같은 문서 B-003).

## D-029: 백테스트 요청은 전략 버전을 나르지 않는다

- **변경 내용:** `backtestRequestSchema` 에서 `strategyVersion` 을 제거했다. 제출 검증의 "전략 버전 불일치" 400 도 함께 없앴다. 실행 기록(`backtest_runs.strategy_version`)은 그대로다 — 워커가 레지스트리에 등록된 전략에서 직접 읽어 남긴다.
- **이유:** 클라이언트가 버전을 보내도 서버가 실행하는 것은 어차피 "지금 등록된" 전략이다. 요청의 버전은 실행 대상을 고르지 못하고 거부 사유만 됐다 — 배포로 전략 버전이 올라가면 열어 둔 위저드에서의 제출이 막히고, 사용자는 새로고침 말고 할 일이 없다. 파라미터가 새 전략과 실제로 안 맞으면 `validateParameters` 가 스키마로 잡으므로 방어선이 사라지지도 않는다.
- **일관성:** 복제(clone) 경로는 이미 옛 버전을 만나면 거부가 아니라 재기준+경고였다(D-025). 같은 상황에 제출만 거부하는 두 정책이 공존했는데, 이제 하나다.
- **재현성 영향 없음:** 무엇이 실행됐는지는 요청이 아니라 실행 기록이 답한다. 기록에는 여전히 `strategyId`·`strategyVersion`·`strategySourceHash` 가 남는다(§9.5). 오히려 요청의 버전은 "이 값으로 돌았다" 는 보장이 없는 값이라 기록으로 착각될 여지가 있었다.
- **저장된 요청:** D-029 이전 요청은 `strategyVersion` 을 품고 있다. `rebaseStoredRequest` 가 그 필드를 버리되, 값이 현재 버전과 다르면 "전략 버전 X → Y 로 재기준했습니다" 경고는 그대로 낸다 — 복제는 재현이 아니라 재실행이므로 결과가 달라질 수 있다는 고지는 남아야 한다.
- **테스트 부채도 함께 사라진다:** 요청을 만드는 모든 테스트가 현재 전략 버전 리터럴을 들고 있었고, `range-breakout` v2.0.0 개정 때 그중 셋이 낡은 채 남아 배포 검증 게이트를 막았다(제품은 멀쩡했다). 이제 요청에 버전이 없으므로 그 리터럴 자체가 없다. 재기준 경고를 확인하는 테스트만 `tests/helpers/strategy-versions.ts` 로 레지스트리에서 현재 값을 받아 쓴다.
- **남은 것:** 화면의 `v2.0.0` 표기는 요청이 아니라 레지스트리(위저드) 와 실행 기록(상세 페이지)에서 읽는다.

## D-030: 운영 실행 모델 — systemd 유닛 + `/opt` 배포 (Docker 도, home 도 아니다)

- **변경 내용:** 새 결정이 아니라 **이미 그렇게 만들어진 것의 근거 기록**이다. 앱은 systemd 유닛(`infra/systemd/quant-platform.service`)으로 돌고, 코드는 root 소유 `/opt/quant-platform/releases/<릴리스>` 에 풀려 `current` 심볼릭 링크로 전환되고, 가변 상태는 quant 소유 `/var/lib/quant-platform` 에만 있다. Dockerfile 은 두지 않는다.
- **이유(하중을 받는 것 하나):** 909MB 박스에서 앱이 555MB 만 써도 sshd·journald·caddy 가 질식했다 (D-023). 앱이 서버를 느리게 만든 게 아니라 **관리 경로를 죽였다** — SSH 가 안 들어가면 고칠 수도 없다. 따라서 "앱에게 메모리 예산을 정해주고 커널이 강제한다" 가 선택이 아니라 생존 조건이고, 그것이 `MemoryHigh=512M`/`MemoryMax=640M`/`TasksMax=256` 이다. `MemoryHigh` 를 따로 두는 이유는 Max 도달(=OOM kill) 전에 회수 압박으로 스왑·캐시로 밀어내기 위해서다.
- **왜 `ulimit` 이 아닌가:** cgroup 은 **프로세스 트리 전체**에 한 예산을 건다. 백테스트는 같은 아티팩트를 자식 프로세스로 fork 해 돌리므로(`src/workers/backtest-child.ts`) 부모+자식 합계가 묶여야 의미가 있다. `ulimit` 은 프로세스별이라 이걸 표현할 수 없다.
- **그 외에 systemd 가 주는 것:** (1) 재부팅 생존 — 클라우드 인스턴스는 호스트 유지보수로 예고 없이 재부팅된다. (2) `Restart=on-failure`+`RestartSec=5` — 위의 OOM kill 을 자동 복구로 강등한다. (3) 샌드박싱을 앱 코드 밖에서(`ProtectSystem=strict`·`CapabilityBoundingSet=` 등) — 스펙 §2.1 "애플리케이션은 인프라를 모른다" 와 같은 방향이다. (4) `EnvironmentFile` 로 600 root:root 비밀을 `ps` 노출 없이 주입, 그리고 그 덕에 CLI 를 같은 컨텍스트로 재현하는 `systemd-run` 이 공짜로 따라온다(§28.2). (5) `systemctl restart` + `is-active` 라는 판정 가능한 단일 상태 — D-010 의 "코드+DB 스냅샷 동반 롤백" 이 이것 없이는 조립되지 않는다. (6) `StandardOutput=journal` — 앱에 로그 파일 회전 코드가 한 줄도 없는 이유.
- **대안(Docker):** 버렸다. 여유가 ~270MB 뿐인 박스에서 컨테이너 런타임 상주 메모리가 그 여유를 잠식한다. 게다가 컨테이너의 주 가치(cgroup 제한·네임스페이스 격리·재시작 정책·로그 수집)를 systemd 가 이미 전부 주므로 겹치고, 단일 아티팩트·단일 프로세스에는 오케스트레이션할 대상이 없다. 네이티브 모듈(better-sqlite3·argon2·@duckdb/node-api, `onlyBuiltDependencies`)의 빌드 무게는 **반-Docker 논거이지 친-systemd 논거가 아니다** — 모듈이 순수 JS 였어도 프로세스 슈퍼바이저는 여전히 필요하다.
- **대안(nohup·tmux·PM2):** 버렸다. 재부팅에서 사라지고, cgroup 예산이 없어 위 장애를 그대로 재현한다. PM2 는 감시 프로세스가 하나 더 상주해 예산을 또 먹으면서도 네임스페이스 격리는 주지 않는다.
- **왜 코드가 home 이 아니라 `/opt` 인가:** (1) 유닛의 `ProtectHome=true` 가 `/home`·`/root` 를 이 프로세스에게 **비어 있게** 만든다 — 코드를 home 에 두려면 이걸 끄는 거래를 해야 하고, 그러면 임의 파일 읽기 버그 하나가 `~/.ssh/id_ed25519`(=배포 전권)에 닿는다. 읽기 전용(`ProtectSystem=strict`)으로는 부족하다 — 훔치는 데는 읽기만 필요하다. (2) 로그인 계정명을 가정할 수 없다 — 클라우드 이미지마다 ubuntu/admin/ec2-user 로 다르고 `scripts/bootstrap.sh` 는 의도적으로 가정하지 않는다(§2.1). home 경로는 그 관례를 유닛 파일에 박아버린다. (3) `quant` 는 `--system --home /var/lib/quant-platform --shell nologin` 이라 애초에 home 이 없다. (4) `/opt` 가 root 소유 + `ReadOnlyPaths` 라 **앱이 자기 실행 코드를 고칠 수 없다** — RCE 가 재시작 후에도 살아남는 지속성을 못 얻는다. (5) 릴리스 회전(`deploy.sh` 의 `KEEP_RELEASES` 초과분 삭제)이 데이터를 먹지 않는 경계가 필요하다 — 코드는 버려도 되는 것, 상태는 백업 대상이라는 분리가 `/opt` vs `/var/lib` 다.
- **비용:** 배포가 `sudo` 를 요구한다. `systemctl restart`·UFW·Caddy 에 어차피 root 가 필요하고 passwordless sudo 는 `bootstrap.sh` 가 `sudo -n true` 로 먼저 검증하는 전제이므로 추가 비용은 없다.
- **뒤집히는 조건:** 근거 서열이 **메모리 제약 → cgroup·샌드박스 필요 → systemd** 이므로, 박스가 충분히 커지면(예: 8GB) 런타임 상주 메모리가 무시할 수준이 되어 "systemd vs Docker" 는 팀 취향 문제로 내려간다. 지금 결론이 명확한 것은 여유가 ~270MB 라는 실측 때문이다. `/opt` 쪽 근거 (2)(4)(5)는 박스 크기와 무관하게 남는다.

## D-031: 미통합 복원 스크립트 제거 — 재해복구는 Phase 7 runbook 에서 설계한다

- **변경 내용:** `scripts/restore.sh` 를 삭제했다. `backup.sh` 는 SQLite 와 exports 백업
  생성만 담당하고, 독립 복원 명령은 현재 제공하지 않는다.
- **이유:** 이 스크립트는 앱·테스트·프로비저닝·배포 어디에서도 호출되거나 서버에
  설치되지 않았다. 현재 백업 형식의 `exports.tar.gz` 를 복원하지 않았고, 운영 데이터
  경로를 하드코딩해 월별 복원 테스트에 사용하면 실제 DB 를 바로 덮어썼다. 복원 전
  스냅샷·SQLite 무결성 검사·실패 시 서비스 재기동 또는 원복도 없어, 존재 자체가 검증된
  재해복구 수단이라는 잘못된 인상을 줬다.
- **배포 롤백과 무관:** deploy.sh 의 실패 롤백은 재시작 직전 SQLite 스냅샷을 만들고
  코드와 DB 를 함께 되돌리는 독립 경로(D-010)라 영향을 받지 않는다.
- **후속:** Phase 7 disaster runbook 은 SQLite 와 exports 를 함께 복구하고, 무결성 검사와
  실패 원복을 포함한 절차를 먼저 정의한다. 운영 데이터가 아닌 격리 환경에서 실제 백업으로
  검증한 뒤에만 자동화 여부를 결정한다. D-019 이전 1h Parquet 백업 호환 경로는 제거한다.

## D-032: 전략 카드가 데이터 요구를 말한다 — 두 상태를 모두 표시한다

- **변경 내용:** `GET /strategies` 목록과 `GET /strategies/:id` 응답이
  `requiresFundamentals` 를 **항상 boolean 으로** 내리고, 위저드 1단계 전략 카드와 5단계
  검토 카드가 그것을 배지로 표시한다. 「재무 필요」(채운 배지·문서 아이콘)와 「봉 데이터만」
  (테두리 배지·봉 아이콘) 두 상태를 모두 그리며, 고른 카드에서는 한 줄로 풀어 쓴다.
  두 엔드포인트는 같은 `toSummary` 를 거친다(`registry.describe()` 신설).
- **이유:** 봉 지표만으로 매매하려는 사용자가 재무가 개입하는 전략을 모르고 고를 수 있었다.
  코드는 `requiresFundamentals` 로 알고 있었고 제출 검증이 그것으로 422 를 냈지만, 화면은
  전략을 고르는 시점에 아무 말도 하지 않았다 — 사용자가 받는 신호는 데이터셋·기간·자본을
  다 채우고 제출한 뒤에 오는 거부 하나뿐이었다. D-027 과 같은 상태이고 같은 방향으로 고쳤다.
  등록 전략 다섯 중 넷은 설명 문구에 데이터 요구를 적지도 않아 배지가 새 정보다.
- **왜 배지 없음으로 「봉 전용」을 표현하지 않는가:** 배지가 없는 카드는 "재무를 안 쓴다" 와
  "아직 표시가 없다" 를 구분해주지 못한다. 예외에만 표찰을 붙이는 관례가 더 깔끔하지만,
  이 기능의 목적은 장식을 아끼는 게 아니라 **없음을 근거로 안심할 수 있게** 만드는 것이다.
  넷에 「봉 데이터만」이 붙어 있어야 하나에 붙은 「재무 필요」가 대조로 읽힌다.
- **왜 `undefined` 를 false 로 좁히지 않는가:** 웹은 응답을 런타임 검증하지 않으므로
  필드가 없는 응답(낡은 서버)이 올 수 있다. `strategyDataRequirement` 는 그때 `null` 을
  줘서 배지를 침묵시킨다 — false 로 뭉개면 재무 전략에 「봉 데이터만」이 붙어, 사용자가
  피하려던 상황을 화면이 보증해 버린다. 서버가 도메인의 선택 필드를 `=== true` 로 정규화해
  내리는 것도 같은 이유다. 잘못 안심시키는 것보다 말하지 않는 게 낫다.
- **표시 수단:** 색만으로 가르지 않는다(§17) — 아이콘·문구·배지 무게가 함께 다르다.
  재무 쪽만 채운 배지(`default`)로 둔 이유는 목록을 훑을 때 "봉이 기본이고 재무가 예외" 가
  한눈에 잡혀야 하기 때문이다. `secondary` 로는 테두리 배지와 무게가 거의 같아 구분되지
  않았다(실측). 신규 색을 들이지 않으므로 neutral/zinc 기조는 유지된다.
- **영향 없음(서버 검증):** 재무 미수집 데이터셋에 대한 422 는 그대로다. 배지는 미리
  알려주는 층이지 거부하는 층이 아니다 — D-027 과 같은 분업이다.
- **남은 한계:** 데이터셋 쪽 재무 보유 여부는 아직 화면에 없다. 위저드가 2단계에서 읽는
  `DatasetSummary` 에 그 필드가 없어(`slices` 는 봉 보유만 말한다) 「재무 필요」 전략에
  재무 미수집 데이터셋을 고르면 여전히 제출 단계 422 에서 알게 된다. 데이터셋 카드가
  재무 보유를 함께 표시하는 것이 이 결정의 자연스러운 후속이다.

## D-033: 데이터셋 카드가 재무 보유와 마지막 수집 시각을 말한다

- **변경 내용:** `GET /datasets` 목록과 단건 응답에 두 값을 더했다. (1) `hasFacts` — 재무
  팩트 보유 여부, (2) `lastSyncedAtMs` — 마지막으로 수집이 완료된 시각. 데이터 화면의
  데이터셋 카드와 위저드 2단계 데이터셋 카드가 「재무 있음」·「재무 없음」 배지와
  「마지막 수집 N일 전」을 표시한다. 배지 표기(채운 배지 = 재무 있음, `FileText`)는
  전략 카드의 「재무 필요」와 맞췄다 — 두 카드가 한 벌로 읽혀야 한다 (D-032).
- **이유:** D-032 가 전략 쪽만 고쳐 놓아, 「재무 필요」 전략에 재무 미수집 데이터셋을
  고르는 조합이 여전히 제출 단계 422 에서야 드러났다. 이제 1단계에서 「재무 필요」를 본
  사용자가 2단계에서 「재무 없음」을 보고 제출 전에 알아차린다. D-032 의 「남은 한계」가
  이 결정으로 닫힌다.
- **있고 없음만 본다:** `hasFacts` 는 파티션 파일 존재만 확인한다
  (`ParquetFactRepository.hasFacts` = `fs.existsSync`). 종목별·연도별로 얼마나 채워졌는지는
  묻지 않는다 — 카드가 답할 질문이 아니고, 커버리지 판정은 DuckDB 질의를 데이터셋 수만큼
  낸다. 제출 검증(422)이 쓰는 것과 **같은 함수**라 화면과 게이트가 어긋날 수 없다.
- **왜 `DatasetSummary` 에 `hasFacts` 를 넣지 않았는가:** 그 타입은 market-data 소관이고
  재무는 facts 모듈 소관이다 (§7). `factsSyncEstimator` 와 같은 방식으로 조립부가
  `datasetHasFacts` 클로저를 라우트에 넘기고, 라우트가 응답에 실어 보낸다 — market-data 는
  facts 를 계속 모른다. 반대로 `lastSyncedAtMs` 는 market-data 자기 테이블
  (`data_import_jobs`)에서 나오므로 `DatasetSummary` 에 들어간다.
- **마지막 수집의 정의:** 가장 최근 **COMPLETED** 수집 잡의 `completedAtMs` 이고, 소스를
  가리지 않는다(BROKER 동기화·CSV·Parquet 가져오기 모두). 카드가 답해야 하는 질문은
  "언제 동기화했나" 가 아니라 "이 데이터가 얼마나 묵었나" 이고, 지금 실제 데이터 경로는
  CSV 가져오기다 (D-002) — BROKER 잡만 세면 대부분의 카드가 영원히 빈칸으로 남는다.
  그래서 화면 문구도 「마지막 동기화」가 아니라 **「마지막 수집」** 이다. 실패한 잡은
  세지 않는다: 실패한 동기화가 "방금 수집" 으로 보이면 신선하다고 착각한다.
  `createdAtMs` 가 아니라 `completedAtMs` 로 정렬한다 — 오래 걸린 잡이 나중에 시작한
  잡보다 늦게 끝날 수 있다.
- **문턱을 두지 않는다:** "며칠이면 묵었다" 를 판정해 경고하지 않는다. 그 기준은 봉
  주기(분봉/일봉)와 시장 휴장에 따라 다르고, 여기서 정하면 화면이 근거 없는 정책을
  말하게 된다. 경과 시간(`formatRelativeTime`)을 절대 시각보다 **앞에** 놓아 판단 재료만
  주고, 동기화 여부는 사용자가 정한다. 미래 시각(시계 어긋남)은 '방금' 으로 접는다.
- **남은 한계:** 조합이 어긋나도 **막지는 않는다** — 두 배지를 나란히 보여 줄 뿐이고,
  「재무 필요」 + 「재무 없음」으로 제출하면 서버가 422 로 거부한다. 위저드가 그 조합을
  단계 게이트에서 미리 막는 것은 다음 개선이다. 또한 배지는 재무 파일의 **존재**만
  말하므로, 일부 종목·연도만 수집된 데이터셋도 「재무 있음」이다 (의도된 범위).

## D-034: 종목을 1급 객체로 — 데이터셋은 참조만 갖는다 (파괴적 전환)

- **변경 내용:** 봉·재무·수집 워터마크·커버리지·버전이 모두 **종목**에 매달린다.
  데이터셋은 `dataset_symbols` 로 참조만 갖고 `market`·`defaultTimeframe`·`symbolsJson` 을
  잃었다. Parquet 최상위 `dataset=` 파티션이 사라져 `market=/timeframe=/symbol=/…` 와
  `facts/scope=SYMBOL/symbol=…` 가 됐다. `SymbolService` 를 신설하고 `DatasetService` 는
  참조 편집 + 버전 스냅샷만 남았다. 수집 잡은 데이터셋이 아니라 **종목 집합**을 받는다
  (`data_sync_jobs.symbols_json`). 호환 경로는 두지 않았다 — 마이그레이션을 통째로
  재생성하고 `dataset-merge-migration.ts` 는 삭제했다 (사용자 지시).
- **이유:** 재무가 `dataset=` 아래 있어 같은 종목이 N번 복제됐고, 비용은 디스크가 아니라
  **DART 일일 호출 한도**였다 (종목·연도당 9회, 한도 40,000/일 — 200종목 50년이면
  데이터셋 **하나로 이미 225%**, 10개면 ~23일). 종목 파티션이 그 중복을 없앤다.
  두 번째 이유는 중복과 무관하다: `writePartition` 이 read-merge-write 라 데이터셋 단일
  파일 시절엔 48만 행을 매 수집마다 재작성했다(SQL VALUES ~38MB, 640MB cgroup 위협).
  이제 해당 종목 몫(~2,400행)만 쓴다. `parquet-fact-repository` 가 근거로 들었던
  "작다 — 200종목 × **20분기**" 는 5년 전제였고 50년에서 만료됐다.
- **재현성(§9.5)을 종목별 버전 스냅샷으로 옮겼다:** 데이터가 데이터셋 간에 공유되면
  "데이터셋 버전" 으로 실행 입력을 고정할 수 없다 — 누군가 종목을 동기화하면 그 종목을
  참조하는 모든 데이터셋의 입력이 변한다. `symbol_versions(code, slice)` 를 두고 수집
  성공마다 올리며, 실행은 `backtest_runs.universeJson`(+`universeHash`)에 소비한 조합을
  스냅샷으로 남긴다. `datasetVersion`/`datasetHash` 는 제거했다. 재무는 슬라이스 축이
  없어 `FACTS` 를 슬라이스 자리에 쓴다. 워커는 스냅샷과 현재 버전을 비교해 **어느 종목이
  변했는지** 경고에 이름으로 적는다 — 종전에는 "데이터셋 버전이 다르다" 뿐이었다.
- **소비 봉 주기의 기준이 데이터로 옮겼다:** `defaultTimeframe` 이 없어졌으므로 요청이
  `timeframe` 을 생략하면 **유니버스가 가진 슬라이스**에서 정한다. 하나면 그것으로,
  둘 다 있거나 둘 다 없으면 거부하고 지정하라고 말한다 — 임의로 하나를 고르면 사용자가
  의도하지 않은 봉으로 돌아간다. 해소한 값은 저장 요청에 박아 넣어 워커가 다시 추론하지
  않게 했다: 규칙이 두 곳에 있으면 갈라지고, 실행 기록도 "무엇을 소비했나" 에 답하지 못한다.
- **종목 구성 중복 금지를 폐기했다:** 구 `symbolsKey`/`DuplicateSymbolGroupError` 가 막던
  비용은 같은 종목을 두 번 긁는 것이었다. 데이터가 종목에 종속된 뒤로는 구성이 같은
  데이터셋 둘이 디스크도 호출도 더 쓰지 않으므로 규칙의 근거가 사라졌다.
- **삭제 의미가 갈렸다:** 데이터셋 삭제는 **참조만** 끊는다(봉·재무는 남는다). 종목 제거가
  실제 삭제이고, 영향받는 데이터셋을 나열해 확인받은 뒤 참조까지 끊는다. 데이터셋을 빈
  껍데기로 만드는 조합은 거부한다 — 판정은 **선택 집합 전체**를 함께 본다: 종목을 하나씩
  보면 2종목 데이터셋에서 둘 다 고른 경우를 "각각 1개는 남는다" 로 잘못 통과시킨다.
- **화면:** 데이터 탭을 데이터셋/종목으로 나눴다. 종목 화면은 봉 보유를 **슬라이스별로**,
  마지막 수집도 **슬라이스별로** 표시한다 — 「봉 있음」·「3일 전」 하나로 접으면 분봉이
  없다는 사실과 분봉이 2개월 묵었다는 사실이 숨는다(D-032·D-033 과 같은 원칙). 참조
  데이터셋 수를 행에 적어 제거를 안전하게 만들고, 동작 바는 하단 고정에 전체 선택을 둔다
  (200종목에서 아래쪽을 체크한 뒤 버튼을 찾아 올라가는 일을 없앤다). 정렬은
  `Intl.Collator('ko')` 가나다순, 이름 없는 종목은 뒤로 몰아 둔다.
- **e2e 가 잡은 세 가지를 함께 고쳤다:** (1) 미지원 시장 이유를 고른 시장에만 붙였다 —
  US 를 고를 수 없으니 그걸 고른 사용자만 읽을 수 있는 문구가 됐다. D-027 의 "상시 표시"
  로 되돌렸다. (2) CSV 로 들어온 종목만 표시명이 빈 채로 남았다 — 등록 경로가 둘인데
  이름 해소가 한쪽에만 있었다. 라우트의 `resolveName` 을 두 경로가 공유한다. (3) 종목 행의
  이름 버튼을 `<label>` 안에 두어 접근성 이름이 배지·수집 시각까지 삼켰다 — 조회 모드는
  `<div>`, 편집 모드만 `<label>` 로 갈랐다. 셋 다 타입·단위 테스트가 잡을 수 없는 층이다.
- **`resolveJobTimeframe` 의 폴백을 없앴다:** 데이터셋 `defaultTimeframe` 으로 추론하던
  코드가 그 필드가 사라진 뒤에도 남아 `undefined` 를 읽고 있었다. 제출 검증이 해소한 값을
  요청에 박아 넣으므로 지금 잡은 항상 값을 갖고, 그 이전 잡은 `null`(화면은 「기록 없음」)
  이다 — 없는 근거로 추측한 값을 "실제로 소비한 봉" 이라고 적는 것이 더 나쁘다.
- **참조 편집 UI (후속으로 채웠다):** 데이터셋 카드의 「종목 편집」이 등록된 종목 전체를
  체크박스로 띄우고 현재 참조를 미리 체크해 둔다. 추가·제거를 **한 번의 PATCH** 로 보내는
  이유: 두 번으로 나누면 교체가 중간에 0종목을 거쳐 서버 검증에 걸리고 앞의 절반만
  적용된다. 0종목이 되는 편집은 저장 버튼을 잠그고 이유를 적는다 — 서버 400 을 받기 전에
  화면이 먼저 말한다. 데이터셋 생성 다이얼로그와 `SymbolPicker` 를 공유해 두 화면이
  갈라지지 않게 했다(보유 봉 표시·정렬). 고르는 자리에 보유 봉을 적는 이유: 봉이 없는
  종목을 참조에 넣으면 제출 단계에서야 걸린다.
- **곁들여 고친 버그:** 이름 변경이 `postJson` 으로 PATCH 라우트를 불러 404 였다 —
  메서드가 안 맞아 온 404 가 "데이터셋이 없다" 로 읽혀 원인이 드러나지 않았다.
  `patchJson` 헬퍼를 추가해 호출부가 메서드를 고민하지 않게 했다.
- **위저드 단계 게이트 (후속으로 채웠다):** 「재무 필요」 전략에 재무 없는 종목을 고르면
  2단계(데이터·종목)에서 막고, 「다음」을 누르기 전에 그 자리에 이유를 띄운다 — 제출한
  뒤 422 를 받는 왕복을 없앤다. **조건은 서버 422 와 같다**: 선택 종목이 전부 비었을
  때만 막고, 일부만 없으면 통과시켜 워커 경고에 맡긴다 (D-025). 화면이 더 조이면 정책이
  둘이 되고, 화면이 막은 제출을 서버는 허용했을 것이라는 사실을 사용자가 알 수 없다.
  **모르는 상태에서는 통과시킨다** — `requiresFundamentals`·종목 목록이 아직 없으면
  근거가 없다. false 로 좁히면 게이트가 조용히 열리고 true 로 좁히면 열 수 없는 문이
  되므로, 둘 다 아니라 통과시키고 방어선은 서버 422 가 맡는다.
- **남은 한계:** 재무 표시는 파일 **존재**만 보므로 일부 종목·연도만 수집된 상태도
  「재무 있음」이다 (D-033 에서 정한 범위를 그대로 유지한다).

## D-035: 종목 목록을 200종목에서 쓸 수 있게 만든다 — 검색·일괄 추가·표시 수 제한

- **변경 내용:** 종목 화면에 (1) 이름·코드 한 입력으로 찾는 검색, (2) 쉼표·줄바꿈으로
  구분한 코드를 한 번에 등록하는 일괄 추가, (3) 페이지당 표시 수 + 페이지 이동을 넣었다.
  데이터셋 카드의 종목 배지는 20개까지만 나열하고 나머지를 「외 N개」로 접는다.
  `POST /symbols` 가 `{code}` 대신 `{codes: []}` 를 받고 `{added, skipped}` 로 답한다.
- **이유:** D-034 가 종목을 1급 객체로 만들면서 화면은 "정렬·필터 UI 는 나중" 으로 남겼다.
  그 나중이 지금이다 — 200종목 목록에서 하나를 찾는 유일한 방법이 스크롤이었고, 등록은
  한 번에 하나여서 200종목을 넣으려면 다이얼로그를 200번 열어야 했다.
- **단건 등록 경로를 따로 두지 않았다:** 단건은 길이 1 목록이다. 라우트를 둘로 나누면
  이름 조회·시장 검증·감사 기록이 두 곳에 생기고 한쪽만 고쳐진다. 이름 조회도 목록으로
  한 번에 묻는다 — 종목마다 부르면 100종목 등록이 외부 호출 100번이 된다.
- **일괄 등록은 부분 성공을 인정한다:** 20종목 중 3종목이 이미 있을 때 전체를 되돌리면
  사용자가 목록에서 그 3개를 손으로 지우고 다시 붙여야 한다. 대신 `skipped` 에 코드와
  이유를 실어 화면이 그대로 말한다. **하나도 못 넣었으면 201 이 아니라 409** 다 — 빈
  성공을 돌려주면 화면이 "추가했습니다" 를 띄우고 목록은 그대로인 상태가 된다.
  형식 위반은 반대로 **요청 전체를 400 으로 거부한다**: 화면이 보내기 전에 걸러 내므로
  여기까지 오면 계약 위반이고, 절반만 통과시키면 무엇이 들어갔는지가 모호해진다.
- **선택은 전체 목록 기준으로 뽑는다:** 보이는 페이지에서만 뽑으면 2페이지에서 고른
  종목이 1페이지로 넘어간 순간 동기화·제거 대상에서 조용히 빠진다 — 「12개 선택」을
  보면서 3개만 수집되는 것을 뒤늦게 알게 된다. 검색을 바꿔도 선택은 남는다.
- **전체 선택 대상은 검색 결과다:** 검색으로 좁힌 뒤 전체 선택이 목록 전체를 담으면
  검색이 무의미해진다. 대신 검색 중일 때 라벨에 「검색 결과 N종목 선택」이라고 적는다 —
  「전체 선택」이 200종목을 담을 것처럼 보이는데 12종목만 담기면 그것도 거짓말이다.
- **코드 형식 정규식을 `src/shared` 로 옮겼다** (`symbol-code.ts`). 화면이 붙여넣은
  목록을 먼저 검증해야 하는데 화면과 라우트가 각자 정규식을 들면 한쪽만 고쳐져 "화면은
  통과시키고 서버가 400" 이 된다. 웹은 `src/server` 를 import 할 수 없어(§7) 공유는
  거기뿐이다. 별칭(`@shared`) 대신 확장자 붙은 상대 경로를 쓰는 이유: 이 모듈의 단위
  테스트는 NodeNext 로, 화면은 bundler 로 타입 검사돼 두 해석 방식에서 같이 풀려야 한다.
- **`parsePageSize` 를 `web/lib` 로 옮겼다** — 거래 내역·경고 목록·종목 목록이 같은
  컨트롤을 쓴다. 탭마다 따로 파싱하면 한쪽만 음수를 막거나 상한이 달라진다.
- **곁들여 고친 버그:** 편집 모드의 하단 고정 동작 바가 모바일에서 하단 탭바
  (`fixed`, z-20) 밑에 깔려 동기화·제거가 **보이는데 눌리지 않았다** — 클릭이 탭바로
  갔다. `sticky bottom-0` 을 탭바 높이만큼(+safe-area) 띄웠다. e2e 의 mobile 프로젝트가
  제거를 실제로 눌러 보게 만들고 나서야 드러났다.
- **이름 변경 404 (D-034 에서 고친 것) 에 회귀 방지를 붙였다:** 원인은 클라이언트가
  PATCH 라우트를 POST 로 부른 것이었고, 타입·단위 테스트가 볼 수 없는 층이다. e2e 가
  이름을 바꾸고 원래대로 되돌린다 — 서버 하나를 mobile·desktop 두 프로젝트가 공유하므로
  (playwright workers:1) 상태를 남기면 두 번째 실행이 실패한다.
- **하지 않은 것:** 서버 검색·정렬 옵션(지금은 클라이언트 필터 + 가나다순 고정),
  한글 초성 검색(자모 분해가 필요하고 서버 검색으로 갈 때 할 일이다), 데이터셋 카드의
  「외 N개」 펼치기(전체 목록은 「종목 편집」에 있다).

## D-036: 데이터셋 편집 화면은 종목 목록과 같은 구성을 **공유**한다 (포함 여부만 정한다)

- **변경 내용:** 데이터셋의 「종목 편집」(과 「데이터셋 만들기」) 이 쓰던 `SymbolPicker` 를
  버리고 `SymbolCheckList` 로 바꿨다. 종목 탭과 **같은 행**(이름·코드 + 슬라이스별 봉 배지
  + 재무 + 마지막 수집 + 참조 데이터셋 수), **같은 검색**, **같은 페이징**을 쓰고 거기에
  왼쪽 체크박스와 「전체 선택」·「페이지내 전체 선택」이 더해진다. 페이지당 기본 10.
  행·검색 상자·표시 수 입력·페이지 이동을 `symbol-list.tsx` 로, 페이지 창 계산을
  `symbol-paging.ts` 로 빼내 두 화면이 같은 코드를 부른다.
- **이유(구성 공유):** 두 화면이 각자 행을 그려서 이미 갈라져 있었다 — 픽커는 보유 봉을
  「일봉·분봉」 문자열로, 종목 탭은 배지로 그렸다. 같은 사실이 두 모양이면 어느 쪽이
  최신인지 알 수 없고, 한쪽에만 재무 배지가 빠진 것도 눈치채기 어렵다.
- **수집 컨트롤은 넣지 않는다:** 동기화 버튼, 수집 봉(일/분봉) 선택, 재무 수집 체크박스가
  없다. 이 화면은 **어떤 종목을 포함할지만** 정한다. 데이터셋에서도 수집을 시작할 수 있으면
  "무엇을 언제 수집했나" 의 답이 두 화면으로 흩어진다 — 수집은 종목 소관이다(D-034).
- **전체 선택과 페이지내 전체 선택을 둘 다 둔다:** 범위가 다르다. 전체 선택은 검색 결과
  전체(1,000종목일 수 있다), 페이지내는 보이는 것만이다. 하나로 합치면 검색 없이 누른
  사용자가 의도보다 훨씬 많이 담거나, 반대로 페이지를 넘겨 가며 100번 눌러야 한다.
  페이지가 하나면 두 버튼이 같은 동작이라 페이지내 버튼을 숨긴다. 범위 밖의 선택은
  건드리지 않는다 — 검색어를 바꿔 가며 고른 것을 새 검색이 지우면 안 된다.
- **페이징이 성능의 전제였다.** 1,000종목 실측: 이전 구현은 등록 종목 **전체**를 한 번에
  그려서 다이얼로그를 여는 데 **1,443ms**(long task 773ms + 480ms), 체크 하나에 126ms 가
  들었다. 페이지당 10이면 **160ms · long task 0**, 체크 토글 33ms 다 (DOM 5,018노드 →
  356노드). 종목 탭이 같은 규모에서 멀쩡했던 이유도 같다 — 20행만 그린다.
- **목록만 안에서 스크롤한다** (`max-h-[55vh]`). 다이얼로그 전체가 스크롤되면 검색·전체
  선택·저장이 화면 밖으로 밀려 나가는데, 그것들이 이 화면에서 가장 자주 쓰는 컨트롤이다.
- **남은 한계:** 검색은 여전히 클라이언트 필터다(D-035 와 동일).

## D-037: 1,000종목 목록의 서버 비용을 종목 수에서 떼어낸다

측정으로 드러난 두 곳을 고쳤다. 둘 다 "종목 하나를 다루는 함수를 N번 부른다" 는 같은 형태다.

- **재무 보유 판정을 집합으로 받는다.** `GET /symbols` 가 종목마다
  `factRepository.hasFacts('SYMBOL', code)` 를 불러 **1,000회 `fs.existsSync`** 를 냈고,
  그 목록은 5초마다 다시 읽힌다. 40ms 요청의 22~30ms 가 여기였다. `symbolsWithFacts(): Set`
  을 포트에 추가해 `scope=SYMBOL` 디렉터리를 **한 번** 훑는다 — 비용이 등록 종목 수가 아니라
  **수집된** 종목 수에 묶이고, 등록만 하고 수집하지 않은 종목은 0원이다.
  결과: **40ms → 5.7ms**.
  단건 `hasFacts` 는 남겼다 — 제출 검증(422)은 선택 종목(≤200)만 보고 조기 종료한다.
  두 경로가 **같은 판정**을 내야 하므로(배지와 게이트가 어긋나면 안 된다, D-033) 통합
  테스트가 두 답의 일치를 직접 확인한다.
- **`getSymbol` 이 목록 전체를 만들지 않는다.** `listSymbols().find(...)` 였고, 등록이
  반환값으로 그것을 부르므로 일괄 등록이 목록을 N번 재구성하는 O(n²) 였다(테이블 4개 ×
  매번 전체 스캔). 코드로 필터한 조회로 바꾸고 행→요약 변환을 `toSummary` 로 공유한다 —
  목록과 단건이 다른 모양을 내지 않게. 결과: **999종목 일괄 등록 1.0초 → 0.48초**.
- **파티션 디렉터리만 보고 판정하지 않는다:** 쓰기가 중간에 죽으면 디렉터리는 남고
  `data.parquet` 은 없을 수 있다. 그 상태를 「재무 있음」으로 세면 배지가 거짓말한다.

## D-038: 종목 정렬(시가총액·거래대금·거래량)과 데이터셋 → 유니버스 도출

설계: `docs/superpowers/specs/2026-08-01-symbol-sort-design.md`

- **변경 내용:** (1) 종목 탭과 데이터셋 「종목 편집」에 정렬(시가총액순·거래대금순·
  거래량순·가나다순)을 넣었다. (2) `GET /symbols/metrics` 가 등록 종목 전체의 지표를
  답한다. (3) 백테스트 위저드에서 **종목 개별 선택 UI 를 없애고**, 데이터셋 카드의
  「편집」이 데이터 화면의 그 데이터셋 편집으로 보낸다. (4) 상한(200종목)을 넘는
  데이터셋은 **백테스트를 돌릴 수 없다** — 2단계 게이트가 막는다.
- **시가총액은 소스가 주지 않아 만든다:** 발행주식수(`/stocks`) × 현재가(`/prices`).
  둘 다 종목을 지정해 물을 수 있어 등록 종목 전부를 덮는다. 하나라도 없으면 null 이다 —
  0 으로 채우면 "시가총액 0원인 종목" 이 되어 정렬 맨 끝에 조용히 박힌다.
- **거래대금·거래량은 시장 상위 100위까지만 알 수 있다.** "이 200종목의 거래대금" 을
  묻는 API 가 없고 랭킹(`/rankings`)만 있다. 랭킹 밖 종목은 **모르는 것**이지 0 이
  아니다 — null 로 남기고 화면이 「N종목은 집계가 없어 뒤에 가나다순으로 놓인다」고
  적는다. 0 으로 채우면 거래 없는 종목과 순위에 못 든 종목이 같은 칸에 놓인다.
  랭킹은 거래대금 상위와 거래량 상위를 **둘 다 받아 합친다**: 서로 다른 100종목이고 두
  응답 모두 두 값을 함께 싣는다. `duration` 은 `1d` 다 — `realtime` 은 장 초반에 거의
  0 이라 그 시간대의 「거래대금순」이 사실상 무작위가 된다.
- **지표 조회 실패는 200 + null 이다.** 자격 증명 미설정으로 종목 화면이 막히면 안 된다 —
  가나다순으로는 멀쩡히 쓸 수 있다 (`SymbolInfoService` 가 이름에 대해 하는 것과 같다).
  대신 규모 정렬 항목을 **잠그고 이유를 상시 표시한다**: 누를 수 있게 두면 골랐는데
  순서가 그대로인 상태가 되고 사용자는 정렬이 고장 났다고 읽는다 (D-027 과 같은 방향).
- **값이 없는 종목은 항상 뒤로, 동률은 가나다순으로 떨어진다.** 랭킹 밖 900종목이 매
  렌더 다른 순서로 보이면 목록이 아니라 셔플이다 — 완전순서를 만든다.
- **백테스트를 만들면서 종목을 골라내는 것 자체가 잘못된 프로세스다.** 위저드 2단계는
  데이터셋만 고르고(해제는 없다 — 다른 데이터셋으로 바꾸는 것만 된다) 유니버스는
  데이터셋이 정한다. 종목을 골라내게 두면 같은 데이터셋으로 돌린 두 결과가 서로 다른
  유니버스를 갖고, 무엇이 달랐는지는 저장된 요청을 펼쳐 봐야만 안다. 유니버스를 바꾸려면
  데이터셋을 바꾼다 — 그러면 그 사실이 데이터 화면에 남고 다음 실행도 같은 것을 쓴다.
  참조를 바꾸는 화면이 둘이던 문제도 같이 없어진다. 딥링크(`?tab=datasets&edit=<id>`)는
  **한 번 쓰고 쿼리에서 지운다**: 남기면 새로고침이 닫은 다이얼로그를 되연다.
- **상한 초과는 자르지 않고 막는다.** 알아서 상위 200종목만 담는 것은 위저드가 종목을
  골라내는 것과 같은 일이고, 기준(시가총액순/거래대금순)에 따라 담기는 종목이 달라져
  "이 데이터셋으로 돌렸다" 가 더는 실행을 특정하지 못한다. 앞에서 200개를 자르는 것은
  더 나쁘다 — 그 200개는 가나다순 앞자리일 뿐이다. 막는 자리는 `stepBlocker(1, …)` 로,
  데이터셋을 고르는 그 자리에서 이유가 뜬다. 상한 초과는 카드에도 적어 **고르기 전에**
  보이게 한다.
- **상한 상수를 `src/shared/schemas/universe-limit.ts` 로 뺐다.** 화면이 자기 숫자를
  들면 상한을 올릴 때 한쪽만 고쳐지고 그 어긋남은 제출 400 으로만 드러난다. 요청 스키마도
  같은 상수를 쓰고, 단위 테스트가 게이트 경계와 스키마 경계가 같은지 직접 확인한다.
  상수만 따로 담는 이유는 zod 를 웹 번들에 끌고 오지 않기 위해서다.
- **복제(clone)는 원본 유니버스를 그대로 되살린다.** 예전 화면에서 부분 선택으로 만든
  잡을 복제하면서 데이터셋 전체로 넓히면 「재실행」이 재실행이 아니게 된다. 데이터셋을
  다시 고르면 그때 그 데이터셋의 종목 전체를 쓴다.
- **지표는 어디에도 저장하지 않는다.** 종목 동기화(봉·재무)와 무관하고, 화면을 열 때만
  호출이 나가 프로세스 메모리에만 캐시된다. 시가총액·거래대금은 "지금" 값이라 과거 시점
  재현이 안 되므로 백테스트 입력이 되면 look-ahead bias 다 — 봉·재무처럼 parquet 에
  남기지 않는 이유가 그것이다.
- **하지 않은 것:** 로컬 저장 봉으로 랭킹 밖 거래대금 채우기(랭킹은 오늘 값이고 마지막
  저장 봉은 몇 주 전일 수 있다 — 한 열에 섞으면 순서가 뜻을 잃는다), 서버 정렬(D-035 와
  같은 한계), 오름차순 토글.

## D-039: 백테스트 설명은 데이터셋을 가리키고, 거래 내역은 서버가 정렬한다

- **변경 내용:** (1) 백테스트 목록 카드와 상세 화면의 설명 줄이 종목을 나열하지 않고
  **데이터셋 이름 + 종목 수**를 적는다. (2) 거래 내역의 수량·진입·청산·순손익·수익률·
  보유 여섯 열이 머리글 버튼이 되어 오름/내림 두 방향으로 정렬된다. 정렬은 서버가 한다.
- **설명이 가리켜야 하는 것은 데이터셋이다.** 백테스트는 종목을 고르지 않고 데이터셋을
  고른다 (D-038). 200종목 중 앞 5개를 적던 표기는 나머지 195개를 감추면서 그 5개가 왜
  앞에 왔는지도(코드순일 뿐이다) 알려주지 않았다. 종목 전체는 결과 화면의 거래 내역
  종목 필터와 종목별 성과 표에 있다.
- **종목 수는 실행된 요청에서 센다.** 데이터셋의 **현재** 종목 수가 아니다. 실행 뒤
  데이터셋에 종목이 더해지면 그 카드가 돌지도 않은 종목까지 센 셈이 된다. 반대로 이름은
  현재 카탈로그에서 찾는다 — 실행이 기록한 것은 id 뿐이고, 실행을 특정하는 그 id 는
  재현 정보 카드에 그대로 남는다. 데이터셋을 지우면 이름을 찾을 수 없어 id 를 적는다.
- **정렬을 서버로 보낸 이유:** 거래 내역은 서버 페이징이다. 화면에서 정렬하면 보이는
  10건만 뒤집혀 「순손익 1위」가 「이 페이지의 1위」가 된다. 정렬을 바꾸면 1페이지로
  돌아간다 — 3페이지에 남아 있으면 방금 고른 상위 거래를 건너뛴 채 21번째부터 본다.
- **`id` 로 한 번 더 정렬한다.** 수량·보유기간·청산시각은 동률이 흔하고, 동률의 순서가
  정해지지 않으면 SQLite 의 LIMIT/OFFSET 이 페이지 경계에서 같은 거래를 두 번 주거나
  빠뜨린다. 통합 테스트가 페이지를 이어 붙인 것과 한 번에 받은 것이 같은지 확인한다.
  기본 정렬(청산 오름차순)은 정렬 파라미터가 없던 시절 그대로다 — 바꾸면 저장된 링크가
  가리키는 순서가 달라지고 그 차이는 어디에도 적혀 있지 않다.
- **축 문자열을 `src/shared/schemas/trade-sort.ts` 로 뺐다.** 화면과 라우트가 각자 들면
  한쪽만 이름을 바꿨을 때 그 어긋남이 조회 400 으로만 드러난다 (`universe-limit.ts` 와
  같은 이유). 모르는 축은 조용히 기본 정렬로 떨어지지 않고 400 이다 — 떨어뜨리면 화면은
  「순손익순」을 표시한 채 청산순 목록을 보여 준다. e2e 가 머리글을 실제로 눌러 거래가
  그대로 보이는지 확인한다: 그 층은 타입·단위 테스트가 볼 수 없다.
- **축마다 첫 방향이 다르다.** 「수량」을 누르는 사람이 보려는 것은 큰 거래고 「진입」을
  누르는 사람이 보려는 것은 처음 거래다 (규모 정렬이 내림차순인 것과 같은 이유, D-038).
  전부 오름차순으로 시작하면 두 번 눌러야 하는 열이 생긴다.
- **종목·사유 열은 정렬 축이 아니다.** 종목은 위 필터가 맡고, 사유는 코드 문자열 순서가
  사람에게 뜻이 없다. 누를 수 있게 두면 골랐는데 순서가 그대로인 상태가 된다 (D-027).
- **미청산 행은 첫 페이지 맨 위에 고정하되 같은 축으로 함께 정렬한다.** 이 행들은 서버
  페이징 밖(재현 정보의 스냅샷)이라 청산 거래와 한 줄로 섞을 수 없다. 그대로 두면
  「순손익 높은 순」인데 맨 위 몇 줄만 아무 순서인 표가 되므로 화면에서 정렬하고, 섞이지
  않는다는 사실을 표 아래에 적는다. 순손익 축은 평가 손익으로 줄을 세운다 — 열에 보이는
  값과 같다. 청산 시각이 없는 축에서는 전부 동률이라 심볼 순으로 떨어진다.
- **이름은 버튼 글자 그대로 두고 상태는 `aria-sort` 가 알린다.** `aria-label` 로 덮으면
  스크린리더가 열 이름을 잃는다. 누르면 어떻게 될지는 `title` 에 적는다.
- **하지 않은 것:** 정렬 상태를 URL 에 남기기(새로고침하면 기본으로 돌아간다), export
  의 정렬(재현을 위해 청산순 고정), 축마다 인덱스 추가(정렬 대상이 한 작업의 거래로
  한정돼 쓰기 비용만 늘린다).

## D-040: 과거 시점 고정 유니버스 — 소유자를 데이터셋이 아니라 실행으로 바꾼다 (REVIEW §7 데이터셋 결합안 대체)

- **변경 내용:** [HISTORICAL_UNIVERSE_SNAPSHOT_REVIEW.md](./reviews/HISTORICAL_UNIVERSE_SNAPSHOT_REVIEW.md)
  §7 원안은 선정 출처(provenance)와 선정 스냅샷을 **데이터셋**에 붙이는 구조였다.
  사용자 결정(2026-08-03)으로 이를 바꿔, `universe_snapshots`·`universe_snapshot_symbols`
  를 데이터셋과 무관한 독립 엔티티로 두고 `backtest_jobs.universeSnapshotId`가 실행
  시점에 직접 참조한다. 데이터셋은 여전히 D-034 그대로 "참조 집합"일 뿐이며, 과거
  유니버스 기능이 그 원칙에 예외를 만들지 않는다.
- **소유자를 바꾼 이유:** 원안대로 데이터셋에 provenance 를 붙이면 같은 스냅샷을 여러
  백테스트가 재사용하는 동안 그 데이터셋이 수동 편집될 수 있어, §7.3 의 "수동 수정
  이력" 상태 기계(원본 유지·플래그·감사 기록·복원 후에도 이력 유지)가 통째로
  필요해진다. 스냅샷을 실행에 직접 물리면 스냅샷 자체가 **저장 후 불변**이라 그
  상태 기계가 필요 없다 — REVIEW §14 완료 판정 표의 "(v2) 수동 편집 이력 표시" 행이
  "해당 없음, 수정 = 새 스냅샷"으로 끝나는 이유가 이것이다. 구성을 바꾸고 싶으면
  미리보기를 다시 조회해 새 스냅샷을 만든다 — 있는 스냅샷을 고치지 않는다.
- **불변 스냅샷과 값 스냅샷을 나눴다:** `universe_snapshots`(요청일·적용일·usable
  from·필터 정책 버전·계약 버전·정렬 기준·선정 방식과 해시)는 수정 컬럼이 없다.
  `universe_snapshot_symbols`(당시 표준·단축코드, 이름, 시장, 시가총액, 순위)는
  `symbols`에 FK 를 걸지 않는다 — `backtest_trades.symbol`이 종목 삭제 후에도 문자열로
  남는 것과 같은 이유로, 종목을 지운 뒤에도 실행 근거를 값으로 설명해야 한다
  (REVIEW §7.2).
- **서버 소유 pin 으로 실행을 자립시켰다:** `backtest_jobs.universeSnapshotId`와
  `provenancePinJson`은 클라이언트가 보내는 필드가 아니라 잡 생성 트랜잭션에서 서버가
  채운다. `datasetId`처럼 FK 를 걸지 않는 것도 같은 이유다 — 데이터셋·스냅샷이 나중에
  지워지거나 편집돼도 실행 기록이 그 시점에 무엇을 소비했는지 값으로 답해야 한다
  (REVIEW §9.2, §14 "종목/스냅샷 삭제 후에도 값으로 남는 실행 근거").
- **부분 유니버스 pin 버그를 이 작업 중에 제거했다:** 기존
  `DatasetService.universeSnapshot(datasetId, slice)`는 요청이 부분집합
  (`body.universe.symbols`)이어도 **데이터셋 전체 종목**을 버전 스냅샷에 담았다 —
  레거시 복제나 직접 API 요청에서는 실제 소비 종목과 pin 된 버전 해시가 어긋날 수
  있는 상태였다(REVIEW 2장 마지막 문단). `universeSnapshotFor(codes, slice)`로 나눠
  `backtest-routes.ts`가 실제 요청 종목만 넘기게 고쳤다(커밋 455c45f) — 과거 유니버스
  pin 을 만들면서 같은 부류의 버그를 새로 심지 않으려면 기존 버그부터 없애야 했다.
- **필터 정책에 버전을 부여했다:** `KRX_FILTER_POLICY_VERSION`(`krx-common-stock-v1`)을
  `universe_snapshots.filterPolicyVersion`에 저장한다. KRX 분류값이나 정책이 나중에
  바뀌어도 과거에 만든 스냅샷이 어떤 규칙으로 골랐는지 그 스냅샷 자체가 설명한다.
  분류가 정책에 없는 값을 만나면 조용히 제외하지 않고 `UnknownKrxClassificationError`
  로 스냅샷 생성 전체를 막는다(REVIEW §4.1) — 이 예외를 잡아 미지값을 나열하는 것이
  `scripts/krx-smoke.ts`(Task 16)의 역할이다.
- **남은 외부 게이트:** 코드·마이그레이션·화면은 이번 작업(Task 1~16)으로 끝났지만
  REVIEW §12 재개 조건 중 세 가지는 아직 사람이 확인해야 한다 — API별 이용 승인
  완료 확인(§12-2), `scripts/krx-smoke.ts`의 실응답 실행·조인·분류 검증(§12-4),
  비상업 약관 범위·로컬 저장·재사용·만료 후 처리 확인(§12-5·6). 통과 전에는 과거
  유니버스 모드를 실서비스 사용자에게 노출하지 않는다.

## D-041: 가격 데이터 기능 제거 — 봉은 KRX 일봉 하나로 좁힌다

- **번호 참고:** 계획 브리프는 이 결정을 D-032 로 적었다. 하지만 계획이 끝나기
  전 다른 작업이 D-032~D-040 을 먼저 채웠다. 번호 충돌을 피해 다음 빈
  번호(D-041)로 옮겨 적는다. 본문은 브리프가 준 내용 그대로다.
- **변경 내용:** 가격 데이터 화면·CSV 가져오기·증권사 봉 수집을 제거하고, 백테스트가
  소비하는 봉을 `krx_daily_bars`(SQLite) 일봉으로 확정했다. `Timeframe` 은 `'1d'` 만
  남고 슬라이스 축(`DatasetSlice`)이 사라졌다.
- **이유:** 1m·1h 는 증권사만 주는데 증권사는 상장폐지 종목의 과거 봉을 주지 않는다.
  생존편향을 없앤 백테스트를 1m·1h 로는 만들 수 없으므로, 그 timeframe 을 남기면
  "일봉은 편향 없고 분봉은 편향 있는" 상태가 조용히 남는다.
- **가격 조회 기능을 뺀 이유:** 사람이 가격을 확인하는 일은 증권사 화면이 더 잘한다.
  이 애플리케이션에서 가격은 백테스트 전략의 입력이지 열람 대상이 아니다.
- **증권사 어댑터는 종목 이름 조회만 남겼다:** `MarketDataSource`(봉 조회)의 소비자가
  사라졌다. 매매 시스템은 나중에 자기 형태의 포트를 새로 갖는다 — 지금 형태를 남기면
  쓰이지 않는 채 낡는다. 다만 같은 어댑터가 구현하던 `StockInfoSource` 는 백테스트
  위저드·상세 화면의 종목 이름 표시가 계속 쓰므로 남겼다.
- **시총·거래대금 정렬도 함께 제거:** `GET /symbols/metrics` 는 증권사 현재가로 계산해
  가격 데이터 화면에서만 썼다. 화면이 사라지면 소비자가 없다. 백테스트 유니버스의 시총
  순위는 KRX 이력(`symbol_master_market_caps`)을 쓰므로 영향이 없다.
- **DART 재무 수집은 CLI 전용이 됐다:** 웹에서 촉발하던 경로는 증권사 동기화 잡의
  `factsPhase` 였고 그 잡이 사라졌다. `pnpm cli facts:sync` 가 같은 유스케이스를 그대로
  부른다 — 기능이 없어진 것이 아니라 진입점이 하나로 줄었다.
- **영향:** `symbol_slices`·`symbol_coverage`·`data_sync_jobs` 가 쓰이지 않게 됐다.
  실제 스키마 정리와 parquet·DuckDB 제거는 후속 계획에서 한다.

## D-042: 백테스트 취소가 실행 도중에도 걸리게 한다 — 동기 루프에 양보 지점을 심는다

- **증상:** 자식 프로세스 실행 중 취소 요청을 보내면 계산이 끝날 때까지
  반영되지 않았다. 이 취소 계약은 `tests/integration/job-queue.test.ts`가
  검증해야 했다. 하지만 그 파일의 `beforeEach`가 이미 삭제된
  `symbolService.importCsv`를 불렀다. 그래서 24개 테스트 전부가 런타임
  TypeError 로 실행조차 되지 않고 있었다. Task 7 이 그 `beforeEach`를
  고치자 이 취소 레이스가 처음으로 드러났다.
- **근본 원인:** 자식 프로세스의 백테스트 실행은 better-sqlite3 기반이라
  전부 동기다. 동기 코드는 이벤트 루프에 양보하지 않는다. 그래서 IPC 로 온
  취소 메시지를 처리할 매크로태스크 경계가 계산 도중에 아예 없었다.
  `shouldCancel()` 폴링 자체는 정상이었다. 폴링할 틈 자체가 없었을 뿐이다.
- **왜 이제야 드러났나:** 위 `beforeEach` 결함 때문에 이 취소 계약을 검증하는
  테스트가 한 번도 실행된 적이 없었다. 커밋 이력이 있다
  (`9bfba70 test: stabilize active job cancellation contract`). 그 커밋을
  보면 과거에도 이 레이스를 잡으려 한 시도가 있었다. 다만 "자식이 계산을
  끝내기 전에 취소가 반드시 도착한다"는 가정 자체가 이미 깨져 있었다.
- **수정:** 엔진 루프 본체(`runBacktestSteps`, `engine.ts`)를 제너레이터로
  뽑았다. 기존 통계·주문·체결 로직은 손대지 않고 그대로 옮겼다. 반복마다
  `yield` 하나만 더했다. 두 얇은 드라이버가 이 제너레이터를 소진한다.
  기존 `runBacktest`(동기)는 그 `yield`를 그냥 흘려보낸다. 신규
  `runBacktestCancellable`(비동기, 자식 프로세스 전용)이 대신 양보한다.
  200봉마다 `await new Promise((resolve) => setImmediate(resolve))`를
  한 번 기다린다. 이 양보가 IPC 취소 메시지를 처리할 매크로태스크
  경계를 만든다.
- **양보 간격 200 을 고른 근거:** 로컬 측정(`range-breakout` 전략, 10만 봉,
  500회 양보) 기준으로 동기 실행과 차이가 잡음 수준(수십 ms)이었다. 대형
  백테스트에는 실질 오버헤드가 없다는 뜻이다. 200봉 미만인 실행(흔한 소규모
  백테스트)은 양보가 한 번도 걸리지 않는다. 그런 실행은 애초에 몇 ms 안에
  끝나 취소할 틈이 원래 없었으므로 손해가 아니다.
- **동기 경로(`runBacktest`)를 건드리지 않은 이유:** 이 경로는 취소 대상이
  아니다. 자식 프로세스 밖(동기 백테스트를 직접 호출하는 테스트·스크립트)
  에서 쓰인다. 양보를 넣으면 없던 비동기 경계가 생겨 호출부 가정을 깰 수
  있다. 제너레이터로 감싼 뒤 두 드라이버로 나눈 설계 자체가 "로직은 하나,
  양보 여부만 갈린다"를 보장한다. 동기 경로의 동작은 리팩터 전후로 문자
  그대로 같다.

## D-043: 자본변동 포지션 연속성 — 계산 시점 조정과 커버리지 게이트

- **증상:** 백테스트 엔진이 액면분할을 넘는 보유 포지션을 조정하지 않았다.
  대기 주문 수량도, 전략이 들고 있는 가격 상태(`stopLevel`·`highestClose`·
  `entryAtr`)도 마찬가지였다. 분할일에 종가가 5분의 1로 떨어지면 평가금액도
  같이 떨어졌다. 에러도 경고도 없이 결과만 조용히 틀렸다.
- **결정 — 원본 봉은 그대로 두고 계산 시점에 반영한다:** 수정주가를 만들어
  덮어쓰는 방식은 택하지 않았다. 대신 엔진이 각 봉 시각에 해당 종목의
  자본변동을 확인해 포지션·대기 주문·전략 가격 상태를 조정한다.
  원본을 고치면 체결가가 합성값이 된다. 분할 이력이 늘 때마다 과거 전체를
  다시 써야 하는 부담도 생긴다. 스펙 §11 의 "원본은 수정하지 않음"
  원칙과도 맞는다.
- **거래정지 구간 처리:** KRX 는 주권교체 기간에 매매를 정지한다. 그 구간에
  빠진 봉의 이벤트는 재개 봉에서 따라잡는다. 이것이 표준 경로다.
- **결정 — 게이트는 커버리지로만 막고 gap 은 경고만 한다:** 유니버스 종목이
  자본변동을 한 번도 수집하지 않았으면 제출을 400 으로 막는다. 수집은
  했지만 DART 가 답하지 못해 gap 이 난 종목은 막지 않고 이름으로 경고한다.
- **이유:** DART 가 못 답하는 종목은 대체로 상장폐지 종목이다. gap 까지
  요구하면 그 종목들이 영원히 막힌다. 생존편향을 없애려고 폐지 종목을
  들여온 것이 이 프로젝트의 출발점이다(D-041). 확실히 아는 것만 통과시키려다
  폐지 종목을 배제하는 쪽이 손실이 더 크다.
- **결정 — 봉 쓰기를 `onConflictDoNothing` 으로 바꾼다:** 기존 upsert 는
  실제로는 도달하지 않았다. `ingestDate` 호출부가 모두 커버리지 게이트를
  지나고, 봉 쓰기와 커버리지 갱신이 같은 트랜잭션이기 때문이다. 그런데
  코드는 덮어쓸 수 있다고 말해 읽는 사람이 봉이 바뀔 수 있다고 오해했다.
  `onConflictDoNothing` 은 "이미 있으면 건드리지 않는다"를 코드에 그대로
  드러낸다.
- **결정 — 지표 누적 상태도 같은 자리에서 조정한다:** `HoldingState` 의 가격
  필드만 고쳐서는 부족했다. 같은 종목 상태가 `EmaState`·`AtrState`·`RsiState`·
  전고점 창·상관 워밍업 종가도 함께 들고 있다. 전부 원본 종가를 먹는다.
  조정하지 않으면 5대 1 분할 봉에서 세 전략이 각자 다르게 틀어진다.
  `ema-trend-switch` 는 두 EMA 간격이 음수가 되어 `TREND_END` 로 허위
  청산한다. `rsi-reversion` 은 −80% 한 봉을 과매도로 읽어 허위 진입한다.
  `range-breakout` 은 기준선이 분할 전 고가에 남아 돌파 진입이
  `lookbackBars` 동안 막힌다. 그래서 `onCorporateAction` 이 가격 단위인
  누적값을 전부 같은 비율로 내린다. RSI 값처럼 그 자체가 비율인 값은 그대로
  둔다. 대신 그 값을 만드는 내부 누적(평균 상승·하락 폭)을 내린다.
- **결정 — 전략 상태 훅은 보유 여부와 무관하게 부른다:** 포지션·대기 주문
  조정은 그 둘이 있는 종목에만 건다. 전략 상태 훅은 봉이 있는 모든 종목에
  건다. 허위 **진입** 신호는 정의상 보유하지 않는 종목에서 나기 때문이다.
  보유 종목으로 좁히면 위 세 증상 중 둘이 그대로 남는다.
- **영향:** `symbol_facts_state` 에 자본변동 전용 커버리지·gap 연도 컬럼을
  각각 추가했다. 재무 커버리지(`coveredYearsJson`)와 분리해, 자본변동만
  받은 종목을 재무 전략이 "데이터 있음"으로 오판하지 않게 했다. 자본변동만
  받는 수집 경로도 새로 냈다. 재무(`fnlttSinglAcntAll`·`irdsSttus`)는
  캐시가 없어 다시 부르면 비용이 크다. 자본변동(`stockTotqySttus`)은
  `shareRowsCache` 로 캐시된다.
- **배포 — 기존 종목의 자본변동 커버리지는 마이그레이션으로 채운다:**
  이 브랜치 전에는 `FactSyncService.sync()` 가 재무와 자본변동을 항상 함께
  받았다. 결과는 `covered_years_json` 한 곳에만 적었다. 그래서 그 시절의
  재무 커버리지가 곧 자본변동 커버리지다. `0010_action_coverage_backfill.sql`
  이 `action_covered_years_json` 이 `NULL` 인 행을 그 값으로 채운다. 채우지
  않으면 배포 첫날 모든 제출이 이 게이트에 걸려 400 이 된다. 위저드도 이미
  있는 데이터를 다시 받으러 DART 를 수천 번 때린다.
- **알려진 한계 — 백필된 종목은 gap 경고 없이 통과한다:** gap 연도는 채울
  수 없다. 그 시절에는 실패 연도를 담을 컬럼 자체가 없었다. 그래서 백필로
  커버리지를 얻은 종목은 "수집했고 분할이 없었다" 와 "gap 이 나서 확인하지
  못했다" 를 구분하지 못한다. 위 세 상태 중 (1) 과 (2) 를 가르는 신호가 그
  종목들에는 없다. 다시 수집하면 그때부터 gap 이 기록된다.
- **알려진 한계 — 종목을 뺐다 다시 넣으면 커버리지가 함께 사라진다:**
  `symbolFactsState.code` 는 `symbols.code` 를 외래키로 두고
  `onDelete: 'cascade'` 를 건다(`schema.ts`). `SymbolService.removeSymbols`
  는 `symbols` 행을 실제로 지운다. 그래서 종목을 뺐다가 같은 코드로 다시
  등록하면 재무·자본변동 커버리지가 모두 함께 사라진다.
  사용자가 겪는 일: 재등록 이후 그 종목이 들어간 모든 제출이 이 게이트에
  걸려 400 이 된다. 자본변동을 다시 수집하기 전까지 계속 막힌다.
  이 함정은 D-043 자신의 근거를 정면으로 건드린다.
  gap 을 막지 않는 이유는 상장폐지 종목을 영원히 막지 않으려는 것이다
  (D-041). 상장폐지 종목을 뺐다 다시 넣는 것이 정확히 이 `cascade` 에
  걸리는 경우다.
  이 태스크(Task 10, 문서·주석 정리)의 범위 밖이라 코드는 고치지 않았다.
  후속 과제로 남긴다 — 후보는 재등록 시 커버리지 재확인을 강제하거나,
  `symbol_facts_state` 를 `symbols` 삭제와 독립된 생명주기로 바꾸는 것이다.
- **알려진 한계 — e2e 는 이 게이트의 HTTP·화면 통합을 검증하지 않는다:**
  `scripts/e2e-server.ts` 의 `seedCorporateActionCoverageOnRegistration` 은
  등록되는 모든 종목에 커버리지를 무조건 심는다. `tests/e2e` 어디에도
  400 차단 경로나 Task 8 게이트 화면을 밟는 시나리오가 없다.
  DART 응답 파싱이 e2e 로 덮이지 않는다는 것과는 다른 공백이다.
  게이트 자체의 라우트·화면 연결이 e2e 커버리지 0 이라는 뜻이다.
  이번 태스크에서 e2e 시나리오를 새로 만들지는 않았다.
  필요 여부는 후속 리뷰가 판단한다.

## D-044: 알림 항목 설명은 제출 경고를 지고 지표는 수익률만 담는다

- **결정 — 제출 경고를 `backtest_jobs.submit_warnings_json` 에 저장한다:**
  `POST /backtests`·clone 응답의 `warnings[]` 는 화면 토스트 10초가 유일한
  수명이었다. 자본변동 gap 경고가 사라지면 "수집했고 분할이 없었다" 와
  "gap 이 나서 확인하지 못했다" 가 같아 보인다 (D-043 이 백필 종목에서
  겪는 것과 같은 구분 실패다). 경고가 없으면 `null` 이다 — 빈 배열을 넣으면
  "경고가 없었다" 와 "이 컬럼이 생기기 전 job" 이 같아 보인다.
  복제 경로는 응답과 저장이 같은 합집합(`rebased.warnings` +
  `validated.warnings`)을 쓴다. 한쪽만 고치면 화면과 기록이 갈라진다.
- **결정 — 알림 설명에 넣는 지표는 수익률뿐이다:** 알림 목록의 접힌 행은
  `truncate` 로 한 줄만 보인다. 지표를 늘리면 그 한 줄에서 정작 전략 이름이
  잘린다. CAGR·MDD·Sharpe 는 상세 화면 지표 카드의 몫이다.
  완료인데 수익률을 못 읽으면 이름만 남긴다 — `수익률 -` 은 "0에 가깝다" 로
  읽힌다.
- **결정 — 설명의 전략 표기는 레지스트리의 한국어 이름이다:** 전략은 이미
  `name` 에 한국어 이름을 갖고 `GET /strategies` 가 그걸 준다. 대시보드도
  같은 이름을 쓴다. 등록이 풀린 전략은 `strategyId` 로 떨어진다 — 빈칸이면
  무슨 전략이었는지 알 수 없다.
- **결정 — 토스트 좌우 스와이프 닫기는 하지 않는다:** sonner 가
  `position="top-center"` 에서 위로 밀기를 이미 지원한다. 닫는 수단이 이미
  있어 방향을 더할 이유가 없다.
- **알려진 한계 — 지난 job 의 제출 경고는 백필할 수 없다:** 이 변경 전
  job 은 `submit_warnings_json` 이 `null` 이다. 제출 시점 경고는 응답에만
  있었고 어디에도 저장되지 않았다. 원본이 없어 채울 수 없다. 지난 결과의
  알림 설명에는 전략 이름과 수익률만 남는다.

## D-045: 종목 마스터의 정본은 종목별 SCD Type 2 버전이다

- **결정 — 날짜별 full universe는 입력이고 저장 단위는 상태 버전이다:**
  `standardCode`별 `[validFromDate, validToDate)` 행에 전체 상태를 저장한다.
  신규상장·폐지·시장·주식 수·이름·유형·단축코드·상장일 변화가 있을 때만
  버전을 추가한다. 같은 날 여러 필드가 바뀌어도 버전은 한 행이다.
- **이유 — 체크포인트가 과거 확장에서 스냅샷으로 폭증할 수 있었다:** 기존 시작점보다
  하루 앞을 반복 수집하면 매번 비교할 과거 coverage가 없어 full checkpoint가 생길 수
  있었다. SCD overlay는 `[D, 다음 관측일)`만 바꾸고 인접 동일 상태를 합치므로 시작점을
  반복해서 당겨도 행 수가 늘지 않는다.
- **결정 — coverage와 거래일은 버전에서 추론하지 않는다:** 상태가 안 바뀐 수집일과
  미수집 갭 모두 버전 행이 없으므로 `symbol_master_coverage`와
  `symbol_master_trading_days`를 유지한다. 같은 연속 coverage 안에 앞선 거래일 anchor가
  없는 고립 휴장일은 다른 구간의 열린 버전을 끌어오지 않는다.
- **결정 — 변경 이벤트는 SCD 경계에서 파생한다:** 이벤트 테이블은 더 이상 정본이 아니다.
  API는 안정적인 `date:standardCode:eventType` ID로 필드별 변경 이력을 만든다. 최초
  baseline은 신규상장으로 표시하지 않는다.
- **결정 — 체크포인트 내부 상태는 사용자에게 보이지 않는다:** coverage API와 종목
  마스터 화면에서 체크포인트·검증·불일치 마커를 제거한다. 사용자는 수집 여부와 실제
  종목 상태만 본다.
- **이행 — 검증 후 legacy 중복 행을 비운다:** 0012 이후 첫 부팅이 기존 조회 의미를
  SCD로 압축하고 모든 경계일 상태 지문을 비교한다. 성공한 같은 트랜잭션 안에서 legacy
  checkpoint/event 행을 비우고 `ACTIVE`로 전환한다. 실패하면 `PENDING`으로 롤백된다.
- **롤백:** 이행 후 코드만 구버전으로 되돌리는 것은 지원하지 않는다. 배포 전 DB
  snapshot도 함께 복원해야 한다.

## D-046: 상장폐지는 마지막 거래 가능 봉 종가로 청산하고, 거래불가일은 별도 테이블에 기록한다

- **증상 — `isValidCandle` 이 거래불가일을 파싱 버그로 오분류하고 있었다:**
  KRX 실응답을 실측하니(`docs/superpowers/specs/2026-08-08-delisting-and-non-trading-days-design.md`
  "KRX 실응답 실측") 거래불가 행의 시·고·저는 `null` 이 아니라 문자열 `"0"`
  이었다. 종가는 직전 종가를 그대로 유지하고 거래량도 0 이다.
  `writeDailyBars` 의 null 분기는 타지 않고 `isValidCandle` 의 `value <= 0`
  검사에 걸려 `invalidCount` 로 버려지고 있었다. 그 통은 원래 `high < low`
  같은 진짜 파싱 버그를 담으려던 것인데, 정상적인 거래불가일이 대량으로
  섞여 들어가고 있었다. KOSDAQ 은 하루 4~6% 종목이 이 모양이었다.
- **결정 — 거래정지와 무거래를 나누지 않는다:** KRX 응답이 둘을 구분해
  주지 않는다. 저유동성 종목의 무거래일과 실제 거래정지 종목이 완전히
  같은 모양(시·고·저 0, 종가 유지, 거래량 0)으로 나온다. 체결 관점에서도
  둘은 같은 사건이다 — 어느 쪽이든 그날은 살 수도 팔 수도 없다. 사유를
  구분하려면 KIND 매매거래정지 공시 수집이 별도로 필요하고, 이번 작업
  범위 밖이다.
- **결정 — 봉 테이블에 flat 봉을 채우지 않고 `krx_non_trading_days` 를
  따로 둔다:** `O=H=L=C` 인 봉을 만들어 채우면 KRX 가 주지 않은 시·고·저를
  우리가 지어내는 셈이 된다. 값을 봉 테이블에 섞으면 청산 코드가 실수로
  그 값을 체결 가능 가격으로 오용할 위험도 생긴다. `last_close` 는 평가용일
  뿐 체결 가능 가격이 아니라는 것을 테이블 분리로 코드에 드러낸다.
- **결정 — 청산가는 마지막 거래 가능 봉의 종가다:** KRX 일봉에는 정리매매
  기간 봉이 이미 들어 있어, 마지막 거래 가능 봉이 곧 정리매매 최종가다.
  시장이 이미 매긴 회수가치를 그대로 쓰는 편이 국내 퀀트 도구의 표준
  처리와도 맞는다. `0원(-100%)` 처리는 쓰지 않는다 — 현금합병·자발적
  상장폐지에서 실제보다 훨씬 나쁘게 나온다. CRSP 식 사유별 추정치도 쓰지
  않는다. 종목 마스터에 폐지 사유 자체가 없고, 사유를 넣으려면 KIND
  수집이 선행돼야 한다.
- **결정 — 백필은 `ingestDate` 재실행이 아니라 전용 CLI
  (`krx:backfill-non-trading`)로 뺀다:** `ingestDate` 는 `isCovered` 게이트가
  재수집을 막는 구조다. 그 게이트를 열면 이벤트 재생성 경로가 함께 열려,
  과거분을 채우려다 이벤트·마스터 coverage·봉까지 다시 쓸 위험이 생긴다.
  전용 경로는 `fetchDailyTrades` 만 불러 `krx_non_trading_days` 와
  `krx_non_trading_coverage` 만 채우고 나머지는 건드리지 않는다.
- **영향 — `scheduleHash` 가 바뀌어 엔진 버전을 1.5.0 으로 올렸다:**
  유니버스 규칙이 리밸런스 기준일에 거래불가인 종목을 후보에서 빼므로
  같은 규칙·기간이라도 이전 실행과 다른 유니버스가 나온다. 재현성 요구
  (같은 입력·버전·seed 는 같은 결과, 스펙 §9.5)가 깨지지 않도록 엔진
  버전을 1.4.0 에서 1.5.0 으로 올려 과거 실행과 구분한다. 과거 실행의
  저장된 결과는 그대로 둔다.
- **알려진 한계 — 배당·유상증자 권리락은 여전히 미보정이다:** 이번 작업의
  범위는 상장폐지 청산과 거래불가일 반영뿐이다. "생존 편향" 이라는 단일
  라벨은 쓰지 않는다 — 부분 보정 상태라 예/아니오로 답할 수 없다.

## D-047: 마이그레이션은 서비스 기동 전에 배포가 돌린다

- **증상 — 배포가 롤백을 반복했다:** 2026-08-09 배포에서 서비스는
  `active (running)` 인데 readiness 확인이 실패했다. 로그는 컨테이너 조립 중간
  (`audit log retention active`)에서 멈췄고 그 뒤가 없었다. `CPU 23.9s / 가동 18초`
  로 프로세스는 죽지 않고 계속 일하고 있었다.
- **원인:** 데이터 마이그레이션이 부팅 안에서 돈다. `SymbolMasterService`
  생성자의 SCD 이행(D-045)이 `createContainer` 안에서 실행되는데, 그 자리는
  `app.listen` 보다 앞이다. better-sqlite3 는 동기라 이벤트 루프를 잡고 있어
  포트가 열리지 않는다. 운영 DB 사본으로 재면 이행에 16.5초가 걸렸고
  `wait_for_ready` 창은 10회 × 2초 = 18초였다.
- **왜 재시도로도 안 풀렸나:** 롤백이 DB 스냅샷까지 되돌린다(D-010). 이행은
  한 트랜잭션이라 중간 진행이 쌓이지 않는다. 배포를 몇 번 반복해도 매번
  처음부터 다시 시작해 같은 자리를 맴돌았다.
- **결정 — `cli db:prepare` 를 서비스 기동 전에 돌린다:** 배포가
  `stop` → `db:prepare` → `start` 순으로 나눈다. 서비스를 먼저 멈추는 것은
  DB 를 잡은 프로세스가 없는 창에서 스키마를 바꾸기 위해서다. 서비스와 같은
  `User`·`EnvironmentFile` 로 실행해 DB 파일 소유자가 어긋나지 않게 하고
  비밀값이 command line argument 로 새지 않게 한다.
- **결정 — 명령을 SCD 에 묶지 않는다:** `db:prepare` 가 하는 일은 컨테이너를
  한 번 만들고 닫는 것이다. 스키마 마이그레이션은 `openDatabase` 가, 데이터
  마이그레이션은 각 서비스 생성자가 이미 돌리므로 컨테이너 조립이 둘을 모두
  태운다. 마이그레이션 목록을 명령 안에 두지 않아, 같은 패턴의 데이터
  마이그레이션이 늘어도 이 명령은 손대지 않는다. SCD 전용 명령으로 만들면
  이행이 끝난 뒤 죽은 코드가 된다.
- **결정 — 서버의 자동 마이그레이션은 남긴다:** 지우면 "준비 안 된 DB 로 뜨면
  죽는다" 는 새 실패 모드가 생긴다. 지금은 `db:prepare` 를 빠뜨려도 예전처럼
  느리게라도 뜬다. 서버가 마이그레이션 대신 거부하도록 바꾸는 것은 별도 작업으로
  남긴다 — 워커는 이미 그렇게 동작한다.
- **결정 — `wait_for_ready` 기본 창을 2분으로 넓힌다:** 마이그레이션이 빠진
  뒤에도 EC2 t계열은 CPU 크레딧 상태에 따라 기동 시간이 흔들린다. 정상 배포는
  첫 시도에 통과하므로 배포 시간은 늘지 않는다.
- **남은 것:** SCD 이행이 거래일 743일·버전 18,964건에 16.5초다. 거래일당 22ms 라
  줄일 여지가 있지만, 배포 경로에서 빠졌으므로 급하지 않다.

## D-048: 자본변동 효력발생일은 DART 기준일이 아니라 KRX 상장주식수 변경일이다

- **증상 — 자산곡선에 없던 봉우리가 섰다:** 2026-08-09 에 확인한 실행에서
  2024-09-27 에 평가금액이 1.78 배로 뛰었다가 2024-10-08 에 그대로 돌아왔다.
  두 날의 보유 종목·수량·현금이 같아 평가단가만 어긋난 것이었다. `maxDrawdown`
  −56.8% 는 그 허수 봉우리에서 떨어진 값이라 실행 전체의 지표가 오염됐다.
- **원인:** 자본변동 팩트의 효력발생일은 DART 증자·감자 현황의 `isu_dcrs_de`
  이고, 액면분할에서 그 날짜는 **분할 기준일**이다. KRX 일봉 주가가 분할 후
  값이 되는 날은 **변경상장일**이며 그 사이 1~2주는 주권교체로 매매거래가
  정지된다. 엔진은 효력발생일 봉에서 보유 수량에 비율을 곱하므로, 그 구간
  동안 수량만 ×비율 이고 단가는 분할 전 값이라 평가금액이 비율 배로 뛴다.
  재개 봉에서 단가가 ÷비율 되며 원래대로 돌아온다.
  `PitFactView.corporateActions` 의 "기준일 첫 봉부터 이미 분할된 가격이 온다"
  가 그대로 깨진 자리다.
- **결정 — KRX 상장주식수가 바뀐 날로 옮긴다:** 종목 마스터(SCD)가 KRX
  기초정보의 `LIST_SHRS` 를 날마다 담고 있어, 그 값이 바뀐 날이 곧 변경상장일이다.
  주가가 조정되는 날과 같은 날이라 수량과 단가가 같은 봉에서 함께 바뀐다.
  가격 점프를 탐지해 맞추는 방법은 쓰지 않는다 — 하한가·급등과 구분할 근거가 없다.
- **결정 — 비율은 DART 값을 그대로 쓴다:** KRX 주식수 비율로 갈아끼우지 않는다.
  같은 날 유상증자가 겹치면 KRX 비율에 그 몫까지 섞여 가격 보정 비율이 아니게
  된다. KRX 는 "언제" 만, DART 는 "얼마" 만 정한다.
- **결정 — 짝짓기는 날짜 창 + 비율 일치로 한다:** DART 기준일 [-30일, +90일]
  안에서 비율이 5% 이내로 맞는 상장주식수 변경 하나를 고른다. 하나의 주식수
  변경을 두 자본변동이 나눠 갖지 않고, 옮긴 결과가 같은 종목의 다른 자본변동
  날짜와 겹치면 옮기지 않는다 — `PitFactView` 가 (종목, 효력발생일)을 한 칸으로
  접으므로 겹치면 둘 중 하나가 조용히 사라진다.
- **결정 — 정렬은 워커가 한다:** 저장된 팩트는 DART 가 준 사실 그대로 둔다.
  KRX 와 맞추는 일은 실행 입력을 조립하는 자리(`backtest-child.ts`)의 몫이고,
  폐지 청산·거래불가일도 이미 같은 자리에서 조립된다. 다시 수집하지 않아도
  기존 팩트가 곧바로 고쳐진다는 실익도 있다.
- **영향 — 엔진 버전을 1.6.0 으로 올렸다:** 분할을 낀 실행은 이전 버전과
  자산곡선이 다르다. 과거 실행의 저장된 결과는 그대로 둔다.
- **알려진 한계 — 무상증자·주식배당은 여전히 어긋난다:** 그쪽은 주가가
  권리락일에 떨어지는데 주식수는 신주상장일에 늘어난다. 이 정렬은 후자로
  옮기므로 그 사이 구간의 평가금액이 실제보다 낮다. 권리락일은 지금 수집하는
  데이터 어디에도 없다. 실행 결과 경고에 이 한계를 적는다.
- **알려진 한계 — 짝을 못 찾으면 DART 기준일을 그대로 쓴다:** 종목 마스터가
  그 구간을 수집하지 않았으면 짝지을 대상이 없다. 조용히 넘기지 않고 실행
  경고에 종목을 밝힌다.

## D-049: 재무·자본변동 수동 CLI 수집을 없애고 백테스트 준비가 온디맨드로 대체한다

- **변경 내용:** `cli.ts` 의 `facts:sync` 명령(인자 파서·리포트 출력 포함)과 웹의
  수동 자본변동 동기화 버튼·전용 게이트를 지운다. 재무전략이나 PER 유니버스
  단계를 쓰는 백테스트를 준비(preparation, Task 1~10)할 때 서버가 요청 기간과
  최소 warm-up 만큼만 DART 공시를 자동으로 수집한다. 운영 문서(README·
  ONBOARDING·SPEC §28.3·`app.env.example`)도 수동 절차 안내를 지우고 이 동작을
  적는다.
- **이유:** 순서형 유니버스 파이프라인이 들어오면서 "제출 전에 필요한 재무·
  자본변동을 갖췄는지" 는 이제 준비 orchestrator 가 항상 먼저 확인하고 채운다.
  그 경로가 이미 연도·종목 범위를 스스로 계산하므로, 운영자가 `facts:sync` 로
  같은 일을 손으로 다시 지정할 이유가 없어졌다. CLI 로 남겨 두면 두 경로가
  서로 다른 답을 낼 수 있는 채로 계속 유지보수해야 한다.
- **대안 — CLI 를 과거 연도 정정공시 재수집용으로만 남긴다:** 보류. 그 유스케이스
  자체가 드물고, 준비 orchestrator 를 다시 돌리면(요청 기간을 정정 대상 연도로
  잡아) 같은 결과를 얻는다. 별도 명령을 유지하는 비용이 이득보다 크다.
- **영향 — OFS(별도) 재무는 더 이상 자동 수집 대상이 아니다:** 준비 orchestrator 는
  `consolidated: true`(연결, CFS) 로 고정돼 있다. 옛 CLI 의 `--fs-div OFS` 가 유일한
  별도 재무 수집 경로였으므로, 이 결정으로 별도 재무를 수집하는 경로 자체가
  없어졌다. 지금 등록된 전략 중 별도 재무를 요구하는 것은 없다.
- **영향 — `FactSyncService` 는 그대로 둔다:** CLI 가 부르던 서비스 자체는 지우지
  않는다. 준비 orchestrator 가 같은 서비스를 계속 재사용한다 — 지우는 것은
  CLI 진입점뿐이다.
- **호환성 — 기존 완료 백테스트 결과는 다시 쓰지 않는다:** provenance pin 의
  `selectionMethod` 가 `'ORDERED_UNIVERSE_PIPELINE'` 로 바뀌지만, 옛 값
  (`TOP_MARKET_CAP_N` 등)을 쓴 완료 run 은 마이그레이션하지 않는다. 읽을 때는
  옛 값 그대로 표시한다 — union 에 남긴 옛 pin 모양이 그 표시를 담당한다.

## D-050: 재설정 및 복제 초안은 재기준만 하고 유니버스 검증은 단계로 미룬다

- **증상:** 이미 생성된 백테스트에서 `재설정 및 복제`를 누르면 전략 화면이 늦게
  열렸다. 첫 화면은 원본 요청과 전략 목록만 필요하지만 `clone-draft`가 전체 기간의
  유니버스를 다시 해소하고 종목 등록·일봉·재무 coverage까지 검증했다.
- **원인:** 단계형 유니버스는 리밸런스 날짜마다 후보군을 다시 계산한다. 월간 10년
  요청처럼 날짜가 많으면 `clone-draft` 응답 시간이 리밸런스 횟수와 후보 종목 수에
  비례했다. 화면도 mount 직후 `/symbols`와 `/backtests/profiles`를 함께 조회했다.
- **결정 — `clone-draft`는 복원과 재기준만 한다:** 저장 요청을 현재 요청 스키마와
  전략 버전에 맞게 재기준하고 `{ request, warnings, blockers: [] }`를 반환한다.
  `blockers` 필드는 응답 호환성을 위해 남긴다. 유니버스 해소와 coverage 검증은
  유니버스 preview와 최종 제출이 맡는다.
- **결정 — 전체 종목 조회를 없애고 나머지 조회를 소비 단계에 묶는다:** 전략 목록과
  선택 전략 schema는 초기 프리필에 사용한다. 위저드는 `/symbols`를 조회하지 않는다.
  preview가 `unionSymbols` 중 실제 재무 행이 있는 종목을 `fundamentalSymbols`로 함께
  반환한다. 자본변동 행과 무자료 수집 coverage는 재무 보유로 세지 않는다.
  `/backtests/profiles`는 자본·비용 단계에서 조회한다.
- **불변:** 즉시 `복제`와 최종 `POST /backtests`는 완료된 preparation과 전체 제출
  검증을 계속 요구한다. 이 결정은 검증을 없애지 않고 사용자가 확인할 단계로 옮긴다.

## D-051: 동적 유니버스 상관 그룹은 종목쌍별 공통 봉과 활성 멤버십으로 계산한다

- **증상:** `ema-trend-switch`와 `rsi-reversion` 실행이 오류 없이 수익률 0%, 거래
  0건으로 끝났다. 백테스트 전체 기간의 유니버스 합집합에 과거 폐지 종목과 미래 상장
  종목이 함께 있으면 전 종목 공통 시각 `correlationBars`개가 생길 수 없었다. 그룹
  미확정 상태에서는 신규 진입을 전부 막지만 종료 경고도 없었다.
- **원인:** 상관 워밍업 gate가 종목쌍이 아니라 합집합 전체에 걸려 있었다. 진입 loop도
  `tradableSymbols`가 아닌 전체 합집합을 훑어, 비활성 미래 종목이 그룹을 먼저 선점한 뒤
  엔진에서 거부되면 같은 그룹의 활성 종목까지 주문을 내지 못했다.
- **결정 — pair별 공통 시각:** 각 종목쌍에 공통인 최근 봉만 맞춰 로그수익률 상관을
  계산한다. 공통 봉이 부족한 pair는 병합하지 않고 단독 그룹으로 둔다. 활성 종목 중
  하나라도 필요 봉 수를 채우면 준비된 그룹부터 사용한다.
- **결정 — 활성 멤버십 수명주기:** 그룹 계산·보유 및 대기 선점·신규 진입은 현재 활성
  멤버십만 대상으로 한다. 엔진은 거래정지·무거래를 포함한 `activeUniverseSymbols`와
  이를 제외한 당일 매수 가능 `tradableSymbols`를 분리한다. 전자는 그룹과 선점에, 후자는
  신규 주문 필터에 쓴다. 멤버십이 바뀌거나 활성 종목이 워밍업을 채우면 그룹을 다시
  계산한다. 새 멤버십에 준비된 종목이 없으면 이전 그룹을 버리고 진입을 보류한다.
- **결정 — 유한 워밍업과 종료 경고:** 동적 재계산용 종가는 종목별
  `correlationBars * 2 + 14`개만 유지한다. `TradingStrategy.completionWarnings` 선택
  훅을 추가해 마지막 활성 멤버십이 그룹을 만들지 못한 경우 필요 봉 수와 확보 최대 봉
  수를 결과에 남긴다. 정상 완료에는 경고를 추가하지 않는다.
- **버전·데이터 요구:** 실행 결과가 달라져 EMA·RSI를 1.0.2로 올린다. 두 전략은
  `requiresFundamentals`를 선언하지 않는 봉 전용 전략이라 일반 가격 기반 유니버스에서는
  재무제표를 준비하지 않는다. PER 유니버스 단계는 전략과 별개로 PER 계산용 재무를
  요구하며, 액면분할 보정용 자본변동 이력도 재무제표와 별도로 계속 준비한다.

## D-052: 결과 진단은 단계별 통과 대신 멤버십 변동을 보여준다

- **변경 내용:** 결과의 「유니버스 단계 진단」을 「종목 리밸런싱」으로 바꾼다.
  리밸런스일과 실제 기준일은 유지하고 단계별 통과 수는 화면에서 제거한다. 첫 일정은
  최초 구성 종목 수를, 이후 일정은 직전 일정 대비 편입·편출 수와 그 합계를 표시한다.
  종목별 성과 표도 제거한다.
- **이유:** 단계별 후보·통과 수는 결과를 보고 다음 실험을 정하는 근거가 약하다.
  반면 멤버십 변동 수는 리밸런싱 강도와 수익률의 관계를 비교하고 주기 변경 여부를
  판단하는 직접적인 실험 변수다.
- **계산:** 편입은 현재 일정에만 있는 종목, 편출은 직전 일정에만 있는 종목이다.
  변동 종목 수는 둘의 합이다. 최종 유니버스 크기는 거래 가능 여부와 지표 결측 등으로
  달라질 수 있어 편입 수와 편출 수를 따로 보존한다.
- **표현:** 편입 숫자는 한국 주식 화면의 상승 색인 빨간색, 편출 숫자는 하락 색인
  파란색을 쓴다. 색만으로 구분하지 않고 편입·편출 문구를 함께 표시한다.
- **데이터 경계:** 새 저장 필드를 만들지 않는다. 상세 조회가 제출 시점에 고정된
  `universeScheduleJson`을 집합 비교해 요약만 반환한다. 원본 멤버 목록은 브라우저에
  보내지 않으므로 기존 결과에도 적용되고 DB migration도 필요 없다.

## D-053: 유니버스 단계가 방향을 명시하고 ROE를 지원한다

- **결정 — 모든 단계가 방향을 저장한다:** 각 단계는 `direction`에 `HIGH` 또는 `LOW`를
  저장한다. 화면은 기준별 의미에 맞는 문구를 표시한다. 시가총액은 상위/하위, 거래량은
  상위/하위, 거래대금은 상위/하위, PER는 낮음/높음, ROE는 높음/낮음, 가격 변동은
  급상승/급하락을 사용한다.
- **결정 — ROE는 양수 재무만 비교한다:** ROE는 point-in-time 시점의 TTM 순이익을
  자본총계로 나눈 값(`TTM NET_INCOME / TOTAL_EQUITY`)이다. 순이익과 자본총계가
  모두 양수인 종목만 적격으로 남긴다.
- **호환성 — 방향이 없는 기존 요청을 보정한다:** `MARKET_CAP`·`VOLUME`·
  `TRADING_VALUE`는 `HIGH`, `PER`는 `LOW`, `ROE`는 `HIGH`, `DECLINE`은 `LOW`로
  보정한다. 새로 만드는 ROE 단계의 기본 방향도 `HIGH`다.
- **호환성 — 가격 변동 식별자는 유지한다:** 화면에는 `가격 변동`으로 표시하지만
  내부 criterion 식별자 `DECLINE`은 유지한다. 기존 방향 없는 가격 변동 단계는
  과거 동작과 같이 `LOW`로 해석한다.
- **결정 — 여섯 단계를 허용한다:** 기준은 시가총액·거래량·거래대금·PER·ROE·가격
  변동의 여섯 개이며, 같은 기준은 한 번만 쓴다. 단계 상한은 기존 5개에서 6개로
  올린다.
