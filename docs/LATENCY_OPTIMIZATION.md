# 2026-09-24 제출 지연 개선

## 확인한 원인과 범위

운영 `req-5n`의 백테스트 제출은 2026-09-24 03:45:24 KST에 시작했고
04:34:29에 연결 종료 오류가 기록됐다. 같은 구간에 다른 요청 로그가 끊겼다.
04:00~04:30 호스트 표본은 CPU 계산 사용률 1% 미만, I/O wait 약 49~51%,
디스크 사용률 약 98.8%, 약 120 IOPS였다. 해당 서비스 시작 이후 cgroup의
`high/max/oom` 이벤트는 0, 메모리 최대치는 약 483MiB였다.

따라서 이번 지연은 HTTP 프로세스의 동기 SQLite 조회와 저장장치 대기가
가장 강한 원인 후보다. 당시 쿼리별 시간이 없어 특정 SQL의 49분 실행을
확정할 수는 없다. EBS 유형·크레딧 고갈 여부도 별도 확인이 필요하다.

제출된 작업은 약 125만 봉으로 추정돼 로컬 실행 예산 약 21만 봉을 넘었다.
접수 지연과 실행 가능한 에이전트를 기다리는 큐 대기는 별개다. 이 변경은
기존 메모리·봉 수 안전 한도를 해제하지 않는다.

## 변경 계약

- 제출·즉시 복제·재설정 복제·난수 복제·기간 검증은 같은 검증 서비스를 사용한다.
  HTTP 성공은 검증 완료 후 기존 201 응답이며, 준비 부족과 데이터 오류의 기존
  400/409/422 응답을 유지한다. 준비 상태를 추가하거나 먼저 접수하지 않는다.
- 검증 SQL과 재무 검사는 별도 자식 프로세스에서 실행한다. 운영 DB는 읽기 전용으로
  열고 연결 전체에 `query_only`를 적용한다. 마이그레이션·수집·작업 생성은 하지 않는다.
- 검증 시작 시 읽기 트랜잭션으로 데이터 revision을 고정한다. 큐 등록과 난수 배치 생성의
  IMMEDIATE 트랜잭션에서 같은 dataset ID/revision을 확인한다. 변경됐으면 409다.
- 검증 자식은 최대 하나, 실행 포함 대기 요청은 최대 넷이다. 포화는 429,
  자원 부족은 507, 검증 시간 초과·종료는 503이다. 실행 제한은 120초이며
  접속 종료나 서버 종료 시 SIGTERM 후 1초 뒤 SIGKILL로 회수한다.
- RSS 예산은 서버가 계산한 가용량과 192MiB 중 작은 값이다. 시작 최소치는
  128MiB, V8 young generation semi-space는 4MiB다. 실행 중 RSS·서버 메모리
  압력을 확인한다. 같은 프로세스 실행은 의존성을 주입하는 테스트에만 사용한다.
- 전체 이력 coverage는 한 검증 안에서 한 번 재사용한다. 기존 봉 수 추정식과
  오류 우선순위를 유지한다. 필요 간격이 0인 전략은 일봉 타임라인을 읽지 않는다.
- 유효한 KOSPI/KOSDAQ OHLCV의 `(short_code,date)` 부분 인덱스를 추가한다.
  인덱스와 조회가 동일한 리터럴 조건을 공유하여 봉 본문을 읽지 않고 날짜를 집계한다.

## 배포 시 확인

운영 배포와 DB 변경은 이 작업에서 실행하지 않았다. 첫 기동의 데이터 DB migration
`0004_valid_daily_bar_lookup`은 기존 봉을 한 번 읽어 인덱스를 만든다. 운영 데이터의
복사본에서 소요 시간·추가 디스크 사용량을 확인하고 유지보수 시간에 적용한다.
스키마의 컬럼·작업 형식은 바뀌지 않으며 데이터/미리보기 내용 버전은 기존 빌드 규칙대로
갱신된다. 오래된 준비 결과는 기존 현재성 검사를 거친다.

느린 동기 SQL을 실제 검증 자식에 넣는 테스트에서 부모 `/health/ready`의 1초 이내
응답을 검사한다. 이는 이벤트 루프 격리 검증이다. 1GB 운영 호스트의 cgroup·실제 느린
EBS를 재현한 부하 시험은 별도로 필요하며, 수집·스냅샷 게시 등 다른 I/O도 계속 관찰한다.
