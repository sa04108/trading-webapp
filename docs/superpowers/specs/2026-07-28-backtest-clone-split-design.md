# 백테스트 복제 2갈래 + 제출 검증 보강 설계

날짜: 2026-07-28
관련: 스펙 §10 §15, D-024 (일봉 timeframe 버그 — 이 기능의 회복 대상)

## 목적

이미 뽑은 백테스트를 다시 돌리는 두 가지 의도를 분리한다.

- **복제** — 같은 조건 그대로 재실행. 중단된 작업의 복구 경로(§10)이고, 지금 있는 동작이다.
- **재설정 및 복제** — 원본 값을 출발점으로 삼되 전략부터 다시 고른다. 조건이 틀려서
  실패했거나, 파라미터 하나만 바꿔 비교하고 싶을 때의 경로다.

지금은 전자만 있어서, 조건을 바꾸려면 위저드를 처음부터 손으로 다시 채워야 한다.
D-024 처럼 기간·종목이 어긋나 실패한 작업은 "같은 조건 재실행"이 구조적으로 무의미한데
그 버튼만 제공되고 있었다.

작업하며 드러난 인접 결함을 함께 고친다: **제출 검증이 기간에 봉이 있는지 검사하지
않는다.** D-024 의 실행이 201 로 접수되고 한참 뒤에 FAILED 로 끝난 이유다.

## 1. 제출 검증 보강 (신규 제출·복제 공통)

`validateSubmission` 은 전략·파라미터·데이터셋 존재·심볼 멤버십·버전·비용 프로파일·
`from > to` 를 본다. **기간에 실제로 봉이 있는지는 보지 않는다.** 심볼 멤버십도
`dataset.symbols`(설정된 유니버스) 기준이라, 증권사 데이터셋에서 아직 한 번도 동기화되지
않은 종목이 통과한다. 그래서 확실히 0봉으로 실패할 제출이 접수된다.

`datasets.getCoverage(datasetId)` 의 심볼별 `firstTsMs`/`lastTsMs`/`barCount` 로 겹침을
검사한다. 커버리지는 메타데이터라 Parquet 을 읽지 않는다 — 제출 검증에 붙일 만큼 싸다.

- 종목에 봉이 있다고 보는 조건: `barCount > 0` 이고 `firstTsMs`/`lastTsMs` 가 비어 있지
  않고 `lastTsMs >= fromTsMs && firstTsMs <= toTsMs`.
- **요청한 모든 종목이 구간에 봉이 없으면 400.** 확실히 실패할 제출이니 즉시 거부하고,
  메시지에 커버리지 범위를 담는다 — `005930 의 데이터는 2025-11-03 ~ 2026-07-27 입니다`.
  진단이 커버리지 화면으로 곧장 이어지게 한다 (D-024 에서 메시지가 반대로 밀었던 실수).
- **일부 종목만 없으면 거부하지 않는다.** 신규 상장처럼 이력이 짧은 종목은 정상이다.
  대신 자식 프로세스가 0봉으로 끝난 종목을 실행 경고로 기록한다 — 이미 `warningsJson`
  경로가 있고, 자식은 어떤 심볼이 봉을 냈는지 정확히 안다(커버리지 추정이 아니라 실측).
  조용히 넘기지도, 과하게 막지도 않는 선이다.

### `from`/`to` → tsMs 변환 공유

제출 검증과 자식이 각자 계산하면 어긋난다 — 제출 검증은 통과시키는데 자식은 0봉을 보는, **D-024
와 똑같은 종류의 결함**(한 사실을 두 곳에서 따로 아는 것)이다.

`src/shared/schemas/backtest-request.ts` 에 `periodToTsRange(period)` 를 두고
`backtest-routes.ts` 와 `backtest-child.ts` 가 함께 쓴다. 두 파일은 이미 이 모듈을
import 하고 있고 §7 의존성 규칙에도 걸리지 않는다. 경계는 현행 자식 구현과 동일하게
`from T00:00:00Z` ~ `to T23:59:59.999Z` 로 고정한다.

### 대기열 상한

`enqueue` 에는 대기열 깊이 제한이 없다. `복제` 를 연타하면 QUEUED 가 무한히 쌓인다.
동시 실행은 `MAX_CONCURRENT_BACKTESTS`(기본 1, 최대 4)가 이미 묶고 있어 서버가 죽지는
않는다 — 과장하지 않는다. 실제 문제는 리소스 가드가 **제출 순간**의 여유 메모리·디스크만
보고 이미 쌓인 대기열은 보지 않는다는 것이다. 1GB 박스에서 건당 수 분이면 몇 시간짜리
대기열이 생기고, 되돌리려면 하나하나 취소해야 한다.

`MAX_QUEUED_BACKTESTS`(기본 20, 1~200)를 두고 제출 시 QUEUED 개수가 상한 이상이면
**429** 로 거부한다. 신규 제출·복제 공통이며, 이미 있는 `queue.countByStatus(['QUEUED'])`
로 센다.

- **QUEUED 만 센다.** 실행 중(STARTING/RUNNING/CANCELLING)은 동시 실행 상한이 이미
  묶고 있다. 그것까지 합치면 상한의 뜻이 흐려진다.
- **429 는 507 과 구분한다.** 507(리소스 가드)은 호스트 자원 부족이고 429 는 "요청을
  너무 많이 넣었다"다. 사용자가 할 일이 다르다 — 기다리거나 취소하거나.
- 검사 위치는 `backtest-routes.ts` 로, 리소스 가드(`checkResources`) 바로 옆이다.
  `JobQueue` 는 설정을 모르는 단순 저장소로 남긴다.
- `재설정 및 복제` 도 결국 `POST /backtests` 이므로 같은 상한을 받는다. 다만 위저드는
  사용자가 한 번 명시적으로 제출하므로 연타 위험은 `복제` 쪽에만 있다.

## 2. 두 경로

| | 복제 | 재설정 및 복제 |
|---|---|---|
| 경로 | `POST /backtests/:id/clone` → 재기준 → 검증 → 즉시 대기열 | `/backtests/new?from=<jobId>` → 위저드 프리필 → 사용자 제출 |
| 제출 | 서버가 대신 | 사용자가 검토 후 `POST /backtests` |
| 검증 | 막는다 (현행 검사 + 위 보강) | 초안에서 알리고, 제출 시 막는다 |

**검증은 세 지점 모두에서 매번 돈다:** `복제`(막음) · 초안(알림) · 제출(막음).
검증 없이 대기열에 들어가는 경로는 없다.

**계보는 기록하지 않는다.** 재설정 경로는 전략까지 바꿀 수 있어 "원본의 복제"라 부르기
애매해진다. 평범한 신규 제출로 두고 감사 로그에는 `backtest.created` 로만 남긴다 —
요청 스키마와 감사 필드를 늘리지 않는다.

## 3. 서버 — `GET /backtests/:id/clone-draft`

```
GET /backtests/:id/clone-draft → { request, warnings: string[], blockers: string[] }
```

- `rebaseStoredRequest` 를 재사용한다. 위저드는 **재기준된** 요청이 필요하다 — 구 스키마
  요청도 되살려야 하고(§10), 재기준은 서버 로직이라 클라이언트가 할 수 없다.
- 읽기 전용 GET. 대기열에 넣지 않고 데이터셋 버전도 고정하지 않는다.
- **검증을 돌리되 막지 않는다.** `validateSubmission` 을 그대로 호출하고 실패 사유를
  `blockers` 로 돌려준다. 여기서 400 으로 끊으면 **고칠 화면 자체가 열리지 않는다** —
  조건이 틀어진 백테스트를 고쳐 다시 내는 것이 이 경로의 유일한 존재 이유다. 검증은
  차단이 아니라 안내이고, 실제 차단은 제출 시점 `POST /backtests` 가 그대로 지킨다.
- 재기준 자체가 불가능하면 400 (`rebaseStoredRequest` 의 에러 메시지), 없는 id 는 404.

`validateSubmission` 은 현재 첫 실패에서 즉시 반환한다. `blockers` 가 사유를 모아
보여주려면 전체 사유를 수집하는 형태로 바꿔야 한다. 반환을 `{ ok, error }` 에서
`{ ok, errors: string[] }` 로 넓히고, `POST`/`clone` 은 `errors[0]` 을 400 메시지로 쓴다.

**검사 순서를 현행과 동일하게 유지한다** — 기존 테스트가 특정 400 메시지를 기대하므로
(`005935` 를 담은 심볼 거부 등) `errors[0]` 이 지금과 같은 첫 실패여야 한다.

**의존 검사는 여전히 가드가 필요하다.** 전부 수집하는 형태로 바꾸면서 앞선 검사 결과에
의존하는 검사를 무조건 실행하면 터진다 — 데이터셋이 없을 때 `dataset.symbols` 를 읽거나,
전략이 없을 때 파라미터를 검증하는 경로다. 전략·데이터셋처럼 후속 검사의 전제가 되는
항목은 실패 시 사유를 담고 그에 딸린 검사를 건너뛴다.

## 4. 웹

### 위저드 프리필

`NewBacktestWizard` 가 `?from=` 을 읽어 초안을 조회하고 폼 상태를 **한 번만** 시드한다.
`step` 은 0(전략) 유지 — 처음부터 고르는 것이 이 경로의 요청 사항이다.

- 순수 변환 함수 `requestToFormState(request, datasets, strategies)` 로 분리한다. 위저드는
  결과를 setState 할 뿐이고, 변환 규칙은 단위 테스트로 고정한다.
- **`seededFor` 충돌 주의:** 기존 effect 가 `strategyId` 변화를 감지해 파라미터를 스키마
  기본값으로 덮어쓴다. 프리필로 strategyId 를 심으면 원본 파라미터가 날아간다 → 프리필
  시 `seededFor.current` 를 같이 세팅해 기본값 시딩을 건너뛴다. 사용자가 나중에 전략을
  직접 바꾸면 `pickStrategy` 가 `seededFor.current = null` 로 리셋하므로 새 전략의
  기본값은 정상 동작한다.
- 초안 로딩 중에는 폼 대신 스켈레톤을 보여준다 — 사용자가 입력하던 값이 프리필에 덮이는
  경합을 없앤다.
- 헤딩은 "재설정 및 복제"(신규 생성 시에는 "새 백테스트").
- `blockers` 는 1단계 상단에 destructive Alert 으로, `warnings`(재기준 알림)는 그 아래
  일반 Alert 으로 띄운다. 6단계까지 눌러가서 400 을 맞지 않게 하는 것이 목적이다.

### 사라진 참조 처리

원본이 가리키는 데이터셋·종목·전략이 그 사이 지워질 수 있다. 조용히 통과시키면 사용자가
모르고 제출한다. `blockers` 가 사유를 말해주고, 폼은 고를 수 있는 상태로 만든다.

- 데이터셋이 없으면 데이터셋·종목을 비운다 (2단계에서 다시 고른다).
- 데이터셋은 있고 일부 종목만 없으면 교집합만 남긴다.
- 전략이 등록 목록에 없으면 전략을 비운다 (1단계에서 다시 고른다).

### 상세 페이지 버튼 (상황별 강조)

터미널 상태에서 둘 다 노출하되 순서·강조를 상황에 맞춘다.

- **FAILED** → `재설정 및 복제`(주버튼, 앞) + `복제`(외관선)
- **그 외 터미널** → `복제`(주버튼, 앞) + `재설정 및 복제`(외관선)

중단(INTERRUPTED) 안내문의 인라인 링크는 `복제` 를 유지한다 — §10 복구는 동일 재실행이
맞고, 서버 재시작은 조건 문제가 아니다.

## 5. 테스트

- 통합 (제출 검증): 전 종목이 구간 밖 → 400 + 커버리지 범위 메시지 / 일부만 밖 → 201 통과 후
  실행 경고 기록 / 동기화 안 된 종목 → 400. 신규 제출과 `복제` 양쪽에서 확인한다.
- 통합 (대기열 상한): 상한까지 채운 뒤 제출 → 429, 신규·복제 양쪽 / 상한 미만이면 201.
- 통합 (초안): 왕복 / 구 스키마 재기준 + warnings / **데이터셋이 삭제된 원본도 초안을
  반환하고 blockers 에 사유가 담긴다**(막지 않음 — 이 경로의 존재 이유) / 없는 id 404.
- 통합 (회귀): 기존 `/clone` 성공·거부 동작 불변.
- 단위: `periodToTsRange` 경계 / `requestToFormState` — 정상 프리필, 데이터셋 소실,
  종목 부분 소실, 전략 소실.

## 6. 범위 밖

- 계보·파생 트리 UI.
- 목록 페이지에서의 복제 (카드 전체가 링크인 현 구조를 건드리지 않는다).
- 실행 중 작업의 복제 (지금처럼 터미널 상태에서만).
- 휴장일 캘린더를 근거로 한 기간 검증 — 커버리지 범위 겹침까지만 본다 (D-006).
- 파라미터 스윕·배치 실행 — 별개 기능이다.
