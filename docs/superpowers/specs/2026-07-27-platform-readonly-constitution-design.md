# 플랫폼 read-only 헌법 개정 — 평면 분리·TOTP 복원·퍼블릭 노출 설계

- 날짜: 2026-07-27
- 상태: 사용자 승인 (섹션별 승인 완료)
- 관련 결정: D-014 (부분 폐기), D-016 (폐기), D-017 (신규 — 이 문서)

## 1. 배경과 동기

지금까지의 보안 모델은 "플랫폼 전체를 사설망(Tailscale) 뒤에 숨긴다"였다. 그
전제 위에서 TOTP 를 제거했고(D-014), 퍼블릭 22 를 닫는 하드닝과 락아웃 가드
체계를 만들었다(D-016).

이번 개정은 전제 자체를 바꾼다: **플랫폼의 권한을 줄이는 대신 노출을 허용한다.**
플랫폼이 돈을 움직일 수 없다면, 플랫폼 침해의 최대 피해는 정보 노출과 백테스트
리소스 낭비로 한정된다. 그 수준의 표면에는 비밀번호 + TOTP 로 충분하며, 사설망
경계와 그에 딸린 운영 부담(Tailscale control plane 의존, 노드 키 만료, 락아웃
가드)이 필요 없어진다.

## 2. 새 헌법 원칙 (스펙 §2 수준 불변식)

### 2.1 평면 분리

- **플랫폼(웹)** 은 조회 평면이다: 자동매매 결과 조회, 백테스트 생성·실행·취소,
  백테스트용 데이터 관리(CSV 업로드·동기화), 그리고 비상정지(킬스위치 끄기).
- **SSH CLI** 는 제어 평면이다: 자동매매 전략 변경, 주문·자금에 관한 직접 조작,
  자동매매 재개, TOTP 등록·재설정 등 보안 설정 변경.
- 웹 API 에는 제어 평면 엔드포인트를 만들지 않는다. "웹에서 없는 기능"이
  이 설계의 방어선이므로, 편의를 이유로 제어 기능을 웹에 추가하는 것은
  헌법 개정 사항이다.
- 제어 평면의 형태는 우선 CLI 로 한다. 별도 GUI 는 미정 — 도입하더라도
  SSH 터널 등 제어 평면과 같은 접근 경계 안에 있어야 한다.

### 2.2 킬스위치는 단방향

- 플랫폼은 자동매매를 **끌 수만** 있다 (fail-safe). 켜는 경로는 CLI 전용.
- 근거: 세션 탈취 시 "끄기"의 최대 피해는 기회비용이지만 "켜기"는 공격자에게
  돈을 움직일 길을 연다. 킬스위치의 본래 목적(긴급 중단)에는 끄기만으로 충분하다.
- 구현 시점: 자동매매 엔진과 함께. 소비자 없는 코드를 미리 만들지 않는다(D-009).

### 2.3 데이터 경로 분리 (실전 단계 예약)

- 현재: 플랫폼의 데이터 쓰기(CSV 업로드, 증권사 동기화)를 허용한다 —
  백테스트는 데이터가 있어야 의미가 있다.
- 실전 매매 도입 시: 실전 신호가 읽는 데이터 경로와 플랫폼에서 쓰기 가능한
  백테스트 데이터 경로를 분리한다. 플랫폼에서의 데이터 오염이 실전 신호에
  간접 영향을 주는 경로를 차단하기 위함이다. 분리 방식(디렉터리, 스냅샷,
  검증 게이트 등)은 그 시점의 요구에 맞춰 설계한다.

## 3. 인증 — TOTP 복원 (D-014 부분 폐기)

D-014 의 제거 근거는 "사설망 경계가 이미 접근을 제한한다"였다. 그 경계가
사라지므로 전제가 소멸한다. D-014 스스로 적어둔 대로 "그 시점의 요구에 맞춰
새로 설계"한다 — revert 가 아니라 재구현이다 (D-015 스쿼시로 마이그레이션
이력이 리셋됐고 이후 코드도 변했다). 제거 직전 구현(`dd00ac5^`)은 참조 자료로
쓴다.

대안으로 passkey(WebAuthn)를 검토했다 — 피싱 내성은 더 강하지만 단일 사용자
환경에서 TOTP 의 단순함(서버는 secret 하나, 클라이언트는 아무 OTP 앱)이 낫다고
판단했다.

### 3.1 스키마 (0000 스쿼시에 흡수)

`users.totp_secret`, `users.totp_enabled`, `users.recovery_code_hashes_json`,
`sessions.pending_totp` — D-014 가 지운 4개 컬럼을 복원하되, 별도 마이그레이션을
추가하지 않고 기존 0000 마이그레이션·스냅샷에 흡수해 재생성한다(스쿼시).

- 근거: 아직 배포 전이다. D-015 가 확인했듯 스쿼시는 모든 기존 DB 를 버릴 수
  있을 때만 가능하고, 지금이 그 시기다. 배포된 적 없는 2단계 이력(0000→0001)은
  보존 가치가 없다.
- 영향: 로컬 개발 DB 폐기 → `pnpm cli admin:create` 재실행 (D-015 와 동일).
- D-010(expand-contract)은 배포된 DB 를 전제로 하는 원칙이므로 D-014 때와 같은
  이유로 적용 대상이 아니다.

### 3.2 로그인 흐름 (2단계)

1. 비밀번호 검증 성공 → `pending_totp=1` 세션 발급. 이 세션은 `requireAuth` 를
   통과하지 못하며 TOTP 검증 라우트만 접근할 수 있다.
2. `POST /api/v1/auth/totp/verify` — 성공 시 세션 회전(새 세션 ID 발급, 회전
   시점이 인증 완료 시점으로 복귀). 실패는 로그인 실패 잠금(5회/15분)에 합산.
3. 복구 코드: TOTP 분실 시 대체 입력 경로. 1회용, Argon2 해시로 저장.

### 3.3 등록·재설정은 CLI 전용

`pnpm cli totp:enroll` 이 otpauth:// URI + base32 secret + 복구 코드를 출력한다.
웹에서는 TOTP 등록·해제·재설정을 **할 수 없다** — 세션 탈취자가 2FA 를 자기
기기로 바꿔치기하는 경로를 차단하며, §2.1 의 "보안 설정 변경은 CLI" 원칙과
일치한다.

### 3.4 전환 순서 보장

- `totp_enabled=0` 계정은 종전대로 비밀번호만으로 로그인된다 — Tailscale 경계가
  아직 있는 동안만 허용되는 상태다.
- 인프라 전환(§4)의 사전 체크리스트에 "관리자 계정 TOTP 등록 완료 확인"을 넣어
  퍼블릭 노출 시점에는 반드시 2단계가 켜져 있게 한다.
- 서버는 부팅 시 `totp_enabled=0` 인 계정을 발견하면 로그에 경고한다.

### 3.5 의존성·테스트

- `otpauth` 재추가 (D-004 의 원래 선택, zero-dep).
- 단위: 코드 검증 창, 복구 코드 1회성. 통합: 2단계 흐름, pending 세션의 보호
  라우트 차단, 실패 잠금 합산, 세션 회전.

## 4. 인프라 — Tailscale 제거, 퍼블릭 + Caddy (D-016 폐기)

### 4.1 노출 모델

퍼블릭 인터넷 + 도메인. TLS 종단은 Caddy 복원(D-016 이전 방식) —
`<도메인> → reverse_proxy 127.0.0.1:3000`, Let's Encrypt 발급·갱신 자동.
Caddy 는 공식 apt repo 로 설치해 unattended-upgrades 대상에 포함한다.

중복 방지: HSTS·보안 헤더는 D-016 때 앱(`SECURITY_HEADERS`)으로 옮겼고 압축도
`@fastify/compress` 에 있으므로 Caddy 에는 리버스 프록시 역할만 둔다.

### 4.2 방화벽·SSH

- UFW: `default deny incoming` + 22(`ufw limit` 으로 브루트포스 속도 제한),
  80(ACME/리다이렉트), 443 허용.
- **퍼블릭 22 는 닫지 않는다.** 클라우드 브라우저 SSH 콘솔이 퍼블릭 22 를 쓰므로
  이것이 out-of-band 복구 경로가 된다.
- sshd 하드닝(`99-quant-hardening.conf`: PermitRootLogin no,
  PasswordAuthentication no, MaxAuthTries 3 등)은 유지한다.
  - **Lightsail web SSH 를 막지 않는다**: 브라우저 SSH 는 AWS 가 관리하는 기본
    키 페어로 `ubuntu` 사용자에 접속하는 **키 인증**이다. 이 설정이 끄는 것은
    비밀번호 인증뿐이므로 브라우저 SSH 경로에는 아무 영향이 없다.
  - 유지 이유: 하드닝의 대상은 "누가 접속하느냐"가 아니라 "열린 포트가
    인터넷으로부터 무엇을 받아주느냐"다. 퍼블릭 22 에는 봇의 비밀번호 추측
    시도가 상시로 들어오는데, 이 7줄이 그 공격 부류 전체를 원천 무효화한다
    (추측할 비밀번호 인증 자체가 없음). Ubuntu 클라우드 이미지의 기본값도
    비밀번호 인증 꺼짐이지만, 기본값은 패키지 설치나 수동 설정으로 조용히
    바뀔 수 있으므로 명시적으로 고정한다. 비용은 설정 파일 하나다.

### 4.3 provision.sh — 2단계 구조 폐지

`--harden` 게이트가 존재했던 이유는 "퍼블릭 22 를 닫으면 되돌릴 경로가
없다"였다. 22 를 유지하므로 락아웃 가드 체계(tailnet SSH 실증, `tag:server`
확인, BackendState 검사) 전체가 불필요해진다 — 단일 실행으로 통합한다.

- 제거: Tailscale 설치·조인·`tailscale serve` 블록, `--harden` 분기.
- 추가: Caddy 설치·Caddyfile, UFW 규칙(§4.2), 도메인 A 레코드가 이 서버의
  고정 IP 를 가리키는지 선행 확인, 인증서 발급 확인.
- 유지: Node 설치, sshd 하드닝, unattended-upgrades, 고정 아웃바운드 IP
  정보성 확인.

### 4.4 bootstrap.sh

tailnet 조인·auth key·SSH 실증 로직을 제거하고 퍼블릭 IP/도메인으로 직접
SSH → provision.sh 전송·실행. 검증은 SSH 접속 →
`https://<도메인>/api/v1/health/live` 200 확인으로 갈음한다.

### 4.5 전환 절차 (하드닝된 기존 서버) — 순서가 락아웃을 결정한다

1. 관리자 계정 TOTP 등록 확인 (§3.4 게이트)
2. UFW 에 22/80/443 퍼블릭 허용 추가 (이 시점부터 퍼블릭 SSH 복귀)
3. Caddy 설치 → 도메인 검증 → 인증서 발급 확인
4. `tailscale serve` 해제 → tailscale 제거
5. 클라우드(Lightsail) 방화벽도 22/80/443 만 열려 있는지 확인

### 4.6 변하지 않는 것

앱의 `127.0.0.1:3000` bind(인프라 무지 원칙), 고정 아웃바운드 IP 요구(§18),
deploy.sh·backup.sh 동작, 로그인 rate limit, 세션 정책. CT 로그에 도메인이
공개되지만 퍼블릭 서비스 전제이므로 무해하다.

## 5. 위협 모델 요약 (개정 후)

| 위협 | 방어 |
| --- | --- |
| 웹 세션 탈취 | 피해 상한 = 조회 + 백테스트 낭비 + 자동매매 끄기(기회비용). 돈을 움직이는 경로 없음(§2.1), 2FA 바꿔치기 불가(§3.3) |
| 비밀번호 유출 | TOTP 2단계(§3) |
| 웹 브루트포스 | 로그인 실패 잠금 5회/15분, TOTP 실패 합산 |
| SSH 브루트포스 | 키 전용 인증, `ufw limit`, 비밀번호 로그인 금지 |
| 데이터 오염 → 실전 신호 | 실전 단계에서 경로 분리(§2.3 예약) |
| 락아웃 | 퍼블릭 22 유지 + 클라우드 브라우저 SSH 콘솔 = out-of-band 경로 상시 존재 |
